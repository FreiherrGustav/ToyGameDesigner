# Toy Game-Maker

## What this is

A "toy" game-maker for kids — structurally different from Scratch/GDevelop
(which require authored logic before anything fun happens) and from
Minecraft/Roblox (finished games you build *inside*, not constructed from
near-nothing). Closer in spirit to Bitsy, but not narrow to one genre:
continuous physics, rooms, and a growing tile vocabulary let it reach
Flappy-Bird-shaped, Dig-Dug-shaped, and Pitfall/Donkey-Kong-shaped games
from the same fixed piece set.

## Non-negotiable design principles

These have held under real pressure across the whole build. **Don't
compromise them for a new feature without flagging it explicitly to the
user first.**

- **No scripting layer, ever.** No if/then, no event/action authoring, not
  even a visual one. All behavior is a fixed, closed reaction table — kids
  compose by placing pieces, never by writing rules. Every feature added has
  stayed a placed piece with a fixed effect; this is the thing most likely
  to erode silently if not actively protected.
- **Always live — no edit/play mode split.** Painting a tile, flipping
  gravity, editing a room all take effect immediately in a running
  simulation. No "test my game" button anywhere in Build mode. (Build and
  Play *do* exist as two modes — see Architecture below — but the
  distinction is about stakes/snapshotting, never about "nothing happens
  until you press play.")
- **Tile vs. marker rule.** A property is a painted **tile** if its effect
  is only felt on contact with that specific cell (solid, hazard, bouncy,
  sticky...). It's a placed **marker** if it changes the rules of a whole
  zone regardless of contact (gravity, wrap). Sort new ideas by this test
  before deciding how a kid places them. (Game Rules — gravity/h-wrap/v-wrap
  — are the marker end of this spectrum: whole-room toggles, not painted
  cells; see `GAME_RULES`.)
- **Modifiers are geometry-agnostic.** `slippery`/`bouncy`/`hazard`/
  `lethal`/`sticky`/`wind` all combine with either `solid` or walkable
  (`none`) geometry; the combination determines the reading (a solid+bouncy
  tile bounces you off it, none+hazard is a puddle you walk through,
  none+lethal is lava, solid+lethal is a spike trap, none+sticky is mud you
  trudge through, solid+sticky is a wall you can climb). v2.20 removed
  `spring` — it was a second, higher-restitution tuning of `bouncy` with no
  distinct reading of its own; that "extra bounce power" idea now lives on
  the dedicated Trampoline *object* instead (see Architecture below), which
  is a better fit anyway per the very next principle.
- **Kid-friendly naming, not implementation-jargon.** "Temperament,"
  "geometry," and "channel" all got renamed once already for reading as
  design-jargon rather than words a kid would use (they persist as
  *internal* variable/field names — that's fine, code can stay precise —
  but anything user-facing must read like a toy, not an engine). Watch for
  this recurring — it's an easy mistake to reintroduce. `MODIFIER_LABELS`
  is the established mechanism for renaming a palette-facing label without
  touching the internal id/serialization format — it briefly held `bouncy`
  → "trampoline" in v2.19, reverted in v2.20 once "trampoline" became a
  real placed object instead (having the same word mean two different
  things — a modifier's display name AND an unrelated object — was the
  actual problem users hit, not the renaming mechanism itself).
- **Characters and Objects get real sprites; Ground stays abstract
  squares.** Identity matters for things with a specific function (what a
  door does, what a chaser does); it doesn't matter for pure terrain. No
  colored role-frame around pieces — it was tried, tested badly, removed
  (v2.14).
- **Win is unconditional.** Touching `goal` or completing full collection
  always wins, full stop — no room-topology check. An earlier, cleverer
  version conditioned this on room graph position and broke the moment
  loops became possible; the fix was simplifying, not patching further
  (v2.11).
- **Stakes (lives, game over, win) only exist in Play mode.** Build mode
  stays frictionless — getting caught just resets, forever, no consequence.
  This is deliberate, not a missing feature. (`consumeLifeIfPlaying()` is a
  no-op outside Play — this is the actual mechanism, not a special-cased
  check scattered everywhere.)
- **Sound is entirely synthesized, nothing sampled.** Even creature/voice
  sounds (cat, dog, chicken) are stylized synthesis, not recorded or
  library audio — keeps the whole audio palette consistent with everything
  else being generated by the same underlying system, and avoids
  file-size bloat in the single-file architecture (v2.18).
- **Single self-contained HTML file, no build step, no framework.** This is
  architectural, not incidental — it's what makes the standalone export
  (v2.7) a natural extension (dump the same runtime + a data blob into a
  second HTML file) rather than new infrastructure.

## Architecture

Everything lives in **one file**: `index.html` (~6,600 lines as of the last
patch — check current line count, it only grows). No `npm install`, no
bundler, no `<script src>` to anything but itself. Open it in a browser and
it runs. This is the whole "app."

### The tile model

A cell is a small stack of independent layers, not one value:

- **`board[y][x]`** — `"geometry:modifier"` (e.g. `"solid:bouncy"`,
  `"none:lethal"`, `"cannon-ne:none"`). Geometry decides what blocks
  movement / does the interesting mechanical thing; modifier is the
  contact reaction layered on top. `gameplayKey(geometry, modifier)`
  builds this string; `geometryAt(x,y)`/`modifierAt(x,y)` split it back.
- **`backgroundBoard[y][x]`** — pure decoration, never touches physics.
- **`colorBoard[y][x]`** — the switch/door/plate/fan **channel color** tag
  (`CHANNEL_COLORS`), independent of geometry/modifier. `isColorTaggable(geometry)`
  gates which geometries can even carry one.
- **`groundSkinBoard[y][x]` / `groundSkinRotationBoard[y][x]`** — which
  named Ground/Lethal skin (grass, stone, lava, spikes...) is painted over
  a plain geometry+modifier combo, purely cosmetic re-skinning of the same
  underlying mechanic (see `groundTileDefs`).

**`GEOMETRIES`** (current, see `index.html` for the live list — this drifts
every patch, don't trust this snapshot blindly):
`none, solid, diggable, trap, goal, switch, plate, door, cannon-ne/se/sw/nw,
bomb, warp, fan-n/e/s/w, magnet, gravitywell, spawner, trampoline`.

A recurring trick: a geometry family with several storable orientations
(`CANNON_ORDER`, `FAN_ORDER`, and the modifier-axis `WIND_ORDER`) shows as
**one swatch** in the palette; a second click on an already-placed tile of
that family rotates it to the next orientation (`cannonRotateStrokeCells`
tracks this per-stroke). Any new multi-orientation piece should reuse this
exact pattern, not invent a new one.

**`MODIFIERS`**: `none, slippery, bouncy, hazard, lethal, sticky,
wind-n/e/s/w`. `MODIFIER_LABELS` is currently empty (`{}`) — it's the
mechanism to reuse any time an internal id needs a friendlier palette name
without a serialization-format migration, not a promise that it's holding
anything right now.

**`TEMPERAMENTS`** (actor self-steering, palette-selectable in the
Character tab): `stationary, wanderer, chaser, fleer`. There are also
actor "kinds" that exist outside this list: `PUSHABLE_KIND` ("pushable" —
full physics, zero self-steering, palette-selectable from the Objects tab
via `OBJECT_ACTOR_KINDS`), `"collectible"` (palette-selectable presets,
picked up on contact), and `HAZARD_BALL_KIND` ("hazardball" — same
zero-steering physics shape as pushable, but always bounces off walls and
always hurts on touch; **spawner-only**, never placeable from a palette
swatch — it's the spawner's default/fallback content, not a kid-facing
piece).

**Important, easy to miss:** not everything in the Objects-tab swatch row
is an actor. `goal, switch, plate, door, cannon, bomb, warp, fan, magnet,
gravitywell, spawner, trampoline` are **geometry tiles** (clicking them
calls `selectGeometry`, painting `board`); only `pushable` (and
collectibles, in their own row) are real **actor kinds** (clicking them
calls `selectActorKind`, setting `selectedActorDefId`/`paintMode =
"actor"`). This distinction matters a lot for anything that reads
`selectedActorDefId` — clicking a geometry-tile swatch does **not** change
it.

**v2.21 nuance to the above**: bomb/magnet/cannon/trampoline are still
painted geometry tiles exactly as described — but a kid can grab one with
the carry key (see Grab/carry/drop/throw below), which turns *that one
placed cell* into a real actor (`CARRY_BOMB_KIND` etc.) on the spot. The
palette/painting story is unchanged; this only matters once something is
already on the board and gets grabbed.

**v2.21, a second nuance**: bomb, magnet, cannon, fan, and spawner are all
now **physical** — `isBlockingGeometry` returns true for every one of them,
same as solid/diggable/Trampoline. Direct feedback: walking straight
through them (they used to be pure contact-trigger pads, like goal/switch)
made grabbing one feel glitchy, since there was nothing there to physically
register the interaction against. Fan and spawner are blocking-only for now
— not carryable — since both are architecturally tied to a fixed board cell
(fan's force calc and spawner's whole contents/timer/concurrency-cap system
scan `geometryAt`, not the `actors` array); making them carryable is a
bigger, explicitly deferred follow-up, not attempted here. See "Physical
objects vs. fixtures" and "Grab / carry / drop / throw" below for the full
story, including what had to change so bomb-arm/cannon-fire still work now
that touching them no longer means overlapping them.

**Trampoline (v2.20)** is a plain, single-orientation geometry tile (no
`_ORDER` family, unlike cannon/fan) — a real object with a real sprite
(`GEOMETRY_ICONS.trampoline`), blocking like solid (`isBlockingGeometry`),
that always bounces the player (and a hazard ball) at `TRAMPOLINE_RESTITUTION`
(0.97) with a minimum enforced launch speed (`TRAMPOLINE_LAUNCH_SPEED`) on
top — see `resolveAxis`'s `isTrampolineGeom` branch. It exists specifically
so "extra bounce power" is a placed, sprite-bearing *thing* a kid finds,
not a hidden second tuning of the plain `bouncy` modifier (that used to be
`spring` — see the Non-negotiable principles section above for why it was
removed instead of kept as a second modifier).

### Actor shape

A live actor (in the `actors` array) looks like:

```js
{
  id, defId, x, y, w, h,           // AABB in px; w/h = ACTOR_SIZE = TILE - 2*ACTOR_INSET
  spawnX, spawnY,                   // where "reset to start" / Play-restart snaps it back to
  vx, vy, grounded, isPlayer, facingDir,
  impactMag, impactWobbleT, impactAxis, jumpCrouch, flashTimer,
  hazardCooldown, goalCooldown, flipCooldown, bouncyCooldown, doorCooldown,
  cannonCooldown, warpCooldown,
  // optional, spawner-created actors only:
  spawnerKey, spawnBornAt, ttlPopped,
  // optional, surface-dependent:
  onWhooshSurface,
  // v2.21, grab/carry/drop/throw (see its own section below):
  carried,             // true while glued to the player, no physics of its own
  carrying,            // player only: the id of whatever it's currently carrying, or null
  fuseArmed,           // carrybomb only: has this specific instance's fuse EVER been lit
  fuseRemainingMs,     // carrybomb only: ms left on the fuse — ticks down only while not held
  fuseTimerId,         // carrybomb only: the live setTimeout handle, or null while held/paused
  fuseStartedAt,       // carrybomb only: performance.now() when the current tick segment began
  cannonDir,           // carrycannon only: "ne"/"se"/"sw"/"nw", copied from the tile at grab time
}
```

`actorDefs[defId]` holds the static definition (`temperament`, `art`/
`poses`, `name`, `voice`, ...) — the live actor is the physics instance,
the def is the "what kind of thing is this."

### Rooms and the "hot globals" pattern

A room object holds: `board, backgroundBoard, colorBoard, groundSkinBoard,
groundSkinRotationBoard, actors, startPos, gravityEnabled, wrapHEnabled,
wrapVEnabled, cameraMode, editorPanCol`.

**Only one room is ever "hot"** — its fields are copied onto matching
top-level `let` globals (`board`, `actors`, `gravityEnabled`, etc.) by
`activateRoom(roomId)`, which also writes the *outgoing* room's globals
back onto its own object first. Every physics/render/paint function reads
these top-level globals directly, never `rooms[i].board` — that's exactly
what makes room-switching (doors, warps) cheap. `gravityEnabled` etc.
**default to `false`/`"fixed"` for a brand-new room** (`createEmptyRoom`) —
don't assume gravity is on just because other rooms/samples have it on.

**The four places new persistent state must be wired in**, every time,
together, or it will silently desync (this bit real time during v2.19's
spawner work):

1. **`activateRoom`** — copy the field both directions (outgoing room ←
   global, global ← incoming room) if it's a *per-room* hot global.
2. **`snapshotCurrentRoomState`** — the "outgoing" half of #1, used
   whenever the room isn't switching but its live state still needs
   flushing back onto the room object before a snapshot is taken.
3. **`captureProjectSnapshot` / `restoreProjectSnapshot`** — the one
   canonical whole-project shape shared by undo/redo, autosave, JSON
   save/load, and New Project. `restoreProjectSnapshot` must also
   backward-compat-default the field for an older snapshot that predates
   it (see the `spawnerContents ? ... : {}` pattern).
4. **`enterPlayMode`'s `buildSnapshot`, `restartPlaySessionFromSnapshot`,
   `exitToBuildMode`** — the separate Play-session snapshot/restore path
   (deliberately distinct from #3 — Play mutates live state directly and
   restores from a frozen pre-Play copy rather than diffing).
5. **`exportStandaloneGame`**'s `gameData` object, if the field needs to
   survive into an exported game at all.

A *project-global* (not per-room) piece of state only needs #3 and #5.

### Physics engine

`stepActor(actor, dt, player)` is the single per-actor physics step, called
once per actor per frame from `tick(dt)`. Shape, roughly:

1. Compute continuous forces as **acceleration**, not direct velocity:
   `windAccelFor`, `radialForceAccelFor` (magnet/gravity well),
   `fanAccelFor`. These fold into `ax`/`ay` alongside player input /
   NPC steering (`steeringAccelFor`) — **never add a raw velocity**, or
   `applyAxisFriction` will just eat it back to zero the instant no key is
   held (the "conveyor doesn't carry a standing player" bug shape). v2.20:
   both the player-input and steering contributions (not wind/fan/radial)
   are additionally scaled by `stickyMoveMult` (`STICKY_MOVE_MULT` while
   `isOnStickyGround(actor)`, else 1) — sticky ground damps a kid's OWN
   push, not a conveyor or fan blowing through it.
2. `applyAxisFriction(actor, axis, dt, accelInput)` integrates that axis:
   adds `accelInput*dt` if nonzero, otherwise decays toward 0 by
   `FRICTION_DECEL * frictionMultiplierFor(actor) * dt`. `frictionMultiplierFor`
   also returns `STICKY_FRICTION_MULT` (high — can't coast to a stop) while
   `isOnStickyGround`, alongside its existing `SLIPPERY_FRICTION_MULT` (low)
   case. The velocity cap itself (`cap`/`effectiveCap` in `stepActor`) is
   also scaled down by `stickyMoveMult` — damping acceleration alone barely
   reads as "slower" once `MOVE_ACCEL` reaches the ordinary cap within a
   fraction of a second; capping the ceiling is what makes it read as mud
   the whole time you're in it.
3. If `gravityOn()` (per-room `gravityEnabled`): normal platformer branch —
   jump, gravity accumulates into `vy` directly (not through `ay`/friction),
   clamped to `MAX_FALL`. If **`isStuckToSticky(actor)`** is true (touching
   a `sticky` solid tile via its LEFT, RIGHT, or TOP side — **not the
   bottom**, see the gotcha below) AND the actor hasn't used up its
   `STICKY_CLING_MS` window yet, it's fully frozen — `vx`/`vy` both hard to
   0, no movement input of any kind contributes (see the input section
   above `stepActor`'s gravity branch). **v2.20.3: sticky is a timed CLING,
   not indefinite climbing.** The original v2.19/v2.20 shape let free-roam
   input move the actor in any direction for as long as contact held, which
   in practice meant holding a direction key let a kid scale a sticky wall
   forever — direct feedback called this out explicitly ("you certainly
   shouldn't be able to climb walls that are sticky"). `actor.stickyClingT`
   counts up only while `isStuckToSticky` is true and resets to 0 the
   instant contact actually breaks, so a fresh touch (a different wall, or
   the same one after fully releasing) gets its own full cling. Once
   `stickyClingT` exceeds `STICKY_CLING_MS` — whether or not contact is
   still being made — the existing `stickyReleaseT` ramp (0 →
   `STICKY_RELEASE_MS`) takes over automatically, scaling gravity back in
   gradually ("slowly letting go") instead of slamming to full weight the
   very next frame; an actor that's never touched sticky keeps
   `stickyReleaseT` at its init value of `STICKY_RELEASE_MS` (= "already
   fully released"), so this is a no-op for everything else.
4. If gravity is off: free-roam 2D movement, single combined speed cap
   (also sticky-scaled, same as #2).
5. `resolveAxis(actor, axis, dt)` resolves AABB-vs-tile collision per axis
   separately (not swept), handling solid blocking, `bouncy` reflection
   (restitution scales with impact velocity — **a rebound can never exceed
   the fall height it came from**, restitution² × drop height is the rough
   rebound-height formula), the Trampoline geometry object's own stronger,
   minimum-enforced bounce (`isTrampolineGeom`, `TRAMPOLINE_RESTITUTION`/
   `TRAMPOLINE_LAUNCH_SPEED`), hazard/lethal damage, diggable erosion, and
   hazard-ball's always-bounce. **`return`s immediately once it resolves one
   blocking cell** (v2.20.1 fix) — see the dedicated gotcha below on why
   looping over every cell the AABB overlaps used to let a bounce tunnel a
   player straight through a multi-tile-wide bouncy floor/wall.
6. `resolveActorContact(moverActor, otherActor)` handles actor-vs-actor
   contact (player vs. NPC): temperament branches (`stationary`/
   `wanderer`/`chaser`/`fleer`/`collectible`/`PUSHABLE_KIND`/
   `HAZARD_BALL_KIND`) each get their own fixed reaction. This is the
   reaction table the "no scripting" principle refers to — it's a closed
   `if/else if` chain, not data-driven, and that's intentional.

Key constants worth knowing before tuning anything: `GRAVITY = 1450`,
`MAX_FALL = 750`, `MOVE_ACCEL = 2200`, `WIND_FORCE = 1000` (a plain wind/
conveyor tile's fixed force, deliberately *less* than gravity — it can slow
a fall, never reverse it, "a kid can still fight against it"),
`BOUNCE_RESTITUTION = 0.82`, `TRAMPOLINE_RESTITUTION = 0.97`/
`TRAMPOLINE_LAUNCH_SPEED = 900` (the Trampoline object, stronger than plain
`bouncy` on purpose), `STICKY_MOVE_MULT = 0.32`/`STICKY_FRICTION_MULT = 5`/
`STICKY_RELEASE_MS = 500` (sticky ground's own slow-down/no-coast/gradual-
release numbers), `STICKY_CLING_MS = 1000` (how long a sticky WALL freezes
an actor before the release ramp kicks in on its own — see below).

### Pushables (v2.20.3)

`shovePushables(actor, axis)` is the actor-vs-actor collision path for
`PUSHABLE_KIND` — a continuous shove every frame contact holds (see its own
comment for why that's a separate mechanism from the discrete bump-and-
cooldown reaction `resolveActorContact` gives every other actor pair). It
attempts to displace the pushable by however far the mover just moved; if
that displacement would be blocked, the MOVER stops at the pushable's edge
instead (or, for a vertical mover with `vy > 0`, comes to rest exactly on
top of it). Two bugs fixed here, both direct feedback:

1. **Landing on a pushable never set `actor.grounded`** — only
   `resolveAxis`'s own tile-landing branch did that, so jump input was
   silently ignored for as long as a kid stood on a pushable. The `vy > 0`
   branch now sets `actor.grounded = true` explicitly when the mover comes
   to rest on top, the same as landing on a tile would.
2. **Two pushables could overlap or pass straight through each other** —
   `shovePushables` used to bail out entirely whenever the MOVER was itself
   a pushable ("no chaining pushable-into-pushable, for now"). It now runs
   for every actor regardless of kind, and its `blocked()` check consults a
   new sibling helper, `actorBlockedByOtherPushables(candidate, selfId,
   moverId)` (the actor-vs-actor analog of `actorBlockedByTiles`), in
   addition to tiles. This is what makes stacking work: a falling pushable
   landing on a resting one hits the same "displacement blocked, come to
   rest on top" path a mover already used for a single pushable resting on
   a tile — no chain-push physics needed, since `PUSHABLE_KIND`'s "zero
   self-driven accel" means a pushable essentially never carries its own
   horizontal velocity beyond an occasional bounce, so true multi-block
   chain-pushing (A pushes B pushes C sideways) isn't really exercised by
   this — it's a low-risk generalization, not a full physics simulation.

### Grab / carry / drop / throw (v2.21)

The first player-invoked verb in the whole project — every other reaction so
far happens automatically from contact or movement, never from a kid
pressing a dedicated key. Still not scripting: it's one more fixed reaction
(closed to a specific set of object kinds, no authoring), just triggered by
a keypress instead of a collision. "E" is the key (unchanged from the
validated prototype, `grab-carry-test.html`).

**State machine**, driven by a pair of `keydown`/`keyup` listeners (not
per-frame polling like movement — press/release edges matter here):
not carrying + `keydown` → `tryGrabNearestCarryable` attaches the nearest
carryable actor or tile within `GRAB_KEY_RANGE`; carrying + `keydown` →
starts a charge (`grabKeyDownAt = performance.now()`); carrying + `keyup` →
`heldMs < THROW_TAP_MS` drops at the feet with zero velocity, otherwise
`throwCarriedObject` fires with speed scaled by how long it was held
(capped at `THROW_CHARGE_MAX_MS`) in `player.facingDir`'s direction plus a
fixed `THROW_UPWARD_SPEED` arc. A carried actor is fully exempted from
physics — `stepActor` early-returns for any `actor.carried` — and instead
gets its `x`/`y` set directly, every frame, by `tick()`'s own carry-follow
step (glued just above the player's head). `renderActors` adds a
charge-shake (scaling with how long the key's been held) as the physical
cue that holding the key is doing something — the same principle as the
spawner's own wind-up pulse; without it the charge-to-throw relationship is
undiscoverable, not just less polished.

**What's carryable**: `PUSHABLE_KIND` (already an ordinary actor, the "does
carry-and-drop alone feel good" baseline) plus four kinds that normally
live as painted tiles — bomb, magnet, cannon, trampoline. Grabbing one of
these picks the *one cell* bodily up off the board (`board[gy][gx] = null`)
and turns it into a real actor of a matching `CARRY_*_KIND`/`CARRY_*_DEF_ID`
(`convertGrabbedTileToActor`/`placeCarryableActor`) — same shape as
`HAZARD_BALL_KIND`, never placed by hand, only ever created this way. Once
turned into an actor it stays one forever, even after being dropped or
thrown — never repainted back onto the board. **Deliberate design choice,
not a migration**: the tile itself is completely unchanged (every existing/
sample-game board full of painted bombs, magnets, cannons, trampolines
keeps working exactly as before) and there's no second, differently-named
palette entry for "the carryable version" — the same swatch a kid already
knows just becomes grabbable once placed. This was an explicit user call
("let's keep the interface simple, players will investigate and discover
on their own") over either a bigger tile-to-actor migration or a parallel
object category.

**Each kind reuses its tile's own mechanism, never a reimplementation**:
- **Bomb**: **held is safe; the tile's own touch-arm hazard is untouched.**
  Bumping into a live bomb TILE still lights it on mere physical contact,
  same landmine feel as always (`triggerBombArm`, fired from `resolveAxis`
  — see "Physical objects vs. fixtures" below), with the same flicker
  warning it's always had (`drawGameplayTile`'s `extra.armed` alpha-blink,
  driven by `bombArmed[key]`). Grabbing it is the one thing that changed
  twice now: `pauseBombFuseIfTicking(obj)` / `startOrResumeBombFuse(obj)`
  are the whole carry-side mechanic — `obj.fuseRemainingMs` (defaults to
  `BOMB_FUSE_MS`) tracks how much fuse is left, `obj.fuseTimerId` is the
  live `setTimeout` handle while actually ticking (`null` while held/
  paused), `obj.fuseStartedAt` is when the current running segment began so
  a pause can compute exact elapsed time to subtract. `attachCarryable`
  calls `pauseBombFuseIfTicking` for a bomb; `dropCarriedObject`/
  `throwCarriedObject` both call `startOrResumeBombFuse` once it's no
  longer held. **Replaced an earlier v2.21 shape** where grabbing armed a
  fresh real-time fuse immediately and it kept ticking whether held or not
  ("explodes in your hands" regardless) — direct feedback was that this
  didn't read as carryable, just as a slightly-delayed explosion.
  **A second round of feedback then caught a gap in that first fix**: the
  first pass reset ANY grab to a fresh full `BOMB_FUSE_MS`, discarding
  however far a tile-side touch-arm had already ticked down — so grabbing
  an already-lit bomb felt like it un-lit the fuse rather than pausing it.
  `bombArmed[key]` is now `{ armedAt, timerId }`, not just a flag:
  `convertGrabbedTileToActor`, on grabbing a bomb, checks it, computes the
  exact remaining time (`BOMB_FUSE_MS - (now - armedAt)`), calls
  `cancelBombArm(key)` (a new helper — `clearTimeout` the tile-side timer
  *then* delete the entry, so it can't also fire later against whatever's
  since been painted over that cell; the four single-cell repaint/erase
  sites that used to do a bare `delete bombArmed[key]` now call this too,
  for the same reason) to cancel the original tile timer, and seeds the new
  actor's `fuseRemainingMs`/`fuseArmed` from that instead of a fresh
  `BOMB_FUSE_MS` — so "grabbed mid-countdown" genuinely means *paused*
  mid-countdown, picking up exactly where the tile left off once dropped or
  thrown again. A bomb grabbed before ever being touched still starts at a
  full, unarmed `BOMB_FUSE_MS`, same as before. `detonateCarriedBombAt(roomId,
  actorId)` finds the actor by id in whichever room it's still in (it's
  simply abandoned there, detonating unseen, if the player's since left
  that room), auto-drops it from `player.carrying` first if it's still held
  (only possible if its `setTimeout` fired in the same tick a grab was
  about to pause it — JS's single-threaded execution makes this a
  theoretical, not practical, case; kept as a defensive no-op rather than
  removed), and calls the *same* `detonateBombAt` the tile uses for the
  tile-clearing/knockback/boom-sound side of the blast — no second
  explosion implementation for that part.

  **The explosion VISUAL was a separate, real gap**, reported as "the
  explosion animation is gone": `detonateBombAt`'s own blast effect
  (`tileAnimState[...] = { recipe: "bombBlast", ... }`) is grid-cell-based
  and only ever applies where `targetBoard[y][x]` actually has a painted
  tile — which a carried bomb, sitting freely over ordinary open ground by
  the time it goes off, usually isn't. The sound and tile-clearing side
  (for solid neighbors actually in the blast radius) still fired correctly;
  only the bomb's own on-screen poof was silently skipped. Fixed the same
  way a "popped" actor already is elsewhere (`popVanish`/
  `RECIPES.popVanish.duration` — see this doc's own testing gotchas):
  `detonateCarriedBombAt` now calls `playRecipe(bombActor, "bombBlast")`
  (position-based, via `animState`, not grid-cell-based, so it works
  wherever the bomb happens to be) and delays the actual
  `removeActorById(actorId)` by `RECIPES.bombBlast.duration` instead of
  splicing the actor out immediately — the bomb visibly plays its own
  shrink-and-fade blast animation for that ~350ms window before vanishing.
  (An off-screen room's bomb still gets removed immediately — nobody's
  watching it pop.) **A carried/dropped bomb also now gets its own ticking
  warning**, the actor-render equivalent of the tile's flicker:
  `renderActors` multiplies in the same alpha-flicker formula
  (`Math.floor(now/120)%2===0 ? 1 : 0.35`) whenever
  `def.temperament === CARRY_BOMB_KIND && actor.fuseTimerId != null` — which,
  since `fuseTimerId` is the same field the pause/resume mechanic already
  tracks, means the flicker and the countdown are always in lockstep with
  no extra state needed: paused (held) is dark and steady, ticking
  (dropped/thrown) blinks, automatically.

  **A third, unrelated latent bug found while chasing this one**:
  `removeActorById` — called by `resolveActorContact`'s own collectible-
  pickup and fleer-pop reactions, both already-shipped, ordinary Play
  mechanics — was never added to `exportStandaloneGame`'s
  `runtimeFunctions` array. Collecting an item (or popping a fleer) in an
  *exported* game threw a `ReferenceError` the instant it happened, same
  species of bug as the `nextActorInstId` and `actorDefs` gaps above and
  below — found here because the new bomb-blast fix's own
  `removeActorById` call was the first time an export test actually forced
  the question. Fixed by adding it to the list; every existing pickup path
  gets it for free.
- **Magnet**: `radialForceAccelFor(actor, player)` (now takes `player`) has
  a second pull source alongside its tile-scanning loop — a currently
  *actively held* `CARRY_MAGNET_KIND` actor's own live position, same
  `MAGNET_FORCE`/falloff math, same `magnetable` restriction (pushable/
  collectible only, never the player). Resting/dropped, it pulls nothing —
  "only while actively held" is the whole point, straight from the patch
  note's "mobile force field" framing.
- **Cannon**: keeps its orientation (`cannonDir`, copied from the tile
  geometry string at grab time — `"cannon-ne"` → `"ne"`) as real pose
  frames (`currentPoseFor` special-cases `CARRY_CANNON_DEF_ID` to pick by
  direction instead of physics state, the only actor def that does).
  Dropped/resting, `resolveActorContact`'s `CARRY_CANNON_KIND` branch calls
  the *same* `triggerCannon` the tile uses, player-only (matching the
  tile — only `checkPlayerTileContacts`/the Build-mode drag handler ever
  call it). Not blocking, exactly like the tile.
- **Trampoline**: the one kind that needed genuinely new physics —
  `bounceOffTrampolineObjects(actor, axis)`, the actor-vs-actor sibling of
  `resolveAxis`'s own `isTrampolineGeom` branch, called right after
  `shovePushables` on both axes. Unlike a pushable, it's never shoved out
  of the way; landing on its TOP specifically reuses the exact same
  `TRAMPOLINE_RESTITUTION`/`TRAMPOLINE_LAUNCH_SPEED` formula and sound as
  the tile. **Deliberate simplification**: bumping its side or underside
  just blocks (rests), it doesn't bounce on those sides the way the tile's
  4-directional `resolveAxis` bounce does — the primary "jump on a
  trampoline" case is what this covers; flag it to the user before trying
  to make every side bouncy too, since that needs a real actor-vs-actor
  collision model, not this one.

**`sounds` and the export-time closure-capture gotcha (see Sound section)
already covered this, but it bit here too while wiring cannon/bomb/magnet
sounds** — nothing new needed, just confirms the rule holds for any future
reaction. **A thrown object needs its own `recentlyLaunched` exemption**:
`throwCarriedObject` sets `obj.bouncyCooldown` (reusing the same field a
bouncy/Trampoline launch already exempts itself with) specifically because
`stepActor`'s non-player speed cap (`NPC_MAX_SPEED = 160`, far below any
real throw speed) would otherwise flatten the throw back down to a slow
drift within a single frame. Safe to reuse `bouncyCooldown` here — the
v2.20.1 tunneling risk that field's own comment warns about only exists
when something holds a directional key during the exemption window, and a
thrown pushable/bomb/magnet/cannon/trampoline never has steering input of
its own.

**A latent, pre-existing export bug found and fixed while building this**:
`spawnActorAt` (already shared into `exportStandaloneGame`'s runtime) does
`nextActorInstId++`, but nothing in the export template ever declared that
variable — a spawner firing in an *exported* game threw a `ReferenceError`
on its very first actor, undetected until this patch's own
`placeCarryableActor` hit the same missing declaration and a Playwright
export test actually exercised a spawner rather than just checking the
page loaded. Fixed by hand-declaring `let nextActorInstId = 1 + <max id
already in GAME_DATA>;` in the export template, the same "declared here by
hand" pattern `audioCtx`/`noiseBufferCache`/`chipBufferCache` already use
for transient runtime-only state.

**A second latent bug, this one live-editor-only and much nastier: `restoreProjectSnapshot`
never backward-compat-defaulted `actorDefs`' own new built-in entries.**
`CARRY_BOMB_DEF_ID`/`CARRY_MAGNET_DEF_ID`/`CARRY_CANNON_DEF_ID`/
`CARRY_TRAMPOLINE_DEF_ID` are seeded into `actorDefs` unconditionally at
boot — but `restoreProjectSnapshot` (called by `loadAutosave()` right after
that seeding, on every single page load) does a blind
`actorDefs = structuredClone(snap.actorDefs);` with no fallback, exactly
the mistake the Rooms section above calls out in general and the pattern
right below it (`collectibleSlotIds`/`groundTileDefs`, both "older saves
predate X, re-derive from `FACTORY_DEFAULT_SNAPSHOT`") was specifically
meant to prevent. Any autosave/save made before this feature existed
— which is to say almost anyone's real saved project, autosave included,
from before this patch — silently wipes those four keys back out of
`actorDefs` on every subsequent load, forever, until a fresh "New Project."
The result: `convertGrabbedTileToActor`'s own `actorDefs[defId].name` (no
null-guard, since the def was assumed to always exist) throws the instant
a kid grabs a bomb/magnet/cannon/trampoline tile, tripping the app's global
error boundary ("😵 Oops! Something glitched.") — reported as "pressing E
on [these] objects gives an error and deletes them," which read at first
like a grab-logic bug but reproduced on literally every carryable *tile*
(pushable, being much older, was unaffected) and turned out to have
nothing to do with grab's own code at all. **Why this evaded testing all
patch long**: every Playwright test in this session used a fresh browser
context with empty `localStorage`, so `loadAutosave()` always returned
false and `actorDefs` was never clobbered — the bug only surfaces on a
*real* browser carrying forward an *old* save, which no throwaway test
naturally recreates without deliberately seeding a stale autosave payload
first. Fixed the same way collectibles/ground tiles already were: right
after `actorDefs = structuredClone(snap.actorDefs)`, backfill
`[PUSHABLE_DEF_ID, HAZARD_BALL_DEF_ID, CARRY_BOMB_DEF_ID, CARRY_MAGNET_DEF_ID,
CARRY_CANNON_DEF_ID, CARRY_TRAMPOLINE_DEF_ID].forEach(id => { if
(!actorDefs[id]) actorDefs[id] = structuredClone(FACTORY_DEFAULT_SNAPSHOT.actorDefs[id]); })`.
**Any future built-in actor def needs the same one-line addition to that
list** — this is now the established, single place that guards against it,
same as `collectibleSlotIds`'s own fallback just above it in the function.

**Still open, carried over from the prototype, not solved by this patch**:
whether carrying something should affect player movement (slower, lower
jump), and whether a held object should collide with geometry while
carried (bonking against walls) instead of staying fully attached. Flag
either to the user before changing — no evidence yet either way.

### Physical objects vs. fixtures (v2.21)

Direct feedback right after grab/carry shipped: every carryable *except*
the pushable felt "glitchy" to grab, because bomb/magnet/cannon/trampoline/
fan/spawner were all pure contact-trigger pads (`isBlockingGeometry`
returned `false`) — a kid could walk straight through the very thing they
were trying to grab, so the grab gesture had nothing physical to register
against. Trampoline was already blocking (see above); this patch made
**bomb, magnet, cannon, fan, and spawner** blocking too, the same
`isBlockingGeometry` list solid/diggable/Trampoline already use. This
surfaced a second, more interesting question from the same feedback: some
placed objects (door, switch, plate, warp, goal, gravitywell) are the
opposite on purpose — their *entire function* is being walked onto, and
making them solid would break them outright. The user asked for these to
be named as their own category rather than left as an implicit exception
list. **`FIXTURE_GEOMETRIES`** (`goal, switch, plate, door, warp,
gravitywell`) is that category — "fixture" as in a kid-friendly word for
"a thing that's part of the room and doesn't move," parallel to how
`PUSHABLE_KIND`/`HAZARD_BALL_KIND`/`CARRYABLE_KINDS` name the actor side.
Unlike most of these internal-only categorization constants, this one is
also **kid-visible**: the Objects tab now shows two separate palette rows
— "Pick an object" (`PALETTE_OBJECT_GEOMETRIES`, now trimmed to just
cannon/bomb/fan/magnet/spawner/trampoline plus the pushable actor swatch —
real, bumpable things) and a new "Fixtures" row directly below it
(`renderFixtureSwatches`, reading `FIXTURE_GEOMETRIES` itself so the two
lists can't drift apart), each with its own hint text explaining the
distinction in the same "walk onto it" vs. "bump into it" language as this
section's own opening paragraph. `goal`/`switch`/`plate`/`door`/`warp`/
`gravitywell` used to live inside the single old `PALETTE_OBJECT_GEOMETRIES`
row undifferentiated from bomb/cannon/etc.; splitting the row was the fix
for a real gap — the category existed in code (this section, first shipped)
but wasn't visible in the app itself, which is what a kid or a parent
skimming the palette actually sees. `renderFixtureSwatches` reuses the
exact same swatch-drawing/`selectGeometry` click path as
`renderObjectSwatches`'s own geometry loop (same icons, same selection
highlighting) — it's a second row, not a second mechanism. No other code
branches on `FIXTURE_GEOMETRIES` beyond this rendering split and
`PALETTE_OBJECT_GEOMETRIES`'s own doc comment — "stay a walk-through
contact pad, never solid, never carryable" is still simply what every
fixture geometry already does by not appearing in `isBlockingGeometry` or
`CARRYABLE_KINDS`.

**Fan and spawner are blocking-only, deliberately not carryable.** Every
other carryable in this patch (bomb/magnet/cannon/trampoline) is a single
self-contained tile whose whole mechanic already lived in one cell, so
"pick the cell up and turn it into an actor" was a clean lift (see Grab /
carry / drop / throw above). Fan and spawner aren't: `fanAccelFor` scans
outward from a fixed `geometryAt` cell along a facing direction, and the
spawner's contents/cooldown/TTL/concurrency-cap system is keyed to its own
board position — neither has a "current cell" that could float around
glued to a player without a much bigger rework of how they store state.
Making them blocking (so nothing floats through empty air where a fan or
spawner obviously physically *should* be) was the fix this feedback
actually asked for; making them carryable is real, separately-scoped
future work, not attempted here.

**Consequence of blocking the tiles: touch-based triggers had to move from
"overlap" to "collision."** Bomb-arm and cannon-fire used to fire from
`checkPlayerTileContacts`, a function whose own comment assumed the player
never overlaps blocking geometry (true before this patch, since bomb/
cannon weren't blocking) — it read `modifierAt`/`geometryAt` under the
player's AABB every frame regardless of whether that cell was walkable.
Now that bomb/cannon tiles physically stop the player at their edge, that
overlap never happens, so the trigger moved into `resolveAxis` itself,
fired at the exact moment a per-axis collision against that geometry is
resolved (right beside the existing lethal/hazard/Trampoline branches, and
still before the v2.20.1 tunneling-fix `return`) — `checkPlayerTileContacts`
and the build-mode drag handler (`clampDragPosition`, via a small shared
`fireBlockingTileReaction` helper for its two blocking-clamp loops) both
had their now-dead overlap-based bomb/cannon branches removed in favor of
this single collision-time call site. Magnet and spawner need no such
migration — their mechanics were never touch-triggered to begin with
(magnet pulls at range, spawner fires on its own timer), so making them
blocking is a pure physics change with nothing else to wire up.

**An emergent interaction worth knowing about, not a bug**: a fan facing
straight up is now solid, so a player standing on/over it can never
actually occupy the fan's own cell (the strongest point on its force
curve, `i = 0`) — the closest it can rest is the cell directly above,
`i = 1`. `FAN_NEAR_FORCE` (1900) still exceeds `GRAVITY` (1450) at that
distance, so the player hovers there indefinitely rather than ever
settling to `grounded = true`. This was verified as a real, stable,
error-free outcome (not a stuck/undefined state) rather than patched away
— the user's instruction was specifically to make fans solid, and "hovers
in the updraft instead of standing in it" is a reasonable reading of that
for a fan, not a glitch. Flag it to the user before changing `isBlockingGeometry`
or the fan force curve if this ever needs to read differently.

### Camera & rooms (v2.17)

A room's board arrays are always allocated at `BOARD_MAX_COLS` (3× the
viewport), but `cameraMode` (`"fixed" | "follow" | "runner"`) controls how
much of it is reachable/rendered — `roomCols()` returns the *usable* width
for the current mode. Runner mode ties into the lethal-hazard reaction for

game-over path.

### Duplicate Room (v2.21)

One button, `renderRoomTabs`'s own last child so it's always the rightmost
thing in the room-tab row regardless of how many rooms exist — acts on
whichever room is currently open (the hot one), the same target every
other room-scoped control in that row already implies, rather than needing
a per-tab button of its own like delete (`×`) has. `duplicateRoom()`
flushes the hot globals first (`snapshotCurrentRoomState()`, so the copy
reflects whatever was just painted, not stale data), then `structuredClone`s
`board`/`backgroundBoard`/`colorBoard`/`groundSkinBoard`/
`groundSkinRotationBoard`/`startPos`/actors and Game Rules/Camera
(`gravityEnabled`/`wrapHEnabled`/`wrapVEnabled`/`cameraMode`/`editorPanCol`)
onto a fresh room object (`nextRoomId++`, name `<original> + " copy"`,
chains fine — duplicating a duplicate named "room 1 copy" yields "room 1
copy copy"), pushes it, and switches to it immediately — same
`rooms.push`/`activateRoom` shape every other room-creation path (an
auto-generated door-linked room, the built-in sample games) already uses,
so nothing new needed wiring into undo/redo/autosave/JSON save-load (those
already snapshot the whole `rooms` array plus its id counters wholesale).

**One deliberate exception to "copied exactly," worth flagging**: the
player is never duplicated. `removeAllPlayerInstances`'s own comment
already establishes the project's one hard rule here — there is only ever
ONE player actor across the *entire project*, not one per room — so
copying it would leave two actors simultaneously marked `isPlayer` (one in
each room) while `playerRoomId` could still only point at one of them, an
inconsistency nothing else in the codebase (camera follow, Play-mode
start, the room tab's own "•" marker) is built to tolerate. `duplicateRoom`
filters the player out of the cloned `actors` array before cloning; every
other actor — pushables, wanderers/chasers/fleers, collectibles, spawners
and their loaded contents, a grabbed-and-dropped carryable — comes along
untouched, reassigned a fresh id (`nextActorInstId++`) so it can never
collide with the original room's copy once both exist side by side.
`startPos` is copied as-is even though it's really "the player's own reset
position for this room" (see the Actor-shape section above) — harmless
dead weight on a room with no player in it, and gets overwritten correctly
the moment a kid places a fresh player there anyway (`placeNewActor`'s own
`if (isPlayer) { startPos.x = ...; playerRoomId = currentRoomId; }`).

Build-mode-only, like `deleteRoom`/`createEmptyRoom` already are — nothing
here belongs in `exportStandaloneGame`'s `runtimeFunctions` (an exported
game never creates rooms, it only ever plays the ones baked into
`GAME_DATA`), and the whole `#roomTabRow` this button lives in is already
hidden outright in Play mode (`body.play-mode #roomTabRow { display:
none; }`).

### Fan and Spawner (v2.19, force curve and always-live fixed in v2.20/v2.20.2)

A fan (`fanAccelFor`) projects wind's own force calculation outward from a
placed Object along its facing direction, scanning up to `FAN_RANGE_TILES`
cells and stopping at a wall or the fan itself. v2.20 gave it a distance
falloff instead of one flat force across the whole range: `FAN_NEAR_FORCE`
(1900, right at the fan — deliberately *more* than `GRAVITY`, so standing
directly in the stream actually lifts you) linearly interpolating down to
`WIND_FORCE` (1000, weaker than gravity, same as plain wind) by the far
edge. **v2.20.2 fix:** the scan used to start at `i = 1` (the cell BETWEEN
the actor and the fan), never `i = 0` (the actor actually overlapping the
fan's own cell) — so the exact moment a kid fell into or stood right on a
fan, the strongest and most expected point, got ZERO force, a cliff-edge
drop-off at closest approach. Now `i = 0` is the fan's own cell (peak
`FAN_NEAR_FORCE`) and `i = FAN_RANGE_TILES` is the far edge (plain
`WIND_FORCE`). This is what lets fan-to-fan hopping climb higher each jump
instead of topping out — the near-force genuinely overpowers gravity, the
far-force never does. `fanAccelFor` also returns a `near` flag (true within
~1 tile) purely for the floating-bob render cue (`actor.nearFan`, read in
`renderActors`) — a cosmetic sine wobble, never physics.

**v2.20.2: continuous accel alone can't visibly arrest a fast fall.** Even
though `FAN_NEAR_FORCE` genuinely "beats gravity" on paper, a terminal-
velocity drop only spends 2-3 frames inside the ~1-tile-deep near zone
before it's past the fan — ~450px/s² of net excess accel over ~0.03s barely
dents 750px/s of existing fall speed. Continuous accel made "fall into a
fan, feel bounced" imperceptible in practice, a real user-reported gap.
Fixed with a discrete kick layered on top (`FAN_BOUNCE_MIN_SPEED`,
`FAN_BOUNCE_RESTITUTION`, applied in `stepActor` right where `fanAccelFor`
is called): when `near` is true and the actor's velocity component along
the fan's push direction is opposing it beyond `FAN_BOUNCE_MIN_SPEED`, that
opposing speed is instantly converted into push-back at
`FAN_BOUNCE_RESTITUTION` — the same "instant, not just gradual" shape
`TRAMPOLINE_LAUNCH_SPEED` uses for the identical reason. A fast fall takes
2-3 successive partial kicks to fully arrest (each one isn't restitution
enough alone, same shape as a real settling bounce) — `actor.fanKickCooldown`
gates the accompanying `sounds.boing()` to once per episode rather than once
per frame. **Deliberately a separate cooldown field from `bouncyCooldown`**
— reusing that one would also flip `stepActor`'s `recentlyLaunched` speed-
cap skip on, and holding a direction key during that window is exactly the
mechanism that caused the v2.20.1 tunneling bug elsewhere; a fan kick must
never disable the movement speed cap.

The animated white "wavy line" VFX (`drawFanStream`) originally spanned
the whole `FAN_RANGE_TILES` reach in the blow direction, which read as
"several tiles of dashes" rather than a wind effect at the fan's mouth — a
second piece of direct feedback. **v2.20.2:** now confined to the single
tile immediately in front of the fan — 2-3 short wavy lines side by side
(spaced across the perpendicular axis), each a small sine ripple kept well
inside that one tile's bounds and animated by phase so they shimmer in
place, rather than a dashed line marching outward across the whole range.

The spawner (`tickSpawners`/`tickSpawnedTTL`) originally only ran in Play
mode, reasoned as "a gameplay mechanic a kid experiences by pressing Play."
v2.20 removed that gate — it directly contradicted "always live" (a
wanderer/chaser already roams the instant it's placed in Build mode; the
spawner sitting inert until Play was the actual bug, not a deliberate
carve-out). It now runs unconditionally from `tick()`, same as every other
actor behavior; only genuinely session-scoped things (`updateCamera`,
`checkRunnerFailState`) stay Play-gated. A spawner still needs nothing
loaded to work — it falls back to `HAZARD_BALL_DEF_ID` — and any actor kind
(the default hazard ball, `pushable`, or a full custom character/temperament)
can be loaded by selecting it and clicking an existing spawner tile
(`toggleSpawnerContent`); the player itself can't be loaded (spawning
players makes no sense). Each spawn plays a `materialize` chime
(`sounds.spawn()`) and reuses the `caughtBounceIn` pop-in keyframe recipe
— deliberately reused rather than inventing a near-identical second
"something appearing" animation.

### Sound (v2.21 — chip engine, replacing the v2.18 Wavesculpt port)

Fully synthesized, no samples. The v2.18 placeholder (oscillator "patches"
ported from Wavesculpt) was replaced wholesale by a tiny NES-2A03-style chip
synth: `renderChipDesign(design, opt)` renders a finished, hand-tuned
per-frame sound description (2 pulse channels, 1 triangle, 1 noise — see its
own header comment for the exact per-frame format) to a `Float32Array`.
`CHIP_DESIGNS` holds eleven finished designs (`thunk`, `boing`,
`trampolineBoing`, `pop`, `splat`, `kaboom`, `ding`, `creak`, `wind`,
`swoosh`, `zip`, `cat`) — **finished per-frame data, not a generator**: they
were tuned in a separate, unshipped throwaway tool (`sound-designer.html`,
built in an earlier session, against `chip.js`/`designs.js`, also not
shipped as-is) and pasted in as plain numbers. `getChipBuffer(name)` renders
a design to an `AudioBuffer` **once, on first use**, and caches it;
`playChip(name, pitchMult, velocity)` always plays from that cache — never
re-renders per trigger. `sounds` is a plain object literal mapping each
reaction directly to a `playChip(...)` call (see below for why it's written
as literals, not built from a lookup table).

**Not every reaction got a new chip design.** `jump`, `flip`, `fuse`,
`gameOver`, and three of the four creature voices (`dogBark`,
`chickenCluck`, `genericCreature` — only `cat` was redesigned) still run on
the original v2.18 one-shot oscillator engine, kept below the chip engine
in the same section (`playPatch`, `osc`, `getAudioCtx`, the trimmed
`SOUND_PATCHES` with just those 7 entries). This is a deliberate, narrow
exception — nothing was silenced just because it wasn't redesigned yet —
not a half-finished migration; flag it to the user before either deleting
this leftover engine or authoring new chip designs to replace it.
`playActorSound(actor, fallbackReactionName)` is what dispatches per voice:
`def.voice === "cat"` goes to `playChip("cat", ...)`, any other non-empty
`def.voice` goes to `playPatch(def.voice, ...)` (the legacy engine), empty
falls back to the generic reaction sound — see `VOICE_PATCHES` for the
picker's id/label list.

**The old ~20-entry `REACTION_PATCH` table is gone, consolidated onto the
new engine's 8 designed families.** Each family's own `use` field (in the
original `designs.js`) is what decided the consolidation, not guesswork:
`boing` also covers a plain actor-vs-actor bounce and (via its own
`trampolineBoing` entry — the family's "fat" tuned variant, not a duplicate
of plain `boing`) the Trampoline object's launch, keeping the "extra bounce
power should be heard, not just felt" distinction v2.20.1 gave it; `pop`
also covers a spawner's arrival (no separate `materialize` sound anymore);
`splat` also covers being caught by a chaser (same severity tier — a life
lost — as a lethal hazard, not the old separate `gotcha` patch); `thunk`
also covers every other physical bump/knock (NPC `boop`/`oof`, a hazard's
non-lethal knockback, a diggable tile eroding) that used to be its own
named patch. **`kaboom` deliberately covers both bomb detonation and cannon
launch** — this looks like it's reintroducing the exact v2.20.1 "cannon and
bomb sounded identical" bug, but it isn't: the delivered sound design's own
`use` field says `"bomb explosion, cannon shot"` together, a decision made
in the design data itself, not by whoever wires up the reaction table. Only
`wind`/`slide`/`warp` changed in the other direction — they're now three
genuinely distinct rendered sounds (`wind`/`swoosh`/`zip`, three tuned
variants of one design family) instead of one shared patch pitched three
ways, which is what `sounds.wind`'s old pitchMult hack was working around.

**Export-pipeline gotcha, found while building this:** `sounds` must be
written as literal, self-contained arrow functions
(`thud: () => playChip("thunk")`), never built by looping over a lookup
table and closing over the loop variable
(`sounds[name] = () => playChip(TABLE[name])`). `exportStandaloneGame`
ships each `sounds.X` function by literal source text (`fn.toString()`) —
a closure over an outer variable serializes as that variable's *name*, not
its resolved value, and throws a `ReferenceError` the instant it runs in
the exported game's own scope, where that outer variable doesn't exist.
This bit every reaction sound except the couple that were already
hand-written as literals (`thud`, the old `wind` override) in the v2.18
engine, undetected until this patch actually loaded an exported game and
called its sounds directly. Same rule for anything else added to `sounds`
later — one line per reaction, referencing only literals and globals that
are also in `runtimeFunctions`/`constantsSource`, never a captured local.

`RECIPES` (separate from sound) are visual deformation/animation keyframe
sequences (`popVanish`, `caughtPunt`, ...) — note `RECIPES.popVanish.duration`
(220ms) is a **real wall-clock `setTimeout`**, not a game-tick-driven delay,
so an actor that "pops" is still in the `actors` array for ~220ms after the
reaction fires before `removeActorById` actually runs.

**v2.20.1: a bounce needs to sound like a bounce.** `triggerImpact` (called
unconditionally from every `resolveAxis` collision, bounce or not) used to
always fire the generic landing `thud` regardless of whether the tile was
plain solid or bouncy — a bounce and an ordinary landing were
indistinguishable by ear, another user-reported bug. Fixed with a 4th
`triggerImpact(actor, axis, incomingSpeed, isBounce)` parameter that
suppresses the thud specifically (the visual impact wobble still tracks
every contact, bounce or not); `resolveAxis` now calls a small
`bounceSound` (`sounds.boing` for plain bouncy, `sounds.trampolineBoing`
for the Trampoline object) right at each of its 4 reflection sites,
player-only (a wandering hazard ball caroming off walls doesn't need a
boing every hit). The general "does an ordinary footstep/small-hop landing
really need its own thud" question is left as-is for now — `mag` (the 0-1
scale `sounds.thud` reads for pitch/volume) saturates to 1 after roughly a
single tile of fall, so there's currently no clean way to distinguish "a
kid hopped down one step" from "an actual big fall" without reworking that
scale; flag it explicitly to the user before changing `IMPACT_NOISE_FLOOR`
or the thud threshold, since a bigger change risks silencing normal jump
landing feedback the game already relies on elsewhere.

### Export pipeline

`exportStandaloneGame()` builds a second, self-contained HTML file:
`gameData` (a frozen snapshot of current project content), a
`runtimeFunctions` array (shared functions serialized via `fn.toString()`
— **any new function the runtime needs at play-time must be added to this
list explicitly**, source-sharing isn't automatic), a `constantsSource`
array (hand-written `const X = ${JSON.stringify(X)};` lines — **also not
automatic**, a new constant needs its own line here), and `soundsSource`.
The exported template declares its own copies of transient
runtime-only state (things like `spawnerRuntime = {}` that don't belong in
`gameData`) and re-derives everything else via the same shared
`activateRoom`/`restartStandaloneGame` functions the editor itself uses.

## Version labels are not reliable — read the code, not the comment

Comments and commit messages use an informal `v2.N` (and occasionally
`v2.N.M`) scheme, but **it is not monotonic and has been reused**. Concrete
example already in this repo's history: `9f5264a` ("Ground tab revamp: real
textures, animated lava/fire, custom tiles") is labeled **v2.19**, has its
own sub-patches commented `v2.19.2` through `v2.19.5` scattered through the
file (e.g. around `placeNewActor`, `activateRoom`, drag-repaint, actor
reset), and predates commits labeled v2.15/v2.16/v2.17 in git history — and
then a **completely unrelated** later patch (magnet/gravity-well/sticky-
wall/fan/spring/spawner) was *also* labeled **v2.19** (commit `775c94c`).
There are two unrelated features both calling themselves "v2.19" in this
codebase. Don't trust a version label to uniquely identify a feature or to
order commits — check the actual diff/git log/surrounding code instead. If
you're tempted to leave a `vX.Y` comment on new work, a plain description
of *why* ages far better than a number that may already be taken.

## Testing conventions

There is no test framework, no `npm test`, nothing checked into the repo.
Tests are throwaway Playwright scripts written fresh each session:

- **Debug hook pattern**: add a temporary `window.__toyDebug = { ... }`
  object exposing whatever internals the current patch needs to assert on
  (`getActors`, `getBoard`, `getSpawnerContents`, etc.), placed right after
  `updateUndoRedoButtons()` near the boot sequence. Write Playwright tests
  against it. **Strip it before the final commit** — `grep -n "toyDebug"
  index.html` must return nothing. This has been the pattern since at
  least v2.16 and should keep being the pattern.
- **Playwright environment specifics** (this sandbox): launch with
  `chromium.launch({ executablePath: '/opt/pw-browsers/chromium' })`,
  `require('/opt/node22/lib/node_modules/playwright')` directly rather than
  via a local `node_modules`. Always wire `page.on('dialog', d =>
  d.accept())` (the app uses native `confirm()` for New Project / sample
  loading / etc.) and `page.on('pageerror', ...)` to catch runtime errors.
  Load via `file://` on the real `index.html` path, not a copy.
- **Test files live in the session scratchpad directory**, not the repo —
  they're intentionally not committed. The literal path changes per
  session; use whatever scratchpad path this session's environment gives
  you.
- **`getActors()`/`getBoard()` etc. should return live references**, not
  copies, when you write a debug hook — this lets a test directly mutate
  actor velocity/position/`spawnBornAt`/etc. to fast-forward past
  real-time waits (e.g. seeding a spawner's `clock` field close to its
  firing threshold instead of waiting the full interval) while still
  exercising the real production code path on the next tick. Very useful
  for anything gated by a multi-second timer.

### Gotchas learned the hard way (read before writing new physics tests)

- **Gravity defaults OFF for every new/empty room.** A fresh "New Project"
  or a room you just created has `gravityEnabled = false`. Any test (or
  manual check) of a gravity-dependent mechanic (sticky wall suspension,
  a bouncy/Trampoline launch, a fan "fighting" a fall) needs to explicitly
  click the gravity swatch in `#gameRuleSwatches` first, every time, after
  every New Project.
- **Row/column indices are 0-based and bounded by `ROWS`/`COLS` (18/24 as
  of v2.20)** — `board[18]` is out of bounds when `ROWS = 18` (valid rows
  are 0–17). A test that paints a "floor" at row `ROWS` itself (an easy
  off-by-one when copying an old test) throws `Cannot read properties of
  undefined` the moment anything reads that row back, not a silent no-op.
- **Selecting the `bouncy` Surface swatch defaults `selectedGeometry` to
  `"solid"` if it was `"none"`** (`selectSurfaceModifier`, v2.20 fix) — a
  deliberate UX default, not a bug, so don't be surprised if a test that
  expects `"none"` after clicking bouncy sees `"solid"` instead. `sticky`/
  `slippery`/`hazard`/`lethal` are deliberately NOT defaulted this way —
  each has its own valid, distinct reading on `"none"` ground.
- **`paintMode` ("tile" vs "actor") is sticky across tab switches and is
  *not* set by a debug-hook shortcut that only assigns `selectedGeometry`.**
  If a previous action selected an actor (e.g. the player, for a "can this
  be loaded into X" check), a later debug-hook `setSelectedGeometry(...)`
  followed by a canvas click will still place an *actor* (whatever was last
  selected), not paint the tile, because nothing changed `paintMode`. Prefer
  clicking the real palette swatch (which sets both `selectedGeometry` and
  `paintMode` correctly via the actual click handler) over a debug-hook
  field-setter for anything that will immediately be followed by a canvas
  click.
- **`enterPlayMode()` silently no-ops if no player has been placed**
  (`if (playerRoomId == null) { log(...); return; }`). If a test's `appMode`
  stubbornly stays `"build"` after clicking Play, this is almost always why
  — check that a real player placement (not a click that got intercepted
  by something else, like a spawner tile's toggle-contents handler) has
  actually happened.
- **A click on an existing spawner tile while `paintMode === "actor"` never
  places an actor there** — it calls `toggleSpawnerContent` instead. This
  is correct product behavior (loading a spawner is the same click-to-place
  gesture, by design) but means "place the player at cell X" tests must
  use a cell that is *not* a spawner tile.
- **A restitution bounce can't exceed the height it fell from** — this
  still holds for plain `bouncy` (0.82). The Trampoline OBJECT is the one
  exception: it enforces a hard minimum launch speed
  (`TRAMPOLINE_LAUNCH_SPEED`) on top of reflection specifically so a gentle
  step-on still gets a real bounce — see `resolveAxis`'s `isTrampolineGeom`
  branch. Testing "does it launch the player" by checking it clears its
  *starting* height still isn't reliable for a short fall onto plain
  `bouncy`; use a tall, deliberate fall and compare rebound height
  *between* plain bouncy and Trampoline, not against the spawn point.
- **A bouncy floor/wall/ceiling more than one tile wide used to let the
  player tunnel straight through it** (v2.20.1 fix, and the actual root
  cause of a user-reported "warp out the bottom of a ring of bouncy tiles"
  bug — the earlier v2.20 geometry-defaulting fix in `selectSurfaceModifier`
  was real but insufficient on its own). Two independent bugs stacked:
  (1) `resolveAxis`'s cell loop didn't stop after resolving one collision —
  an actor's AABB routinely spans two columns (or rows) that are BOTH
  blocking whenever a bouncy surface is more than one tile wide (i.e. any
  real one), so the loop reflected `vy` twice in the same call: once
  correctly (positive → negative), then a second time reading its OWN
  already-flipped negative value as "hit from below," pushing the actor to
  `(cy+1)*TILE` — the tile's FAR side. Ordinary non-bouncy solid never
  showed this because its landing branch zeroes `vy` to exactly 0, and
  neither `vy > 0` nor `vy < 0` fires on a second pass over 0 — only
  bouncy's nonzero reflected velocity exposed it. Fixed by `return`ing
  immediately after resolving the first blocking cell per axis call — one
  AABB only ever needs one resolved collision per axis per frame. (2)
  Separately, `checkPlayerTileContacts` (written assuming, per its own
  comment, that "the player never overlaps blocking geometry" since
  `resolveAxis` pushes it flush to the boundary) fired
  `triggerBouncyLaunch` — meant only for the non-blocking `none:bouncy`
  walk-over pad — whenever it saw `modifier === "bouncy"` on ANY cell the
  AABB overlapped, blocking or not. On uneven/staircase terrain (a
  hand-painted circle of solid+bouncy tiles is exactly that) the player's
  AABB can genuinely graze a neighboring solid+bouncy cell it isn't
  resting on. That falsely set `bouncyCooldown`, which `stepActor`'s
  `recentlyLaunched` check uses to skip the `MOVE_ACCEL` speed cap
  entirely — holding a direction key during that ~350ms window let
  velocity run away completely unbounded (observed vx > 1000px/s), more
  than enough to fly past a ring's own curve. Fixed by gating all three
  modifier reactions in that function on `!isBlockingGeometry(geometry,
  player)`. **When testing any bounce-related mechanic, always test it
  under active player input (hold a direction, jump repeatedly) in
  addition to passive drop-and-watch** — the passive case alone won't
  surface either of these; both needed genuine held input to reproduce (a
  ring that "stays inside for the full duration" with zero input proves
  nothing about whether it holds up once a kid actually plays with it).
- **`WIND_FORCE (1000) < GRAVITY (1450)`** for plain wind/conveyor tiles,
  deliberately — a "none/solid + wind" tile facing straight up will slow a
  fall, never reverse it. A **fan is different since v2.20**: its force
  falls off with distance (`FAN_NEAR_FORCE = 1900` at `i = 0`, the fan's own
  cell, down to `WIND_FORCE` at `i = FAN_RANGE_TILES`), and right at the fan
  it's *stronger* than gravity on purpose (so fan-hopping climbs higher).
  Query `fanAccelFor(x, y)` directly at fixed distances to test the falloff
  curve itself — physically dropping an actor toward a fan conflates
  "distance from the fan" with "time elapsed" since both change every frame
  as it falls, which makes the curve much harder to isolate, AND (see the
  next gotcha) continuous accel alone genuinely isn't enough to arrest a
  fast fall regardless of the curve's shape — check `fanAccelFor`'s raw
  output for the force curve, and a real physics trace (with the discrete
  kick engaged) for the felt bounce.
- **`fanAccelFor`'s distance index `i` starts at 0 (the actor overlapping
  the fan's own cell), not 1** (v2.20.2 fix — it used to start at 1, so an
  actor actually standing on/falling into the fan, the single most expected
  moment for it to matter, got zero force). If a test scans distances with
  `for (i = 1; i <= FAN_RANGE_TILES; i++)`, it's silently skipping the
  strongest point on the curve.
- **A fan's continuous force can't visibly arrest a fast fall on its own —
  a discrete kick does the real work** (`FAN_BOUNCE_MIN_SPEED`/
  `FAN_BOUNCE_RESTITUTION` in `stepActor`, v2.20.2). Testing "does falling
  into an upward fan produce a bounce" by only checking `fanAccelFor`'s
  returned `ay` proves the force curve is right but not that it's felt —
  run an actual fall (`enterPlayMode`, drop the player through several
  tiles onto/through the fan, sample `vy` every frame) and look for `vy`
  actually going negative (a true reversal), not just a smaller positive
  number.
- **`isStuckToSticky` only checks a sticky solid tile's LEFT, RIGHT, and TOP
  sides — never the tile directly under an actor's feet** (fixed in v2.20;
  it originally also checked the bottom-adjacent tile, which meant merely
  *standing on* an ordinary sticky floor was misread as "clinging to a
  wall" — gravity got permanently stuck at `vy = 0`, `grounded` never went
  true again, and jump input silently stopped working, for anyone who ever
  stood still on one). Sticky ground's own separate "slows you down" effect
  is `isOnStickyGround` (any geometry, top-surface-or-walkable-through),
  deliberately a different function from the wall-climb check.
- **Sticky is a timed cling (`STICKY_CLING_MS`), not indefinite climbing**
  (v2.20.3 — direct feedback that holding a direction while stuck let a kid
  scale a sticky wall forever). An actor freezes completely (no movement
  input of any kind, see `stuck` in `stepActor`) for `STICKY_CLING_MS`,
  THEN the existing `stickyReleaseT` ramp starts automatically — whether or
  not contact is still being made. If a test tries to "break contact early"
  by holding a direction away from the wall while still within the cling
  window, **nothing happens** — input is fully ignored while `stuck` is
  true, so the actor won't actually move until the cling timer itself
  expires. Don't assume pressing away ends the stick early; sample well
  past `STICKY_CLING_MS` (1000ms) before expecting any release to have
  started.
- **The level has an implicit solid floor/edges at the board boundary.**
  An actor that free-falls long enough will ground out at the bottom of
  the room and read `vy === 0` for that reason — not because whatever
  gravity-suspension mechanic you're testing is still active. Sample
  velocity *mid-fall*, not after an arbitrarily long wait.
- **A "popped" actor lingers ~220ms after its reaction fires** (real
  wall-clock `setTimeout`, `RECIPES.popVanish.duration`) before
  `removeActorById` actually removes it from `actors`. Wait past this
  before asserting an actor is gone.
- **Not every swatch in the Objects tab row is an actor** (see Architecture
  above — `goal`/`switch`/`plate`/`door`/`cannon`/`bomb`/`warp`/`fan`/
  `magnet`/`gravitywell`/`spawner`/`trampoline` are geometry tiles).
  Clicking one and reading `getSelectedActorDefId()`
  afterward will silently return whatever actor def was last actually
  selected, not anything related to the tile you clicked. Only `pushable`
  and the Collectibles-row presets are real loadable/placeable actor defs
  from the Objects tab.
- **`GRAB_KEY_RANGE` (~1.3 tiles) is measured from the player's own
  center to the target's center** — an actor-vs-actor grab and a
  grab-off-a-tile-cell both use this, but a kid (or a test) walking at
  `MAX_SPEED`/`NPC_MAX_SPEED` for even a few hundred ms covers this
  distance and more, especially toward a NON-blocking tile like cannon/
  bomb/magnet that a moving actor just walks straight through. A test that
  walks toward a carryable and then presses the grab key needs either a
  short, precisely-timed walk or (simplest) to place the player already
  adjacent before pressing Play — don't assume "walked roughly toward it"
  lands back in range. Under gravity, this cuts the other way too: a
  player placed in mid-air starts falling the instant Play begins, so a
  grab attempted even 100-200ms later may already be out of range of
  whatever's beside its ORIGINAL placed cell.
- **A dropped/thrown pushable-or-carryable's landing spot isn't
  predictable enough to assume in a later step of the same test.** A test
  that throws an object and then tries to grab something else nearby (by
  walking there) can end up re-grabbing the just-thrown object instead, if
  it happened to land closer than the intended target. Prefer teleporting
  the player via a debug-hook position set (or spacing the two objects/
  cells much further apart) over chaining "throw, then walk toward the
  next thing" in one test.

- One file changes almost every commit: `index.html`. Commit messages so
  far explain the **why** for each feature at some length (see `git log`)
  — matches this project's own principle of design rationale mattering
  more than mechanical description. Keep that style.

  designated feature branch per the session's instructions.
- Nothing else in the repo needs updating for a typical feature patch —
  no lockfile, no build artifacts, no test files (those are scratchpad-only
  and never committed).
