# Toy Game-Maker

## What this is

A "toy" game-maker for kids — structurally different from Scratch/GDevelop
(which require authored logic before anything fun happens) and from
Minecraft/Roblox (finished games you build *inside*, not constructed from
near-nothing). Closer in spirit to Bitsy, but not narrow to one genre:
continuous physics, rooms, and a growing tile vocabulary let it reach
Flappy-Bird-shaped, Dig-Dug-shaped, and Pitfall/Donkey-Kong-shaped games
from the same fixed piece set.

## Non-negotiable design principles

These have held under real pressure across the whole build. **Don't
compromise them for a new feature without flagging it explicitly to the
user first.**

- **No scripting layer, ever.** No if/then, no event/action authoring, not
  even a visual one. All behavior is a fixed, closed reaction table — kids
  compose by placing pieces, never by writing rules. Every feature added has
  stayed a placed piece with a fixed effect; this is the thing most likely
  to erode silently if not actively protected.
- **Always live — no edit/play mode split.** Painting a tile, flipping
  gravity, editing a room all take effect immediately in a running
  simulation. No "test my game" button anywhere in Build mode. (Build and
  Play *do* exist as two modes — see Architecture below — but the
  distinction is about stakes/snapshotting, never about "nothing happens
  until you press play.")
- **Tile vs. marker rule.** A property is a painted **tile** if its effect
  is only felt on contact with that specific cell (solid, hazard, bouncy,
  sticky...). It's a placed **marker** if it changes the rules of a whole
  zone regardless of contact (gravity, wrap). Sort new ideas by this test
  before deciding how a kid places them. (Game Rules — gravity/h-wrap/v-wrap
  — are the marker end of this spectrum: whole-room toggles, not painted
  cells; see `GAME_RULES`.)
- **Modifiers are geometry-agnostic.** `slippery`/`bouncy`/`hazard`/
  `lethal`/`sticky`/`wind` all combine with either `solid` or walkable
  (`none`) geometry; the combination determines the reading (a solid+bouncy
  tile bounces you off it, none+hazard is a puddle you walk through,
  none+lethal is lava, solid+lethal is a spike trap, none+sticky is mud you
  trudge through, solid+sticky is a wall you can climb). v2.20 removed
  `spring` — it was a second, higher-restitution tuning of `bouncy` with no
  distinct reading of its own; that "extra bounce power" idea now lives on
  the dedicated Trampoline *object* instead (see Architecture below), which
  is a better fit anyway per the very next principle.
- **Kid-friendly naming, not implementation-jargon.** "Temperament,"
  "geometry," and "channel" all got renamed once already for reading as
  design-jargon rather than words a kid would use (they persist as
  *internal* variable/field names — that's fine, code can stay precise —
  but anything user-facing must read like a toy, not an engine). Watch for
  this recurring — it's an easy mistake to reintroduce. `MODIFIER_LABELS`
  is the established mechanism for renaming a palette-facing label without
  touching the internal id/serialization format — it briefly held `bouncy`
  → "trampoline" in v2.19, reverted in v2.20 once "trampoline" became a
  real placed object instead (having the same word mean two different
  things — a modifier's display name AND an unrelated object — was the
  actual problem users hit, not the renaming mechanism itself).
- **Characters and Objects get real sprites; Ground stays abstract
  squares.** Identity matters for things with a specific function (what a
  door does, what a chaser does); it doesn't matter for pure terrain. No
  colored role-frame around pieces — it was tried, tested badly, removed
  (v2.14).
- **Win is unconditional.** Touching `goal` or completing full collection
  always wins, full stop — no room-topology check. An earlier, cleverer
  version conditioned this on room graph position and broke the moment
  loops became possible; the fix was simplifying, not patching further
  (v2.11).
- **Stakes (lives, game over, win) only exist in Play mode.** Build mode
  stays frictionless — getting caught just resets, forever, no consequence.
  This is deliberate, not a missing feature. (`consumeLifeIfPlaying()` is a
  no-op outside Play — this is the actual mechanism, not a special-cased
  check scattered everywhere.)
- **Sound is entirely synthesized, nothing sampled.** Even creature/voice
  sounds (cat, dog, chicken) are stylized synthesis, not recorded or
  library audio — keeps the whole audio palette consistent with everything
  else being generated by the same underlying system, and avoids
  file-size bloat in the single-file architecture (v2.18).
- **Single self-contained HTML file, no build step, no framework.** This is
  architectural, not incidental — it's what makes the standalone export
  (v2.7) a natural extension (dump the same runtime + a data blob into a
  second HTML file) rather than new infrastructure.

## Architecture

Everything lives in **one file**: `index.html` (~6,600 lines as of the last
patch — check current line count, it only grows). No `npm install`, no
bundler, no `<script src>` to anything but itself. Open it in a browser and
it runs. This is the whole "app."

### The tile model

A cell is a small stack of independent layers, not one value:

- **`board[y][x]`** — `"geometry:modifier"` (e.g. `"solid:bouncy"`,
  `"none:lethal"`, `"cannon-ne:none"`). Geometry decides what blocks
  movement / does the interesting mechanical thing; modifier is the
  contact reaction layered on top. `gameplayKey(geometry, modifier)`
  builds this string; `geometryAt(x,y)`/`modifierAt(x,y)` split it back.
- **`backgroundBoard[y][x]`** — pure decoration, never touches physics.
- **`colorBoard[y][x]`** — the switch/door/plate/fan **channel color** tag
  (`CHANNEL_COLORS`), independent of geometry/modifier. `isColorTaggable(geometry)`
  gates which geometries can even carry one.
- **`groundSkinBoard[y][x]` / `groundSkinRotationBoard[y][x]`** — which
  named Ground/Lethal skin (grass, stone, lava, spikes...) is painted over
  a plain geometry+modifier combo, purely cosmetic re-skinning of the same
  underlying mechanic (see `groundTileDefs`).

**`GEOMETRIES`** (current, see `index.html` for the live list — this drifts
every patch, don't trust this snapshot blindly):
`none, solid, goal, switch, plate, door, cannon-ne/se/sw/nw,
bomb, warp, fan-n/e/s/w, magnet, gravitywell, spawner, trampoline`.

A recurring trick: a geometry family with several storable orientations
(`CANNON_ORDER`, `FAN_ORDER`, and the modifier-axis `WIND_ORDER`) shows as
**one swatch** in the palette; a second click on an already-placed tile of
that family rotates it to the next orientation (`cannonRotateStrokeCells`
tracks this per-stroke). Any new multi-orientation piece should reuse this
exact pattern, not invent a new one.

**`MODIFIERS`**: `none, slippery, bouncy, hazard, lethal, sticky, diggable,
trap, wind-n/e/s/w`. `MODIFIER_LABELS` is currently empty (`{}`) — it's the
mechanism to reuse any time an internal id needs a friendlier palette name
without a serialization-format migration, not a promise that it's holding
anything right now. `diggable`/`trap` joined this list in v2.22 — see
"Ground merges with Ground Textures; diggable/trap become modifiers" below.

**`TEMPERAMENTS`** (actor self-steering, palette-selectable in the
Character tab): `stationary, wanderer, chaser, fleer`. There are also
actor "kinds" that exist outside this list: `PUSHABLE_KIND` ("pushable" —
full physics, zero self-steering, palette-selectable from the Objects tab
via `OBJECT_ACTOR_KINDS`), `"collectible"` (palette-selectable presets,
picked up on contact), and `HAZARD_BALL_KIND` ("hazardball" — same
zero-steering physics shape as pushable, but always bounces off walls and
always hurts on touch; **spawner-only**, never placeable from a palette
swatch — it's the spawner's default/fallback content, not a kid-facing
piece).

**Important, easy to miss:** not everything in the Objects-tab swatch row
is an actor. `goal, switch, plate, door, cannon, bomb, warp, fan, magnet,
gravitywell, spawner, trampoline` are **geometry tiles** (clicking them
calls `selectGeometry`, painting `board`); only `pushable` (and
collectibles, in their own row) are real **actor kinds** (clicking them
calls `selectActorKind`, setting `selectedActorDefId`/`paintMode =
"actor"`). This distinction matters a lot for anything that reads
`selectedActorDefId` — clicking a geometry-tile swatch does **not** change
it.

**v2.21 nuance to the above**: bomb/magnet/cannon/trampoline are still
painted geometry tiles exactly as described — but a kid can grab one with
the carry key (see Grab/carry/drop/throw below), which turns *that one
placed cell* into a real actor (`CARRY_BOMB_KIND` etc.) on the spot. The
palette/painting story is unchanged; this only matters once something is
already on the board and gets grabbed.

**v2.21, a second nuance**: bomb, magnet, cannon, fan, and spawner are all
now **physical** — `isBlockingGeometry` returns true for every one of them,
same as solid/diggable/Trampoline. Direct feedback: walking straight
through them (they used to be pure contact-trigger pads, like goal/switch)
made grabbing one feel glitchy, since there was nothing there to physically
register the interaction against. Fan and spawner are blocking-only for now
— not carryable — since both are architecturally tied to a fixed board cell
(fan's force calc and spawner's whole contents/timer/concurrency-cap system
scan `geometryAt`, not the `actors` array); making them carryable is a
bigger, explicitly deferred follow-up, not attempted here. See "Physical
objects vs. fixtures" and "Grab / carry / drop / throw" below for the full
story, including what had to change so bomb-arm/cannon-fire still work now
that touching them no longer means overlapping them.

**Trampoline (v2.20)** is a plain, single-orientation geometry tile (no
`_ORDER` family, unlike cannon/fan) — a real object with a real sprite
(`GEOMETRY_ICONS.trampoline`), blocking like solid (`isBlockingGeometry`),
that always bounces the player (and a hazard ball) at `TRAMPOLINE_RESTITUTION`
(0.97) with a minimum enforced launch speed (`TRAMPOLINE_LAUNCH_SPEED`) on
top — see `resolveAxis`'s `isTrampolineGeom` branch. It exists specifically
so "extra bounce power" is a placed, sprite-bearing *thing* a kid finds,
not a hidden second tuning of the plain `bouncy` modifier (that used to be
`spring` — see the Non-negotiable principles section above for why it was
removed instead of kept as a second modifier).

### Ground merges with Ground Textures; diggable/trap become modifiers (v2.22)

Direct feedback: the old Ground tab had four separate rows — flat "Ground"
swatches (`none`/`solid`/`diggable`/`trap`), "Surface" modifier swatches
(`slippery`/`bouncy`/`hazard`/`lethal`/`sticky`/`wind`), a "Ground textures"
row of real-art skins (grass/stone/dirt/snow), and "Lethals" (lava/fire/
spike). The ask: merge Ground and Ground textures into one row, rename
Surface to **Ground Effects**, and move `diggable`/`trap` OUT of the
geometry axis and into Ground Effects too — "so any tile can be made
diggable or trap or lethal etc," the same geometry-agnostic combining every
other modifier already had (see "Modifiers are geometry-agnostic" in the
Non-negotiable principles section — this patch is that principle finally
applied to the two modifiers that had been left out of it since v2.5).

**The merged Ground row** (`renderGroundSwatches`) now draws, in one
row: the two flat swatches (`none`, plain gray `solid`) from
`PALETTE_GROUND_GEOMETRIES` (trimmed to just those two), then every
`groundSlotIds` skin (real art, same swatch-drawing/`selectGroundSkin`
click path as before — `renderGroundSkinSwatch(container, id)` is the
shared per-swatch helper, reused by both this row and Lethals), then the
"+" custom-texture button. Five new built-in textures ship with this
patch: **Rubble** (`gndRubble`, `RUBBLE_ART`) is literally the old
`diggable` geometry's own dedicated icon art (a plain taupe square with a
few crack specks) — now that diggable has no geometry-level identity of
its own, that look becomes a normal, paintable ground texture instead, so
a kid who liked it doesn't lose it. **Brick** (`gndBrick`), **Sand**
(`gndSand`), and **Crystal** in two colorways (`gndCrystalPink`/
`gndCrystalCyan`, sharing one `CRYSTAL_FACET_PATTERN` array recolored via
two different `pat()` legends — the same "one shape, several palettes"
trick `FIRE_FRAMES`/`LAVA_FRAMES` already used) were direct, explicit
requests. The old separate "Ground textures" section/row/container
(`#groundSkinSwatches`) is gone entirely; `renderGroundSwatches` also
gained a `!selectedGroundSkinId` guard on the flat-swatch highlight so
picking a skin (which sets `selectedGeometry = "solid"` as a side effect)
doesn't ALSO show the flat `solid` swatch as selected right next to it —
harmless when the two lived in separate rows, visually wrong once merged
into one.

**v2.24 fix: Ground and Ground Effects genuinely combine now** — they
didn't, right up until a kid reported it. `selectSurfaceModifier` used to
unconditionally clear `selectedGroundSkinId` on every click, and
`selectGroundSkin` used to unconditionally overwrite `selectedModifier`
with the skin's own default (`"none"` for every plain texture) — so
whichever row you clicked *last* silently won, and picking grass then
bouncy (or the reverse order) always painted just one or the other, never
both. Fixed by making the two axes actually independent: a Ground Effect
pick no longer touches the selected skin at all, and a Ground texture pick
only forces the modifier when the skin has a real one of its own to offer
— a Lethal (lava/fire/spike), whose whole identity IS being lethal, per
its own "tagged lethal automatically" hint text. A plain texture's `"none"`
was never a meaningful reading to force onto whatever effect a kid had
already chosen, so it's left alone now. The flat `none`/`solid` swatches
are unaffected — picking one is still an explicit "no skin," same as ever.
**One thing this reopens, not yet addressed**: `drawGameplayTile`'s
modifier ring is suppressed whenever a skin is present (`!skinned` in its
own condition) — reasoned in v2.20 as "redundant clutter" back when a
skin+modifier combo other than a skin's own baked-in default was
unreachable anyway. It's reachable now, so a kid painting grass+bouncy
gets zero Build-mode visual cue that the bouncy effect is even there,
until they touch it in Play. Flag this to the user before changing the
ring-suppression rule — it was a deliberate call for the skin's-own-default
case, and it's not yet clear whether they'd want a cue back just for a
non-default combo specifically, or leave discovery to touching it.

**`diggable` and `trap` move from `GEOMETRIES` to `MODIFIERS`.** Each
keeps its *exact* old mechanic, just generalized to combine with whatever
base geometry (normally `solid`, or a solid-based ground texture) it's
painted over, instead of being its own fixed geometry:
- **`diggable`**: still blocks like `solid` and still only erodes via
  sustained player contact (`DIG_DURATION_MS`, `digProgress`, holding
  Down) — `isBlockingGeometry` doesn't need a branch for it at all anymore
  (it blocks purely because its base geometry already does); `resolveAxis`
  checks `modifier === "diggable"` (not a geometry) to run the erosion
  timer. `DIGGABLE_STAGE_ICONS` (the progressive crack art swapped in via
  `extra.digFrac`) is unchanged except stage 0 is now the standalone
  `RUBBLE_ART` constant instead of a now-deleted `GEOMETRY_ICONS.diggable`.
  Rendering-wise this is otherwise just like any other modifier: a colored
  ring around the base icon/skin (`MODIFIER_SWATCH_COLORS.diggable`, the
  same taupe hex the old geometry swatch used) — see `drawGameplayTile`.
- **`trap`**: still "solid to everyone but the player, who always slips
  straight through instantly and destroys it on contact" — the exact old
  asymmetric behavior, now expressed as `isBlockingGeometry(geometry,
  actor, modifier)` gaining a third parameter and a new first check,
  `if (modifier === "trap" && actor.isPlayer) return false;`, BEFORE any
  geometry check. This is the one deliberate exception to "modifiers never
  block on their own" (see that function's own updated comment) — it
  doesn't make trap block anything by itself, it makes the player
  transparent to whatever WOULD otherwise block per the base geometry. An
  NPC gets no such exception, so `solid:trap` still walls off a patrol
  path exactly like plain `solid` until the player's own touch clears it
  for everyone (`checkPlayerTileContacts`'s `modifier === "trap"` branch
  calls the unchanged `triggerTrap`, which nulls the whole board cell).
  `isBlockingGeometry`'s signature change means every call site needs the
  modifier too: `isCellBlocking` (computes it internally from
  `modifierAt`), `resolveAxis`'s main collision loop, and
  `checkPlayerTileContacts` all updated; `clampDragPosition`'s own
  non-blocking drag-contact loop switched its `geometry === "trap"` check
  to `modifier === "trap"` the same way.

**Backward compat for old saves — two separate gaps, both real:**
1. A save from before this patch can still have a raw `"diggable:none"` or
   `"trap:hazard"` board-cell string — a geometry value `GAMEPLAY_TILE_DEFS`'
   cross-product no longer generates ANY entry for, since `GEOMETRIES` no
   longer contains those values. Left alone, `gameplayTileAt` would
   silently return `undefined` for that cell forever (not a crash — the
   tile just vanishes from the game, permanently, the moment an old
   project loads). `migrateLegacyGroundEffects(board)`, called on every
   room's board from `restoreProjectSnapshot` right after `rooms =
   structuredClone(snap.rooms)`, rewrites any `diggable`/`trap` geometry
   cell to `solid` + that same value as the modifier —
   `gameplayKey("solid", geometry)`. **Deliberately lossy**: any modifier
   that used to be stacked on a `diggable`/`trap` tile (e.g. an old
   `"trap:hazard"`) is dropped, since a cell only ever holds one Ground
   Effect now and preserving the tile's PRIMARY mechanic (dig-through /
   crumble-on-touch) matters far more than a secondary modifier it
   happened to also carry — a rare, incidental old combo to begin with.
   The built-in "Tunnel Trouble" sample's own maze-string builder
   (`paintMazeString`, the `'D'` character) is source code, not a saved
   project, so it was fixed directly (`gameplayKey("solid", "diggable")`)
   rather than relying on this migration to catch it.
2. `groundSlotIds` itself — the ordered list of which texture swatches
   show up at all — is **also** backward-compat-vulnerable, a level up
   from the more familiar "does `groundTileDefs[id]` have real content"
   gap the Rooms section above already covers: `restoreProjectSnapshot`
   used to do `groundSlotIds = snap.groundSlotIds ? snap.groundSlotIds.slice()
   : GROUND_SEEDS.map(...)`, which takes the `snap.groundSlotIds` branch
   for ANY older save (one already exists, just missing the five new
   ids) — so a returning project's Ground row would stay frozen at
   whichever built-in textures existed when it was last saved, forever,
   never gaining Rubble/Brick/Sand/Crystal. Fixed with one more line right
   after: `GROUND_SEEDS.forEach(seed => { if (!groundSlotIds.includes(seed.id))
   groundSlotIds.push(seed.id); })` — appends any missing BUILT-IN seed id
   without touching a kid's own custom ids. **Any future built-in
   `GROUND_SEEDS`/`LETHAL_SEEDS` addition needs this same append pattern**,
   not just the existing `groundTileDefs[id]` content-backfill just below
   it in the same function — two different gaps, both need covering.

### Barrier: a moveable wall/door (v2.23)

Direct feedback: `plate` could toggle a channel and wire up to a matching
switch/door/solid, but nothing in the shipped samples ever demonstrated
*why* a kid would want that — the mechanism existed with no purpose behind
it. The ask was two things at once: give plate/switch a real reason to
exist, and add a genuinely "moveable" wall/door, since the existing
channel-gated `solid` just goes instantly non-blocking with a faint ghost
outline — never actually reads as something that *moves*.

**`barrier`** is a new Object geometry (`PALETTE_OBJECT_GEOMETRIES`, real
sprite — a portcullis: a frame top and bottom with four vertical bars,
plain and mechanical on purpose, since its *channel color* is what tells a
kid which switch/plate controls it, the same corner-badge convention every
other color-taggable tile already uses). Mechanically it's `solid`'s own
channel-gate rule, generalized: blocks unless its channel is on. That
generalization is `isChannelGateGeometry(geometry)` (`solid` or `barrier`),
now shared by `isCellBlocking` and `resolveAxis` in place of each having
its own inline `geometry === "solid"` check — the one thing this feature
actually changes about existing wall-gating code, and a pure refactor: a
plain gated solid wall behaves identically to before. `isColorTaggable`
gains `barrier` alongside `solid`/`switch`/`plate`/`door`/fan. Not
carryable (`CARRYABLE_KINDS` doesn't list it) and not a Fixture (it DOES
physically block while closed, unlike goal/switch/door/warp/gravitywell,
which is exactly why it lives in the Objects row instead) — see "Physical
objects vs. fixtures" above for why that distinction matters.

**The actual "moveable" part is `drawGameplayTile`'s own barrier branch**:
instead of `solid`'s instant ghost-outline, the portcullis sprite is
clipped to the tile and translated straight up as it opens (straight back
down as it closes), so it genuinely looks like it slides into a slot above
rather than just fading. `BARRIER_SLIDE_MS` (350) is how long a full
open/close takes. Purely visual — the tile's actual blocking is still the
same instant `isChannelOn()` read every other gate already uses; nothing
about *when* a kid can walk through changes, only what it looks like while
that happens. The timing input is `channelStateSince` (color ->
`{ on, since }`), recomputed once a tick by `updateChannelTransitions()`
(called right after `updatePressurePlates()`, so it sees the current
frame's fresh plate state) — a cheap, unconditional 5-entry loop over
`CHANNEL_COLORS`, the same "just always run it" choice `updatePressurePlates`
itself already makes. Transient, never persisted, same lifecycle as
`plateChannelsActive` (reset in `clearTransientRuntimeState`/
`restartStandaloneGame`) — nothing physics-facing ever reads it.

**A pressure plate can now genuinely trap something**, not just gate a
wall — this is the actual payoff the whole feature was built to
demonstrate (see "The Monster's Den" sample below for it in practice).
`updatePressurePlates()` already keys a plate's channel on *any* actor
overlapping it (player, pushable, or an NPC — "any actor works... no
weight/mass comparison needed" per its own v2.9 comment), so a chaser
crossing a plate holds a barrier open exactly as well as the player
standing on it does. Lure something across a plate positioned just before
a barrier's doorway, then clear the plate yourself (walk past, don't
linger) — the channel drops the instant nothing overlaps it, and the
barrier reseals with whatever crossed it now on the far side. Verified
directly: an actor placed on a plate opens its barrier; moved fully past
the barrier and off the plate, the channel drops and the SAME barrier that
let it in now blocks it from leaving too. No inversion or new state
machine needed — this is `solid`'s original v2.9 gate rule, unchanged,
just given a second physical form kids can literally watch move.

### The Monster's Den (v2.23)

A fifth built-in sample, built specifically to demonstrate Barrier/plate
having a real purpose: a monster sealed in its own den, a goal inside with
it, and a room full of tools — not required, just offered — for surviving
the chase once it's out. `buildMonstersDenGame()`/`MONSTERS_DEN_MAZE`,
registered in `SAMPLE_GAMES` with its own icon
(`drawMonstersDenIcon` — a dark archway, a portcullis, two glowing eyes).
Free-roam (no gravity), the same choice Cheese Heist's own cat-chase
already made — a top-down hunt reads more naturally than platformer jump
arcs for "something is hunting you."

**The forced beat**: the den's one doorway is a red Barrier, openable only
by a red switch elsewhere in the room. Reaching the goal *requires*
finding and flipping that switch — and because a switch's flip is
permanent (unlike a plate), that release is for the rest of the game, not
a momentary window. This is the literal "switch opens a door, the monster
chases you" beat from the original ask.

**The offered tools**, none required to win: a second Barrier/Plate pair
(orange) at a chokepoint doubles as a trap, per the mechanism above — lure
the monster through, clear the plate yourself, and it reseals behind
whatever crossed it; a pushable block sits in the open, ready to shove
into the monster's path; retreating back through the den's own single
doorway under pressure already reads as "leading it into a dead end," just
approached from the far side, so no separate dead-end structure was built
on top of it. A collectible sits right next to the monster as deliberate
bait (risk/reward, not a literal AI lure — chasers only ever steer toward
the player, never toward items) and a second, safer one sits out in the
open. The room is deliberately not a puzzle with one correct solution —
every tool here is something to experiment with, matching this whole toy's
"kids compose, they don't solve" stance; the monster is a piece to play
with, not a wall to get past. Getting caught costs a life and punts the
player back to start (the existing `chaser` reaction, `resolveActorContact`
— "eaten" is a setback here, not an instant loss), verified directly:
standing next to the released monster does cost a life, so the danger is
real, not cosmetic.

**A real chaser-pathing gotcha, found building this and worth knowing
for any future pen/den design**: the den was first built as a tall 7-row
box with a single-row doorway partway down one side. The monster never
came out — 0px of movement over two full seconds once released. Cause: a
`chaser` has no pathfinding at all, only a straight accel toward wherever
the player currently is right now (`steeringAccelFor`) — with the player
positioned diagonally from the den, that accel vector doesn't point along
the doorway's own row, so the monster drove itself straight into a corner
of the pen (pressed against the south wall, one row off from the door) and
sat there indefinitely with genuinely zero net velocity, not just visibly
stuck. Cheese Heist's own chamber already learned a version of this lesson
("a through-passage, not a dead-end pen," gapped on two sides so a cat
always has a route toward whichever half of the maze the player is in);
this room applies the more general fix — **a den/pen's interior should
share a row or column with its own doorway everywhere inside it**, not
just at one point along an otherwise taller/wider box. `MONSTERS_DEN_MAZE`
makes the den exactly one row tall for this reason: wherever the monster
is inside it, it's already on the doorway's own row, so the straight-line
accel that already works for every other direction also works for finding
the exit. Confirmed with a direct physics trace (position/velocity sampled
every 400ms) before and after the fix, not just a single before/after
screenshot — the first version's "stuck" reading was a real, reproducible
zero, not a timing fluke.

### New character presets from a reference sprite sheet: monster, skeleton, slime, tabby cat (v2.24)

The user supplied an external 8x8-labeled pixel-art reference sheet (47
icons across Characters/Objects/Terrain/Structures/Hazards/FX) and asked
for four specific pieces to become playable character presets: monster,
skeleton (explicitly to **replace** the old stick-figure preset), slime,
and cat. Extraction used programmatic grid detection (background-color-
distance masking plus row/column content-band profiling) rather than
manual coordinate guessing, verified against a rendered contact sheet
before any art was touched.

**The sheet's sprites are natively ~16x16, not actually 8x8 despite the
sheet's own label** — this engine's whole pixel-art system (`ART = 8`,
`pat()`, every existing `CHARACTER_PRESETS` entry) is hard-fixed to 8x8,
so each of the four was hand-redrawn at the engine's real resolution
following the reference's silhouette/color-blocking/readability, the same
"matched pixel-for-pixel AT the engine's resolution, not the reference's"
approach `HERO_POSES`/`PRINCESS_POSES`/`GHOST_POSES` already established.
None of the four got per-pose art (`HERO_POSES`-style stand/walk/jump
frames) — the reference only ever supplied one static image per creature,
and the existing `blocker`/`wanderer`/`chaser`/`fleer`/`cat` presets are
the established precedent for a single-`art` preset with no poses, so
these four followed that same simpler shape rather than inventing motion
frames with nothing to base them on. `MONSTER_ART`, `SKELETON_ART`,
`SLIME_ART`, and `TABBY_CAT_ART` are defined right after the existing
`CAT_ART` constant, each built with the same `pat(rows, legend)` helper
every other preset already uses.

**"Cat" needed a naming decision.** The engine already has a built-in
`CAT_ART` (deep red, used as the fixed chaser look in Cheese Heist, Tunnel
Trouble, and The Monster's Den) — silently overwriting it with the
reference sheet's own differently-colored cat would have reskinned every
sample's monster without anyone asking for that. The new sprite is a
separate preset, `"tabby cat"` / `TABBY_CAT_ART`, sitting right next to
the original `"cat"` in `CHARACTER_PRESETS` — both are picker options, and
the original `CAT_ART`/`"cat"` preset is completely untouched, still the
one every built-in sample's chaser actor def points at.

**Skeleton replaces the stick figure outright, not alongside it.** The
old `STICK_LEGEND`/`STICK_POSES` constants (the very first player art this
project ever had, dating to before hero/princess/ghost existed) are
deleted entirely — confirmed via a full-file grep that nothing else
referenced them before removing — and `"stick figure"` no longer appears
in `CHARACTER_PRESETS` at all. This was an explicit user instruction
("skeleton, to replace the stick figure"), not an inference; nothing else
about the preset list's shape changed as a result — `CHARACTER_PRESETS`
still holds one entry per name, monster/skeleton/slime slotting in where
poses-less entries already lived, right before `blocker`.

**No export-pipeline changes were needed.** A preset is purely a
Build-mode convenience — clicking one just copies its `art`/`poses` onto
whichever `actorDefs[defId]` is currently selected (`renderPresetSwatches`,
pre-existing code, untouched by this patch). Once applied, the resulting
def is a completely ordinary entry in `actorDefs`, serialized and restored
by the same snapshot/export machinery every custom character already goes
through — there's no separate "preset" concept once the art has been
picked. Verified directly: applied the skeleton preset to the player,
exported a standalone game, and confirmed the exported HTML both contains
the new art's color data and plays back error-free with the skeleton
sprite rendering correctly on screen.

Verified with Playwright: all four new presets (`monster`, `skeleton`,
`slime`, `tabby cat`) appear in the character preset shelf alongside the
untouched originals; `stick figure` no longer appears anywhere; all four
existing built-in sample games still load and play with zero errors; the
standard export pipeline (tested via The Monster's Den, and separately via
a project with the skeleton preset applied to the player) produces a
working, error-free standalone game in both cases.

### Custom pixel-editor colors (v2.25)

Direct feedback right after the monster/skeleton/slime/tabby-cat presets
shipped: the reference sheet's colors didn't exactly match any of the 12
fixed swatches (`PALETTE_COLORS`) the pixel editor has always offered, so
there was no way to touch up a preset's art to match it more closely once
grabbed. **The pixel-art format itself was never the limiter** — `paintPixel`
already stores a literal hex string (or `null` for transparent) directly
per cell (`currentArt[py*ART+px] = currentColor`), no palette-index
indirection — so this was purely a UI gap: `renderColorRow()` only ever
rendered the 12 hardcoded swatches, with no way to add another one.

**The fix**: a "+" swatch at the end of the color row (`renderColorRow`,
styled like the existing swatches with a dashed border to read as "add"
rather than "select") opens a hidden native `<input type="color">`
(`#customColorPicker`) via a synthetic `.click()`. Picking a color deliberately
uses the browser's own OS color-picker rather than a hand-built hex/RGB
UI — zero extra markup or dependencies, and every browser's native picker
already ships an eyedropper that can sample a color directly from a
reference image elsewhere on screen, which is exactly the "match this
exactly" use case that prompted the ask. On the picker's `change` event,
the hex is appended to `customColors` (deduped — picking the same color
twice doesn't add a second identical swatch) and immediately selected as
`currentColor`. `customColors` is a plain ordered array, rendered right
after `PALETTE_COLORS` in the same swatch loop — a custom color behaves
exactly like a built-in one from that point on: click to select, paint
with it, it persists in the row.

**Persistence**: `customColors` is wired into `captureProjectSnapshot`/
`restoreProjectSnapshot` (the "four places" pattern's #3 — see the Rooms
section above), with the usual `snap.customColors ? ... : []` backward-compat
default for a save from before this patch. It's a project-global, not
per-room, so it needs nothing in `activateRoom`/`snapshotCurrentRoomState`.
It's also deliberately **not** wired into `enterPlayMode`'s `buildSnapshot`/
`restartPlaySessionFromSnapshot`/`exitToBuildMode` — that path only covers
state Play mode can actually mutate (rooms, doorLinks, spawnerContents,
switchChannels), and painting sprites isn't possible in Play mode at all,
the same reason `actorDefs`/`groundTileDefs`/`customActorSlotIds` aren't in
that path either.

**No export-pipeline changes needed, for the same reason the character
presets above needed none**: `exportStandaloneGame` only ever ships the
*resolved* art (literal hex strings already baked into each `actorDefs`/
`groundTileDefs`/`backgroundTileDefs` entry) — it has no notion of "the
editor's available colors" to begin with, custom or otherwise. Verified
directly: picked a custom color, painted the player with it, exported a
standalone game, and confirmed the exported HTML's `GAME_DATA` contains
the exact custom hex and the exported game plays back error-free with it
rendering correctly.

Verified with Playwright: the color row renders the 13 built-in swatches
(12 colors + the eraser) plus the new "+" button; picking a custom color
adds exactly one new persistent swatch and selects it; painting with it
stores the precise hex in the art array; re-picking the same color doesn't
duplicate the swatch; `captureProjectSnapshot`/`restoreProjectSnapshot`
round-trips `customColors` correctly; restoring a snapshot missing the
field (simulating an older save) defaults cleanly to an empty array with
no crash; all four built-in sample games still load and play with zero
errors after this change.

### A second sprite-editor round: pressure plate reskin, Button, Cannon 2/Bomb 2, Crate, key/star collectibles, bomb/cannon animation (v2.27)

The sprite-editor tool built for the previous round (a standalone
`sprite-editor.html`, originally delivered separately rather than committed
— see "The sprite editor tool" section below for where it actually lives
as of v2.36 — it exists purely so the user can touch up auto-extracted
reference art with a proper pixel editor + eyedropper-capable color picker,
outside this app) came back with a project JSON holding refined versions
of a handful of its 24 extracted icons. The request named eight specific pieces and asked for
each to land in its own "logical category" — deliberately **not** all 24;
the other sixteen (wall, door, gate, platform, ladder, bridge, barrel,
chest, fire, fan, spring, wind, teleporter, moving_platform) were left
untouched and unwired, same as they've sat since the tool shipped, pending
a future request that names them specifically.

**Pressure plate reskin + on/off indicator recolor.** The user's fixed
`plate` art replaces the old hand-drawn `GEOMETRY_ICONS.plate` outright — a
metal frame over a red indicator strip. The "add the color animation to
red spot for on/off" ask needed a mechanism this codebase didn't have yet:
swapping one baked color for another at render time without touching the
underlying `pat()`-built array. `recoloredArt(art, fromHex, toHex)` is that
mechanism — a one-line `art.map(c => c === fromHex ? toHex : c)`, general
enough that any future recolor-on-state need can reuse it rather than
hand-editing a second copy of an icon. `PLATE_INDICATOR_OFF_HEX` (the red
the user's art already uses for the indicator) and
`PLATE_INDICATOR_ON_HEX` (`CHANNEL_COLOR_HEX.green`, not a new color of its
own — reusing the existing channel-color palette rather than inventing an
"activated" color nothing else uses) are looked up by `drawGameplayTile`'s
plate branch: `extra.channelOn ? recoloredArt(icon, OFF_HEX, ON_HEX) :
icon`. Verified by sampling the actual rendered canvas pixel at the
indicator strip before and after a player stands on the plate — the pixel
color measurably changes, confirming the recolor fires at the right
moment, not just that the code compiles.

**Button — a genuinely new mechanic, not just new art.** The request was
"works like a pressure plate, but works by pushing into it" with two
facing states. A plate keys its channel off *overlap* (any actor
overlapping its cell, checked every tick in `updatePressurePlates()`) — but
a pushed-into button needs to be **blocking** (that's the whole "push"
feel), and `isBlockingGeometry` returning true means nothing can ever
truly overlap it, so the plate's own overlap-scan approach doesn't apply.
Instead, `pushButtonChannelsActive`/`pushButtonFacing` (two new globals,
reset every tick the same way `plateChannelsActive` already is, inside
`updatePressurePlates()` for locality with the other channel-state reset)
are populated from inside `resolveAxis`'s own per-axis collision
resolution — the exact same "collision-time trigger" pattern this codebase
already uses for bomb-arm and cannon-fire (see "Physical objects vs.
fixtures" above) — rather than an overlap scan that could never fire. Both
`vx > 0` and `vx < 0` collision branches record which side the actor
pushed from (`"left"`/`"right"`, i.e. which direction the actor was
travelling when it made contact) into `pushButtonFacing`, and light the
button's own channel color for that frame. `isChannelOn(color)` now ORs a
third source (`switchChannels` permanent, `plateChannelsActive` momentary
overlap, `pushButtonChannelsActive` momentary push-contact) — a button's
"on" state lasts only as long as something is actively pressed against it,
same momentary lifetime as a plate, just keyed by a collision resolution
instead of an overlap check. **The "two states" ask is handled entirely in
rendering, no second sprite drawn**: `drawGameplayTile`'s button branch
mirrors the same icon horizontally (`ctx.scale(-1, 1)` around a
translated origin) when `facing === "right"`, left unmirrored otherwise —
one piece of art, two readings, the same "one shape, several orientations"
economy the cannon/fan rotation families already lean on, just via a
canvas transform instead of a stored alternate array. Named **"Button"**
in the palette (`GEOMETRY_LABELS[PUSH_BUTTON_GEOMETRY] = "button"`,
internal id stays `pushbutton`) rather than reusing "switch" or "plate" —
neither existing word fit a "push into it" mechanic, and the project's own
established mechanism for a friendlier palette-facing name without an id
migration (`GEOMETRY_LABELS`, mirroring the pre-existing
`MODIFIER_LABELS`) was already there to reuse. This naming choice, and the
left/right-via-mirroring interpretation of "two states," were both made
without asking first — flag either back if "button" doesn't read right, or
if the two states were meant to be visually distinct art rather than a
mirrored single sprite.

**Cannon 2 / Bomb 2 — parallel families, not forks.** "Will theoretically
replace the existing cannon... let's add it as a 2nd cannon so I can try
it out" (same wording for bomb) was a deliberate scoping choice by the
user: ship the refined art as a genuinely separate, second palette entry
rather than overwriting the original, so both can be compared/played
side-by-side before ever deciding to retire the old one. Mechanically
these are **not** reimplementations — every existing cannon/bomb code path
was generalized to also recognize the new geometry, via a small set of
shared predicates rather than literal duplication at each call site:
`cannonFamilyFor(geometry)` looks up which of `CANNON_FAMILIES`
(`[CANNON_ORDER, CANNON2_ORDER]`) a given orientation string belongs to,
`isAnyCannonGeometry` replaces every old `CANNON_ORDER.includes(geometry)`
exact check, `isBombGeometry` replaces every old `geometry === "bomb"`
check, and `isCarryBombKind` replaces every old `temperament ===
CARRY_BOMB_KIND` check on the carried-actor side. Every one of the
pre-existing call sites that used the old exact-match form was found by
grep and updated: `isBlockingGeometry`, the bomb-arm/cannon-fire trigger in
`resolveAxis` (and its `clampDragPosition`/`fireBlockingTileReaction`
duplicate), `convertGrabbedTileToActor`'s tile-to-actor conversion,
`currentPoseFor`'s cannon-direction pose lookup, `resolveActorContact`'s
dropped-cannon-fire branch, `attachCarryable`/`dropCarriedObject`/
`throwCarriedObject`'s bomb-fuse pause/resume calls, and
`renderActors`' bomb-flicker check. `CANNON2_ICON_NE` is the one hand-built
orientation (from the user's fixed art); `rotateArt90CW` (the same helper
`cannon`/`fan` already use to derive their other three orientations from
one drawn base) produces the other three — no new rotation logic needed.
`selectGeometry`/`paintGeometryModifierAt`'s "click again to rotate through
the family" behavior (`cannonRotateStrokeCells`) was generalized the same
way, keyed off `cannonFamilyFor` so a click on a `cannon2` tile only ever
rotates within `CANNON2_ORDER`, never crossing into `CANNON_ORDER`.
Grabbing a `cannon2`/`bomb2` tile converts it into its own new carried-kind
actor (`CARRY_CANNON2_KIND`/`CARRY_BOMB2_KIND`, defs `CARRY_CANNON2_DEF_ID`/
`CARRY_BOMB2_DEF_ID`) — confirmed end to end with Playwright, including a
bomb2 grabbed mid-arm correctly pausing its already-ticking fuse exactly
like bomb1 does (the exact "grabbed mid-countdown genuinely means paused"
behavior documented under Grab/carry/drop/throw above, now proven to hold
for the generalized `isCarryBombKind` check too, not just the original
literal one). Palette labels ("cannon 2"/"bomb 2") come from
`GEOMETRY_LABELS`, same mechanism as Button above. **Backward-compat**: the
existing documented `actorDefs` backfill list in `restoreProjectSnapshot`
(the one this doc's Grab/carry/drop/throw section calls out as needing a
one-line addition for every new built-in actor def) gained
`CARRY_BOMB2_DEF_ID`/`CARRY_CANNON2_DEF_ID` — verified directly by
restoring a simulated pre-patch snapshot with both keys stripped out and
confirming they're backfilled rather than left missing.

**Crate replaces "pushable" as the display name — and exposed a real,
separate crash in doing so.** The user's fixed crate art replaced
`actorDefs[PUSHABLE_DEF_ID].art`, and its `.name` field changed from
`"pushable"` to `"crate"` so the palette shows the friendlier word (the
internal `PUSHABLE_KIND`/`PUSHABLE_DEF_ID` identifiers are deliberately
untouched, per the project's own "internal ids can stay engine-jargon"
convention). This alone should have been a pure cosmetic rename, but it
broke clicking the crate swatch outright: `selectActorKind(kind)` — the
handler that actually runs when *any* Objects/Characters swatch is
clicked — resolves which def to select via
`findDefaultActorDef(kind)`, which requires `actorDefs[id].name === kind`
(the temperament string) to match. Renaming the def's `.name` away from
the literal string `"pushable"` meant `findDefaultActorDef("pushable")`
could no longer find its own def, returned `undefined`, and
`activeArtFor(actorDefs[undefined])` threw immediately — a real,
reproducible crash (confirmed via a targeted Playwright repro before
touching any code), not a hypothetical. The fragility already had a
partial fix elsewhere: `renderObjectSwatches` (the code that draws the
swatch in the first place) already special-cases `PUSHABLE_KIND` to look
up `PUSHABLE_DEF_ID` directly rather than trust the name-match — but
`selectActorKind`, the handler wired to the click itself, had never
gotten the same treatment, presumably because nothing had ever renamed
pushable's `.name` away from `"pushable"` before now. Fixed by mirroring
that exact same special case: `selectedActorDefId = kind === "player" ?
playerDefId : kind === PUSHABLE_KIND ? PUSHABLE_DEF_ID :
findDefaultActorDef(kind)`. **Any future rename of a built-in def's own
`.name` away from its temperament string risks this same class of bug for
whatever OTHER code still leans on `findDefaultActorDef`'s name-match** —
this fix only covers pushable/crate; a similarly-renamed hazard ball or
carried-object def would need the identical special case added at this
same call site. Confirmed fixed via the original repro (zero errors) and
via a full batch of crate/collectible/cannon2 assertions that had
previously crashed partway through on this exact bug. **A secondary,
deliberately-accepted nuance found while backward-compat-testing this**: a
genuinely old save whose own serialized `actorDefs.pushable.name` literally
still says `"pushable"` keeps showing "pushable" in the palette forever
after this patch, never force-renamed to "crate" — because `actorDefs` is
live, per-project data (same category as a custom character's own name),
and the backward-compat backfill mechanism only fills in *missing* keys,
it never overwrites an existing value. Only a brand-new project or a
built-in sample (both of which take their `actorDefs` from the current
`FACTORY_DEFAULT_SNAPSHOT`) picks up the new "crate" name automatically.
This is consistent with how a custom character's name has always worked,
not a gap — flagging it since it means "crate" won't appear for
already-published/exported old games without a fresh save.

**Gem/Key/Star as collectibles.** The user's fixed gem art replaced the
existing `COLLECTIBLE_ART` in place (gem was already a built-in
collectible; only its art changed). Key and star are new collectible
presets/seeds: `KEY_ART`/`STAR_ART` alongside the existing per-item arts,
added to both `COLLECTIBLE_SEEDS` (the persisted per-project slot list) and
`COLLECTIBLE_PRESETS` (the picker shelf). This is the exact same
"append-missing-built-in-seed-id" backward-compat gap the Ground section
above already hit once for `groundSlotIds`/`GROUND_SEEDS` — a save from
before this patch has its own `collectibleSlotIds` already populated
(cheese/gem/heart/coin), and a blind `snap.collectibleSlotIds ? ... :
COLLECTIBLE_SEEDS.map(...)` in `restoreProjectSnapshot` would take the
"already has a list" branch forever and never gain key/star. Fixed with
the identical append pattern already established for ground seeds:
`COLLECTIBLE_SEEDS.forEach(seed => { if
(!collectibleSlotIds.includes(seed.id)) collectibleSlotIds.push(seed.id);
})`, right after the existing snap-or-default line. Verified by restoring
a simulated old snapshot with `collectibleSlotIds` stripped back to its
pre-patch four entries and confirming key/star get appended rather than
staying missing. **Any future built-in collectible needs this same
append line** — now the second confirmed instance of this exact gap
shape (ground seeds, collectible seeds), worth checking for on any list
of built-in ids gated behind an "already exists in the save" branch.

**Bomb/cannon animation — an art-override on the existing keyframe
system, not new sprites drawn per-frame.** "We've made particle and
explosion, but what I want are animations for our bomb and cannon to make
them more exciting" was interpreted as: reuse the existing `RECIPES`
keyframe-deformation system (scale/rotate/translate/fade over a fixed
duration), but let a recipe instance show a *different* sprite than the
thing that triggered it, rather than deforming the bomb/cannon's own icon.
`playRecipe(entity, name, art)` gained an optional third `art` parameter,
stored alongside the existing `t`/`recipe` fields in `animState`/
`tileAnimState`; the render loop for both actors and tiles now checks
`if (anim.art) { art = anim.art; }` before falling back to the triggering
entity's own icon. Two new baked sprites, `EXPLOSION_ART` and
`PARTICLE_ART`, are what get shown this way — not because the user's own
"Particle"/"Explosion" reference art was reused directly (those were
listed as *already made*, existing pieces from the earlier extraction
round, not part of this round's fixed-sprite JSON), but because an
explosion/particle look was needed for exactly this override slot and this
was the natural place to add it, matching the user's own naming for what
they wanted to see. **Bomb**: `detonateBombAt`'s existing
`tileAnimState[...] = { recipe: "bombBlast", ... }` now sets `art:
EXPLOSION_ART` specifically for the bomb's own cell — a neighboring solid
wall the same blast also clears still plays the blast recipe on *its own*
icon, undecorated, since only the bomb's own detonating cell should show
an explosion sprite, not every tile the blast happens to affect.
`detonateCarriedBombAt` (the carried/dropped-bomb detonation path, entirely
separate from the tile path per the existing Grab/carry/drop/throw
section) got the same `art: EXPLOSION_ART` on its `playRecipe` call.
**Cannon**: firing now anchors a new `muzzleFlash` recipe (120ms,
scale-and-fade, `art: PARTICLE_ART`) at the cannon's own board cell via
`tileAnimState`, not at the fired actor's position via `animState` — a
flash attached to the fired actor would fly away with it instead of
staying at the muzzle. This needed `triggerCannon(actor, geometry, cx,
cy)` to gain two new optional parameters so it has cell coordinates to
anchor to; both tile-based call sites (the direct-collision trigger in
`resolveAxis`, and the build-mode-drag `fireBlockingTileReaction` path)
pass them through. **Deliberately left out**: the one call site with no
board-cell context — a *dropped/resting* carried cannon actor firing the
player who bumps it (`resolveActorContact`'s `CARRY_CANNON_KIND`/
`CARRY_CANNON2_KIND` branch) — has no fixed cell to anchor a
`tileAnimState` flash to, and forcing an `animState`-based flash onto the
actor being fired (rather than the player being launched) would need a
different anchor entity than what's cleanly available at that call site;
flag this to the user before attempting it, since it's a real gap in
"every way a cannon can fire gets a flash," not an oversight that was
already fixed elsewhere. Verified with Playwright: the cannon flash
mechanically fires (`muzzleFlash` observed live in `tileAnimState` at the
moment of collision) for the two tile-triggered paths that now have it;
the bomb detonation's explosion-sprite-override renders without errors on
both the tile and carried paths; the full 4-sample regression sweep plus a
fresh export (with bomb2/cannon2/crate/key/star all painted into a room)
both run error-free.

**Scope note, stated explicitly rather than left implicit**: of the 24
icons the sprite-editor tool extracts, only these 8 — plate, button (new),
cannon2, bomb2, crate, gem, key, star — were wired into the live game this
round, exactly matching what the request named. The other 16 fixed
sprites sitting in the user's uploaded JSON (wall, door, gate, platform,
ladder, bridge, barrel, chest, fire, fan, spring, wind, teleporter,
moving_platform) were not touched, not integrated, and don't yet correspond
to any mechanic in this engine — they're future work, not an oversight.

### Crate/gem "didn't publish" for a returning project — stale factory content (v2.27.1)

Direct feedback right after v2.27 shipped: several of the new pieces
"didn't publish" — most visibly, the palette kept showing "pushable" where
"crate" should be, and gem's refreshed art never appeared. **Real, not a
misunderstanding of the intentional 16-sprites-out-of-scope note above** —
this was a genuine gap in v2.27's own backward-compat work. Every backfill
in `restoreProjectSnapshot` up to this point followed one shape: "does
`actorDefs[id]` exist at all? If not, seed it from
`FACTORY_DEFAULT_SNAPSHOT`." That's correct for a *new* id nobody's save
could already have — but pushable and `colGem` both already existed
*before* this patch, so `!actorDefs[id]` was false for them on every
returning project, and the OLD factory content (the name `"pushable"`, its
old brown crate-cut art; the old cyan gem art) kept shadowing the new
default forever, on every single load — reproduced directly by simulating
a pre-v2.27 snapshot and restoring it.

Fixed the same way `migrateLegacyGroundEffects` (above) already upgrades
stale board content, applied to `actorDefs` instead: `migrateStaleFactoryArt`
keeps two frozen copies of the exact pre-v2.27 art (`LEGACY_PUSHABLE_ART`,
`LEGACY_GEM_ART`) and, right after `actorDefs = structuredClone(snap.actorDefs)`,
checks each live entry against its legacy twin byte-for-byte
(`artEquals`). Only a match — proof nothing was ever hand-edited — gets
swapped for the current `FACTORY_DEFAULT_SNAPSHOT` version; a kid's own
repaint of either is left completely alone, exactly the same "never
overwrite real customization" rule every other actorDefs backward-compat
fix in this file already follows. Verified directly: restoring a simulated
old snapshot (old name, old art, byte-identical to the legacy constants)
now correctly upgrades to "crate" and the new gem art; a *not*-legacy-clean
copy (this migration was never tested against a genuinely hand-edited
pushable, since none existed before this patch, but the byte-equality gate
is the same mechanism this file trusts everywhere else for exactly this
distinction) would be left untouched. **Any future patch that replaces an
EXISTING built-in's art or name (not just adds a new id) needs this same
"freeze the old content, compare byte-for-byte, upgrade on exact match"
treatment** — the existing "is the key missing" backfill check silently
doesn't cover this case, and won't for any future revision of existing
factory content either.

### Old cannon/bomb removed; cannon2/bomb2 promoted to the only cannon/bomb (v2.27.2)

v2.27 shipped cannon2/bomb2 as a second, side-by-side option specifically
so the user could compare the reference-sheet art against the original
before committing either way. Direct follow-up: "I like the new bomb and
cannon, please remove the old ones." Rather than just hiding the originals
from the palette (which would have left two live-but-invisible mechanics
maintained forever), this **fully deletes** the original cannon/bomb from
the codebase — same "replace, don't keep a hidden legacy branch" precedent
the old stick-figure preset and the original plate icon already set.
Removed: `CANNON_ORDER` and its four `CANNON_ICON_*` art constants, the
`GEOMETRY_ICONS`/`CANNON_DIRECTIONS`/`GEOMETRY_SWATCH_COLORS` entries for
plain `cannon-ne/se/sw/nw` and `bomb`, `CARRY_CANNON_KIND`/
`CARRY_CANNON_DEF_ID`/`CARRY_BOMB_KIND`/`CARRY_BOMB_DEF_ID` and their
`actorDefs` seeds, their spot in the `restoreProjectSnapshot` backfill
list and the export `constantsSource` lines, and every geometry-string
branch that used to special-case `"cannon"`/`"bomb"` (`selectGeometry`,
`renderObjectSwatches`' swatch-highlight/icon-lookup ternaries,
`convertGrabbedTileToActor`, `resolveActorContact`'s dropped-cannon-fire
branch, `currentPoseFor`). `CANNON_FAMILIES` is now `[CANNON2_ORDER]` — a
one-family array rather than collapsed away entirely, so a future second
cannon can reuse the exact same machinery again. `isBombGeometry`/
`isCarryBombKind` simplified to check only the surviving `BOMB2_GEOMETRY`/
`CARRY_BOMB2_KIND`. **Internal ids were deliberately left alone** —
`cannon2-ne`, `bomb2`, `carrycannon2`, `carrybomb2` keep their "2"-suffixed
identifiers; only `GEOMETRY_LABELS` changed (`cannon2`/`bomb2` now read as
plain "cannon"/"bomb", dropping the "cannon 2"/"bomb 2" comparison-mode
label) — renaming an internal id that's never kid-facing to begin with
would have been pure churn for zero benefit, the same reasoning that kept
`PUSHABLE_KIND` unchanged under the "crate" rename.

**Two places already had old content that needed carrying forward, not
just deleting the code that made it:** the built-in "Dungeon Diving"
sample's own maze-building source directly painted a `cannon-ne` tile
(`board[13][10] = gameplayKey(...)`) — fixed in source, the same way
"Tunnel Trouble"'s maze string was fixed directly for the diggable/trap
migration rather than relying on a runtime migration to catch source
code. And any **already-saved project** could have an old `"cannon-ne"`/
`"bomb"` board cell, or — a level up from that — an already-materialized
carried actor of the old `carrycannon`/`carrybomb` kind sitting in a room
(from a grab that happened before this decision, now dropped or thrown
and just resting there). Both are real backward-compat gaps of the exact
shape `migrateLegacyGroundEffects` already exists to prevent: a deleted
geometry means `gameplayTileAt` returns `undefined` forever for that cell,
and a deleted actorDefs id means `renderActors` crashes reading a
nonexistent def. `migrateLegacyCannonBomb(room)`, called alongside

in one pass per room: rewrites any `cannon-*` board geometry to the

`sw`/`nw` suffixes, so this is a straight string substitution preserving
whatever modifier was stacked on the cell) and any `"bomb"` geometry to
`BOMB2_GEOMETRY`; then walks the room's own `actors` array reassigning any
`defId === "carrycannon"`/`"carrybomb"` to the new `CARRY_CANNON2_DEF_ID`/
`CARRY_BOMB2_DEF_ID` — the actor's own live fields (fuse state, `cannonDir`,
position) are untouched, only its def pointer changes. Verified directly:
a simulated old snapshot with a painted `"cannon-se"` tile, a painted
`"bomb"` tile, and both an already-materialized `carrycannon` and
`carrybomb` actor all migrate to their exact new-geometry/new-defId
equivalents on restore, with zero errors before or after; the migrated
board geometry string was independently confirmed identical to what
painting a cannon2 tile through the real palette produces (same mechanism
already verified firing correctly in the v2.27 testing pass, so this
doesn't need re-proving the physics, only proving the string transform
lands on the exact same value).

### Thrown/dropped objects now bounce off bouncy and Trampoline tiles (v2.28)

Direct request: "I want objects to be able to interact with each other —
if I throw an object at a bouncy tile, it should bounce off it." Before
building anything, this was investigated rather than assumed, since a lot
of what "objects interacting" could mean already existed:

- **Sticky ground and wind/fan force already applied to any physics
  object**, verified directly (not just read) by calling
  `windAccelFor`/`isOnStickyGround`/`frictionMultiplierFor` with a
  synthetic non-player actor — all three are purely positional, with no
  `isPlayer` gate anywhere in them. `stepActor`'s own main branch already
  folds their output into `ax`/`ay` unconditionally for every actor except
  `stationary`/`collectible` temperaments, so a thrown pushable, a dropped
  magnet, or a hazard ball already gets slowed by mud and blown by a fan
  exactly like the player does. Nothing needed changing here.
- **Object-vs-object collision already existed**, and already gives a real
  reaction: `checkActorContacts` runs every frame for every actor, and
  `resolveActorContact`'s very first branch — "neither actor is the
  player" — routes straight to `reflectActorsApart`, an elastic-ish bounce
  (real velocity reflection plus a separation nudge and a sound) that
  fires for any two non-player actors that touch, gated only by a 500ms
  per-pair cooldown. Verified directly: two "wanderer" NPCs given contact
  velocity reflect apart correctly. Pushable-vs-pushable is a distinct,
  *already-correct* case — `shovePushables`'s own continuous
  displacement keeps two crates in flush contact rather than truly
  overlapping, so they push each other rather than bouncing, which is the
  right feel for a shoved crate and was confirmed to still work
  unchanged. Nothing needed changing here either.
- **The one real, confirmed gap**: `resolveAxis`'s own `bouncy` flag
  (`((modifier === "bouncy" || isTrampolineGeom) && actor.isPlayer) ||
  isHazardBall`) — and its exact counterpart in `bounceOffTrampolineObjects`
  for a *dropped Trampoline object* — only ever bounced the player (plus a
  hazard ball's own unconditional always-bounce). The function's own
  pre-existing comment said as much outright: "only for the player; NPCs
  only ever react to geometry, never to modifiers." A thrown/dropped
  pushable, magnet, Trampoline object, bomb2, or cannon2 hitting a
  solid+bouncy tile or a Trampoline tile just stopped dead — confirmed by
  reproducing it directly (a pushable given real velocity into a
  solid+bouncy wall settled at `vx = 0`, no reflection at all) before
  touching any code.

**The fix**: `isPhysicsObject = def && CARRYABLE_KINDS.includes(def.temperament)`
— reusing the existing `CARRYABLE_KINDS` list as-is (it's already exactly
"pushable + every carried-tile kind," the precise set of things a kid can
throw) rather than inventing a second, parallel list that could drift out
of sync. `bouncy` becomes `((modifier === "bouncy" || isTrampolineGeom) &&
(actor.isPlayer || isPhysicsObject)) || isHazardBall`, and every
`bounceSound()` call site in `resolveAxis` (both x-axis branches, both
y-axis branches) and in `bounceOffTrampolineObjects` picked up the same
`|| isPhysicsObject` — a thrown crate caroming off a bouncy wall should be
heard, not just felt, the same reasoning every other reaction in this file
already follows. Landing on a Trampoline tile/object from above, a
physics object also picks up the tile's own enforced
`TRAMPOLINE_LAUNCH_SPEED` minimum for free, since that logic already lived
inside the same `if (bouncy)` block — verified directly: a pushable
dropped onto a Trampoline tile launches at exactly `-900`
(`TRAMPOLINE_LAUNCH_SPEED`), not a weaker scaled-by-impact-speed bounce.

**Deliberately untouched, matching the user's own scoping**: a wandering/
chasing/fleeing/stationary NPC still doesn't bounce off a bouncy tile —
only genuinely thrown/dropped *objects* gained the reaction, characters
didn't, and nothing in the request asked for that. The player-only
"vector kick" polish (`applyBouncyWallKick`, the jump-assist,
`isPlainBouncyHit`) stays exactly player-gated too — those explicitly read
held keys and are about a *kid's* aim/timing, which doesn't apply to an
inanimate thrown object; only the base restitution reflection (and its
sound) widened.

**Testing note, worth keeping in mind for any future bounce-adjacent
work**: a pushable's own friction (`FRICTION_DECEL = 1800`) is strong
enough that a naive test — spawn it some tiles away from a bouncy wall,
give it velocity, wait — will show it stopping from friction alone long
before it ever reaches the wall (at `vx = 250`, it travels only a few
tiles before friction alone zeroes it out). The reliable way to test any
bounce reaction on a non-steering physics object is to teleport it to
within 1px of the target tile (using the actor's own real `w`/`h`, not a
guessed size) immediately before giving it velocity, the same lesson this
doc's own "gotchas" section already has for fan/trampoline testing, now
confirmed to apply here too. Re-ran the existing v2.20.1 "ring of
solid+bouncy tiles, gravity on, 4 seconds of active held-key input"
tunneling regression against the player specifically after this change
(the two `bouncy`-related call sites are shared code) — it still never
warps through.

### The World's Worst Elevator (v2.29)

A sixth built-in sample, and the first one explicitly comedic rather than a
maze or a chase — the request was for "a ridiculous physics contraption,"
built specifically to put the v2.28 object-bounce work (and the whole
bouncy/wind/cannon/bomb toolkit) on display at once, with the game itself
providing zero of the usual structure (no scripted sequence, no "correct
path" enforcement — the reaction table is still the only logic that exists,
same as every other sample). `buildWorstElevatorGame()`/
`drawWorstElevatorIcon()`, registered in `SAMPLE_GAMES` like every other
sample. Two rooms ("The Lobby" and "The Penthouse (Probably)") since this
engine has no vertical camera scroll (`ROWS = 18` is a hard per-room
ceiling) — a "vertical shaft" has to be built as stacked rooms linked by a
door, not one tall room, the same constraint every prior sample's room
count already reflects.

**Every placement in this room is sized against a REAL measured number,
not the constants alone** — this sample generated more corrective
Playwright tracing than any prior one, because hand-deriving where a
bounce or a cannon shot actually lands from the physics constants directly
turned out to be unreliable in three separate, concrete ways below. The
lesson generalizes: for any future sample that chains multiple
launch/bounce mechanics together, trace the actual trajectory before
placing the next piece, not just once but after each placement change,
since a launch mechanic's real landing point routinely differs from the
naive restitution-formula prediction.

**Room 1, "The Lobby"**: a starting ledge (row 4, cols 1-3) over a wide
open wind corridor (rows 5-16, cols 1-9, `none:wind-e` — walkable, not a
floor, so a falling actor passes freely through it while the wind modifier
still pushes it sideways) sitting over a bouncy floor segment (row 17,
cols 0-9, `solid:bouncy`); the rest of row 17 (cols 10-23) is a plain,
non-bouncy floor — a safe walk-back if a bounce undershoots. A platform
(row 14, cols 13-21) carries a switch, a barrier (both colored red, the
switch permanently opens the barrier on contact), an optional bomb toy,
and a cannon2 that fires the final leg up into the room's exit door.

**Bug found and fixed: a straight fall off the start ledge, holding right
the whole way down, landed directly on the intended platform's door
BEFORE ever engaging the wind or bounce** — confirmed via a real
Playwright trace (the exact "hold right the entire descent" pattern a kid
actually plays) that showed the natural fall-drift alone (no wind
involved) carries the player about 5-7 tiles sideways over a ~13-row fall,
which is enough on its own to reach a platform placed too close to the
start. A first fix attempt (sealing the platform with a ceiling directly
above it) was caught as flawed by re-reasoning about the SAME columns the
fall already drifts into, before ever re-testing it — the ceiling would
have just become a new, unintended landing spot rather than closing
anything. The actual fix: the platform's LEFT edge sits at col 13, several
tiles past where the wind corridor even ends (col 9) — confirmed by trace
that a plain drift-fall, with no wind, never reaches that far, so nothing
short-circuits the sequence; only the wind's much stronger, sustained push
gets a falling player that far right.

**A second, subtler placement bug in the same platform: an ascending
actor can only ever hit a platform's UNDERSIDE, never land on its top** —
worth restating here since it cost a full redesign pass. The platform was
first placed at row 11, assuming the bounce's rebound would comfortably
clear it; a real trace of the actual bounce (not the textbook restitution
formula) showed its apex only reaching about row 12.4 — short of row 11 —
so the bounce sailed underneath it every time and the player just fell
back down past the whole platform onto the plain floor at row 17 instead.
Moved to row 14, well below the real measured apex, so the DESCENDING
half of the arc (still carried sideways by the wind) settles onto it with
real margin, instead of needing to clip an exact peak height. The
platform's own left edge (col 13) does double duty here too: it sits past
the bounce's own apex COLUMN (traced at ~col 12.6), so the still-rising
half of the arc never even reaches the platform's footprint to begin
with — only the falling half, past the apex, ever does.

**A bomb, but not in the walkway.** Bomb2 tiles are physical (blocking, per
v2.21) — one dropped directly into the row-13 walkway (the first attempt)
stopped every single player dead until they either jumped it or it blew up
in their face, which is a much stronger interaction than "maybe bombs" was
asking for. Moved one row up (row 12, directly above the walkway) instead —
a kid has to jump up into it on purpose to set it off, a genuine "maybe."
Confirmed via trace what actually happens if they do: `detonateBombAt`
clears any cardinally-solid neighbor, and the platform's own row-14 floor
sits directly below this cell, so the explosion punches a real hole
straight through the platform, dropping it (and the kid, if they're
standing near it) back down to the base floor — the game's own "ridiculous
contraption" physics turned into a discoverable trap, not a bug, and
confirmed fully recoverable (the bounce/wind route back up is untouched by
the hole).

**Room 2, "The Penthouse (Probably)"**: a plain floor, a Trampoline OBJECT
(not a painted bouncy tile — its enforced minimum launch is what makes a
single ~8.7-tile leap possible without a tall drop to build speed from
first), and — the one piece of this room that took the most rework — the
goal.

**Bug found and fixed: a single goal tile, placed where hand-calculation
suggested the bounce would land, missed under multiple different
realistic play patterns, in different ways each time.** A trampoline
bounce with genuinely zero held input drifts sideways NOT AT ALL (straight
up, straight back down the same column — confirmed directly, since there's
no wind in this room to force any drift the way room 1's bounce has). So a
goal reachable at all requires the player to be actively holding a
direction key through the bounce — a real assumption to make explicit, not
an edge case: a kid walking toward a trampoline they've just discovered is
the overwhelmingly likely case. But three different plausible reactions —
holding right forever without ever letting go, letting go the instant the
bounce fires, and letting go too early to even reach the pad at all — were
each traced and produced three genuinely different outcomes: the
"never let go" case drifted the ascent as far as ~col 20 by the time it
reached goal height (the same launch-exemption that lets a bounce/throw
briefly ignore the normal speed cap is what makes this drift so much
larger than a normal walk would); the "let go at the bounce" case crossed
that height back around col 13; and the "let go too early" case never
reached the trampoline at all (friction alone stops it a fraction of a
tile short — not a softlock, just needs one more tap of the key, same as
approaching any obstacle in this engine). A first attempt at four
individually-placed goal tiles, spaced to bracket these three traced
points, still missed the middle ("let go at the bounce") case outright —
its actual crossing column fell into the gap between two of the four
guesses, proving the range is genuinely gappy under this exemption
mechanic, not a smooth curve four sample points could safely bracket.
Fixed with a whole ROW of goal tiles (row 9, cols 7-20) rather than trying
to out-guess the exact landing column — confirmed by re-tracing all three
scenarios again, all three now win. A continuous row of goals also just
suits this level's own "ridiculous contraption" spirit rather than reading
as a workaround.

**No shelf sits directly above the trampoline itself**, for the same
underside-only-blocks-ascent reason room 1's platform placement already
established — anything solid there would cap the bounce short instead of
ever letting the player past it.

Verified with Playwright: the full intended sequence (fall → wind → bounce
→ land on the platform → switch opens the barrier → cannon → exit door →
trampoline → goal) completes end to end under multiple realistic input
patterns (sustained held-right the whole way, and releasing right at the
moment each bounce/launch fires); the bomb toy arms and detonates above
the platform with zero errors; the standard 5-sample regression sweep (now
6 including this one) and a fresh export both run error-free, including a
3-second held-right playthrough of the exported standalone game.

### Switch becomes a real two-state toggle, and can now be hit by a thrown object (v2.31)

Direct feedback: the `switch` tile's art never showed which way it was set
(just a plain cross icon, dimmed when off — the same uniform alpha-dim
every other switch/plate used before `plate` got its own real indicator in
v2.27), and nothing but the player's own footsteps could ever flip one —
"throws something into it" didn't work at all. Three asks bundled
together: a real two-state sprite, a thrown/pushed object being able to
flip it, and confirming it already works as "one channel, many switches
and many controlled things" rather than a door's 1:1 pairing.

**The third ask turned out to already be true — nothing to fix.** A
colored switch has never stored any per-tile state of its own; it flips
`switchChannels[color]`, a single boolean keyed only by COLOR, shared by
every switch, plate, barrier, and gated solid wall painted with that same
color (see `isChannelOn`). Touching any one red switch already turns every
red barrier on and every other red switch's own reading along with it, for
free, just by all of them reading the same shared value at render time —
confirmed directly rather than assumed: a pushable placed on one red
switch's cell flipped the channel, and a SECOND red switch painted
afterward immediately read that already-on state with no extra wiring.
This is also exactly why switch's channel model is NOT like a door's: a
colored door's color means something else entirely (see `wireColoredDoor`
— it pairs exactly two doors together for room-linking, v2.11), never a
shared gate value, so "many things, one channel" was never a question of
switch needing to catch up to anything — it already had the right model
from day one, just no visual proof and no way for an object to trigger it.

**A real two-state sprite**: `SWITCH_OFF_ART`/`SWITCH_ON_ART` replace the
old plain cross icon — a gray bracket housing (the "neutral switch," pixel-
identical in both arrays, never changes) around a red knob on a short dark
lever with a 1px black shadow, mirrored left (off) vs right (on). The two
arrays differ in exactly one 2x2 block of cells (rows 3-4, cols 1-2 vs
5-6) — everything else matches byte-for-byte, which is what makes it read
as "the same switch, lever thrown" rather than two unrelated icons.
`drawGameplayTile`'s switch branch picks between them: `extra.color ?
extra.channelOn : gravityOn()` — a COLORED switch reads its own channel,
same as plate/barrier/button already do; an UNCOLORED switch has no
channel of its own to read (it flips the room's shared gravity toggle
instead, its original v2.2 behavior, untouched), so it shows whichever way
THAT boolean currently reads instead — the same "the switch shows the
state it drives" idea the old alpha-dim comment already had, just a real
position now instead of a dim. Verified by sampling the actual rendered
canvas pixel at the knob's position before and after a touch, for both the
off→on direction and back — the knob measurably moves, not just a color or
alpha change.

**"Throws something into it"**: `checkPhysicsObjectSwitchContacts(actor)`,
a small new function living right next to `checkPlayerTileContacts`
(deliberately NOT folded into it — that function is explicitly player-only
by name and by its own comment, and goal/door/warp/hazard/lethal/bouncy
don't make sense for an inanimate object the way they do for a kid; this
new function reacts to exactly the one thing that was actually asked for).
Called from `stepActor` for any actor whose `actorDefs` temperament is in
`CARRYABLE_KINDS` (pushable, or a grabbed-then-thrown bomb/magnet/cannon/

### Spawner and Barrier join the rotateable family; Barrier renamed "Gate"; Gate's stand-on-closed/fall-through-open behavior confirmed (v2.33)

Direct feedback: "Not all objects appear to be rotateable. That's probably
fine, but we do need that ability for the Spawner and barrier (which
should be renamed 'Gate')." Two bundled asks — rotation for two single-
orientation Objects that had never needed it before, plus a rename — each
needed its own design decision before writing anything, since neither
geometry had any existing notion of "facing" to generalize.

**Two open questions, both put to the user rather than guessed**, since
getting either wrong would have meant redoing real physics/art work:
what should rotating a Spawner actually *do* (there's no existing
direction field to reuse, unlike cannon/fan), and how many distinct
orientations Gate should support given a portcullis looks identical from
either side. Answers: Spawner rotation should give spawned actors a real
**launch direction**, like a gentle cannon (not just a cosmetic facing
marker); Gate should use the full **4-orientation** family (N/E/S/W) for
consistency with cannon2/fan's existing machinery, even knowing two of
the four will render identically to the other two.

**Both generalized onto the exact same "one swatch, four storable
orientations" machinery `CANNON2_ORDER`/`FAN_ORDER` already established** —
`BARRIER_ORDER = ["barrier-n", "barrier-e", "barrier-s", "barrier-w"]` and
`SPAWNER_ORDER = ["spawner-n", ..., "-w"]`, both spread into `GEOMETRIES` in
place of the old bare `"barrier"`/`"spawner"` values. Every call site that
used to check `geometry === "barrier"` or `=== "spawner"` — `isBlockingGeometry`,
`isChannelGateGeometry`, `isColorTaggable`, `selectGeometry`,
`renderObjectSwatches`' icon/selection lookups, `paintGeometryModifierAt`'s
click-to-place/click-to-rotate branches (new ones added, mirroring the
existing cannon2/fan branches exactly — Spawner never carries a channel
color like cannon2, Gate does like fan), `tickSpawners`, the spawner-tile
click-loads-contents guards, and `drawGameplayTile`'s windingUp/loaded/
barrier-slide render checks — was found by grep and switched to
`SPAWNER_ORDER.includes(geometry)`/`BARRIER_ORDER.includes(geometry)`.

**Gate's rotation decides which way it slides open, generalizing its
existing "slides straight up" animation rather than leaving it fixed.**
`BARRIER_DIRECTIONS` (`n: {x:0,y:-1}`, `e: {x:1,y:0}`, etc., the same
cardinal-vector shape `FAN_DIRECTIONS`/`WIND_DIRECTIONS` already use) feeds
`drawGameplayTile`'s barrier branch: the slide-clip translation is now
`dir.x/dir.y * slideFrac * TILE` instead of a hardcoded `-slideFrac` on the
y axis alone. `"n"` (today's only pre-v2.33 look and slide-up behavior) is
unchanged pixel-for-pixel; `BARRIER_ICON_N`'s own art is unchanged too —
`BARRIER_ICON_E/S/W` are generated the same `rotateArt90CW` chain
cannon2/fan's other orientations already use. Since a portcullis is
left-right AND top-bottom symmetric, `n`/`s` (and `e`/`w`) render as the
literal same pixels — acknowledged up front as the cost of reusing the
4-member machinery instead of inventing a narrower 2-member one.

**Spawner's rotation is a genuine behavior change, not just art**:
`SPAWNER_DIRECTIONS` (same cardinal-vector shape) feeds `spawnActorAt`,
which now takes a required `dir` parameter and sets `vx`/`vy` to
`dir.x/y * SPAWNER_LAUNCH_SPEED` (420 — weaker than `CANNON_LAUNCH_SPEED`
(700), reading as "a shove outward" rather than "fired") plus a small
perpendicular jitter, replacing the old undirected small random "pop out"
kick every spawned actor got regardless of orientation. `bouncyCooldown =

in this file sets it — `stepActor`'s `NPC_MAX_SPEED` (160) clamp would
otherwise flatten a 420px/s launch back down to a slow drift within a
single frame; reusing this exemption field here is safe for the identical
reason the throw/cannon-launch comment already gives (a freshly spawned
actor never has steering input of its own during the exemption window).
`SPAWNER_ICON_N` gained a small gold "mouth" notch on its facing edge
specifically because the old art was fully radially symmetric and would
have shown literally no visible difference between orientations otherwise

reads the spawner's own current orientation and passes
`SPAWNER_DIRECTIONS[geometry]` through to `spawnActorAt` on every fire.

**Barrier renamed "Gate" in the palette only** — `GEOMETRY_LABELS.barrier =
"Gate"`, the exact established display-rename mechanism `cannon2`→"cannon"/

### Spawner always fires (concurrency cap removed, launch scatter actually fixed); crates destroyed by lethal; Large Stone, a lethal-immune pushable for building bridges (v2.34)

Direct feedback right after v2.33 shipped: "I'm getting a glitch with the
spawner where it won't produce anything. This effect is more pronounced
if I have more than 1 on the screen... Spawner should always produce the
thing." Investigated rather than taken at face value, since the user's
own guess (a population cap) and the actual felt symptom turned out to be
two different, both-real things.

**The cap was real, and is now gone — but a direct trace proved it was
never silently stuck.** `SPAWNER_MAX_CONCURRENT` (4) made `tickSpawners`
skip its own firing cycle outright once that many of its own content were
still alive. A live trace (two spawners, real wall-clock ticks, 24
seconds) showed population cycling normally the whole time — 2, 4, 6, 8,
back down to 6, repeating — never stuck at a fixed count, let alone 0. So
the cap was doing exactly its v2.19 job ("manage the population"), just a
job the user no longer wants: the ask is for the timer to NEVER skip a
cycle, full stop, not for a higher ceiling. `SPAWNER_MAX_CONCURRENT` is
removed outright (not just raised) — `SPAWN_TTL_MS` (8s) alone now bounds
how long any one spawned actor lives, which was already enough to prevent
true runaway growth even with the cap gone.

**The actual "isn't producing anything" feeling was a real, separate bug
— one v2.33's own launch-direction feature introduced.** A direct position
trace (one spawner, real gravity, 13 seconds) found three separate hazard
balls from the same north-facing spawner settling within ~40px of each
other — visually indistinguishable from a single ball sitting there. Root
cause: v2.33 replaced the old undirected small random "pop out" kick with
a strong, FIXED-direction launch (~420px/s dead straight up for a
north-facing spawner) — gravity brings that straight back down to almost
the exact same column every time, with only a small perpendicular jitter
(±40px/s on `vx`) to separate repeat spawns.

**First fix attempt (bigger velocity jitter) was traced and found not to
work, for a reason specific to this engine's physics model** — worth
keeping in mind for anything else that tries to "spread out" a
non-steering actor's trajectory. `stepActor`'s `applyAxisFriction(actor,
"x", dt, ax)` call runs UNCONDITIONALLY every frame, airborne or not; a
spawned hazard ball has zero self-driven horizontal accel (`ax` stays 0),
so `FRICTION_DECEL` (1800px/s²) eats ANY initial horizontal jitter almost
instantly regardless of its starting magnitude. Confirmed with a direct
frame-by-frame trace: a synthetic actor given `vx = 150` decayed
150→60→30→0 in four ticks (~0.067s), covering barely 5px of real
horizontal travel before friction fully killed it — `bouncyCooldown`'s
"recentlyLaunched" exemption only skips the speed-CAP clamp elsewhere in
`stepActor`, never this friction call. Bumping `SPAWNER_PERPENDICULAR_JITTER`
from the old ±40 to ±150 therefore barely changed the observed spread at
all (confirmed by re-running the same position trace) — the real
constraint is friction, not the jitter's own size.

**The actual fix: jitter the spawn POSITION itself, not just its launch
velocity.** A positional offset is permanent — nothing decays it the way
friction eats a velocity kick. `tickSpawners` now offsets `px`/`py` by
`SPAWNER_POSITION_JITTER` (48px, ~1.5 tiles) along the axis perpendicular
to the spawner's own facing (computed the same `perpX = -dir.y, perpY =
dir.x` 90°-rotation `drawGameplayTile`'s Gate branch already uses) before
ever calling `spawnActorAt` — so successive spawns start from genuinely
different columns (for a vertical-facing spawner) or rows (horizontal-
facing), landing in visibly different spots regardless of how fast
friction consumes their velocity afterward. Re-verified with a fresh
position trace after the fix: raw sampled offsets spanned the expected
~±46px range, and a real multi-spawn run showed a healthy ~60px spread
between landed actors (small-sample variance aside — any given run of 3-4
samples from a uniform distribution won't always hit the full range, but
the mechanism itself is confirmed working, unlike the velocity-only
attempt which was mathematically incapable of producing real spread no
matter how large the constant). `SPAWNER_PERPENDICULAR_JITTER` (the old
velocity-based ±150) is kept at a small value purely for launch-feel
variety frame-to-frame — it is explicitly NOT what separates spawns
anymore, and its own comment says so to head off the exact same mistake
being made twice.

**Crates destroyed by lethal; most other objects deliberately untouched.**
Direct request: "Crates should be destroyed when they touch lethal (lava,
fire, etc). Not all objects should, though." `checkPhysicsObjectLethalContacts(actor)`,
called from `stepActor` scoped to `PUSHABLE_KIND` specifically (not the
whole `CARRYABLE_KINDS` list) — magnet, Trampoline, bomb2, cannon2, and
the new Large Stone are all left completely unaffected by lethal, Large
Stone deliberately so (see below). A wooden crate burning/sinking in
lava is intuitive; a metal magnet or a stone doing the same isn't, so
this is a narrow opt-in list rather than an opt-out one. Mirrors the
same `playActorSound`/`playRecipe("popVanish")`/delayed-`removeActorById`
shape every other "this actor vanishes" reaction in this file already
uses (fleer-pop, collectible-gather, spawner TTL-despawn) — `splat` is
the reused sound (its own family already covers "a life lost," the same
severity tier as meeting a fatal end in lava). A new `actor.destroyed`
flag (distinct from `ttlPopped`, which is specifically spawner-TTL's own
state and could otherwise collide if a crate is ALSO loaded as spawner
content) guards the ~220ms `popVanish` window against re-firing every
frame. **Deliberately scoped to non-blocking lethal only** (`none:lethal`
— the "lava/fire, a pool you fall into" case the request names): a
blocking lethal tile (`solid:lethal`, a spike trap) already stops a crate
at its edge via ordinary collision the same way any wall would, so there's
no cell left to actually overlap and this reaction never fires there — a
real, acknowledged scope boundary, not an oversight; flag it to the user
before trying to extend "destroyed by lethal" to a spike wall a crate is
thrown into.

**Large Stone: a second placeable physics object, immune to lethal by

actor def needs per that list's own established comment.

**Export pipeline**: `LARGE_STONE_KIND`/`LARGE_STONE_DEF_ID`,
`STANDABLE_OBJECT_KINDS`, `SPAWNER_POSITION_JITTER`, and the (now

### Spawner: single-item-at-a-time, and the real root cause of "disappearing into the wall" near an edge (v2.35)

Direct follow-up, right after v2.34: "still having issues with the
spawner (especially when placed on the edge — even with the spawner
aimed away from the edge, items are seemingly disappearing into the wall
or not appearing at all)." Two bundled asks alongside the bug report:
"only spawn one item (whatever is loaded into the spawner will replace
the default)," and "very clearly have the spawned item come out in the
intended direction (still with an animation)."

**Root cause of the edge bug, found before writing any fix**:
`SPAWNER_POSITION_JITTER` (v2.34's own fix for a DIFFERENT problem —
several concurrent spawns visually clumping together) offset the spawn
position along whichever axis is PERPENDICULAR to the spawner's facing —
and "perpendicular to facing" has no relationship at all to which edge of
the ROOM the spawner happens to sit near. A spawner facing east, placed
near the TOP edge, still got jittered vertically (perpendicular to
east/west is north/south) — exactly the "aimed away from the edge" case
the user called out as still broken, because the jitter was never
edge-aware to begin with, it just happened to usually land somewhere
harmless. A big enough roll of that jitter (±48px, ~1.5 tiles) could push
the spawn position above row 0 — off the board entirely, outside anything
`geometryAt` or the camera ever accounts for, so the actor just floats or
falls in open space forever, invisible ("not appearing at all") — or into
a solid border tile if one was painted there ("disappearing into the
wall"). This was a real, confirmed-by-design-reading bug, not a one-off
fluke: the jitter direction was always orthogonal to the one axis a kid
actually reasons about when placing a spawner near a wall.

**The fix for both the bug and the two asks turned out to be the same
change**: since the two jitter mechanisms (`SPAWNER_PERPENDICULAR_JITTER`
on velocity, `SPAWNER_POSITION_JITTER` on position) existed for exactly
one reason — keeping several concurrently-alive spawns from clumping
together — and the new "only spawn one item" ask removes the concurrency
that clumping even requires, both jitters are simply gone, not replaced
with an edge-aware version. `tickSpawners` now tracks a per-spawner
`activeId` (the id of its own currently-alive spawn, or `null`) in
`spawnerRuntime[key]`, and gates actually firing on that slot being
empty: `const occupied = state.activeId != null && actors.some(a => a.id
=== state.activeId);`. A plain `actors.some(...)` scan is enough — it
catches every way a spawned actor can stop existing (TTL despawn, lethal
destruction, a chaser's own pop-on-catch, literally any future reaction
that ever calls `removeActorById`) for free, with no per-reaction
bookkeeping required to keep an explicit "this spawner's slot just
emptied" event in sync. The interval clock keeps counting even while
occupied (not reset or paused), so a spawner whose full `SPAWN_INTERVAL_MS`
has already elapsed by the time its current spawn disappears fires again
on the very next tick rather than making a kid wait out a second full
interval on top. The wind-up "tell" pulse is suppressed while occupied —
nothing is about to fire yet, so pulsing would read as a lie.

**Directional clarity**: `spawnActorAt` is called with the spawner's own
exact cell center (`x * TILE + TILE/2, y * TILE + TILE/2`) — no
perpendicular position offset at all now — and its velocity is exactly
`dir.x * SPAWNER_LAUNCH_SPEED, dir.y * SPAWNER_LAUNCH_SPEED`, with zero
perpendicular component. This went one step further than just removing
the two v2.34 jitters: the OLDER, pre-v2.34 `+60` fixed downward bias a
horizontal launch always carried (there since v2.33, to keep a flat
horizontal toss from looking unnaturally "sliding" in free-roam mode) is
also gone — it's small and was never random, but it's still a
perpendicular component, and "very clearly... in the intended direction"
reads better served by a launch that's exactly on-axis, no caveats, than
by one that's "almost always on-axis except for a deliberate tiny tilt."
Under gravity the bias was redundant anyway (gravity takes over the
instant the object launches); in free-roam it was the one thing left
nudging a horizontal shot off true. **"Still with an animation"** needed
no change — the existing pop-in (`sounds.spawn()` + the `caughtBounceIn`
keyframe recipe, both already in `spawnActorAt`, from v2.19/v2.20) was
never touched by either this or the v2.34 jitter; removing the jitters
only changes where the actor starts and which way it's launched, not
whether it animates in.

**"Whatever is loaded into the spawner will replace the default" was
WRONGLY declared "needs no code change" in this patch's first pass** —
see the immediate v2.35.1 follow-up below for the actual fix. The
re-reading at the time only checked that loaded content (any content)
replaces the hazard-ball DEFAULT, which was true; it missed that loading
a SECOND kind into an already-loaded spawner didn't replace the first,
it joined a random-pick pool alongside it — a real, un-asked-for-fifth
behavior the user had to report back separately before it got fixed.

Verified with Playwright: a spawner run for ~14 real seconds across many
spawn/TTL cycles never has more than 1 of its own spawns alive at once;
a freshly caught east-facing spawn starts exactly on the spawner's own
cell (zero perpendicular position offset) with `vx` strongly positive and
`vy` EXACTLY 0 (confirmed, not just "small"); a spawner placed directly on
the room's TOP edge row, facing east (away from that edge, matching the
user's own repro), fired multiple times over an extended run with zero
spawns ever landing off-board or at a negative coordinate — the exact
scenario that reproduced the original bug; and a fresh export with a
placed spawner runs error-free for several full spawn cycles, plus the
full 5-sample regression sweep and another fresh export (with a switch
and Gate) both still run clean.

### Spawner content is a single replaceable slot, not a random pool (v2.35.1)

Direct, terse follow-up right after v2.35 shipped: "Spawner still trying
to do multiple objects." The v2.35 concurrency fix (at most one spawn
alive at a time) was re-verified and still holds — that part was never
the issue. The actual remaining gap was in `spawnerContents` itself,
untouched by v2.35: since v2.19, loading an actor/object onto an existing
spawner tile APPENDED it to a list (`toggleSpawnerContent`'s `list.push`),
and `tickSpawners` picked randomly among everything in that list on each
fire (`contents[Math.floor(Math.random() * contents.length)]`). Loading a
second kind into an already-loaded spawner never replaced the first —
it joined it, and from then on the spawner alternated between different
kinds at random. That's "still trying to do multiple objects" exactly:
not a concurrency bug (already fixed), but the spawner's own *content*
model still being a multi-item pool when the ask was for a single
replaceable slot.

**Fix: `spawnerContents[key]` is now a single `defId` string (or absent,
meaning the hazard-ball default), not an array.** `toggleSpawnerContent`
simplifies to a plain compare-and-swap: clicking a kind that's already
the spawner's own loaded content clears it back to the default; clicking
any OTHER kind replaces whatever was loaded, full stop — no more "several
loaded, picked randomly," which was the literal behavior the user was
describing wanting gone. `tickSpawners`'s own `defId` selection collapses
to `spawnerContents[key] || HAZARD_BALL_DEF_ID`. The render-time `loaded`
flag (whether a spawner tile shows as carrying something, read by
`drawGameplayTile`) changes from `!!(contents && contents.length)` to the
simpler `!!spawnerContents[spawnerKey]` — same meaning, now matching the
simpler shape.

**Backward compat**: a pre-v2.35.1 save can still have the old array
shape (`["wandererA", "wandererB"]`) under a spawner's key.
`restoreProjectSnapshot` now walks `spawnerContents` right after loading
it and collapses any `Array.isArray` entry down to its first element (an
empty array is treated as "nothing loaded" and deleted) — the same "keep
the primary thing, drop the rest" call `migrateLegacyGroundEffects`
already made for a diggable/trap tile's secondary modifier, applied here
to a spawner's secondary loaded kinds instead. No export-pipeline change
needed: `spawnerContents` is already shipped wholesale in `gameData`, and
`tickSpawners`/`toggleSpawnerContent` are shared via `runtimeFunctions`
from earlier patches, so the single-slot behavior applies automatically
to an exported game the moment this code lands.

Verified with Playwright: loading a second kind into an already-loaded
spawner replaces the first (confirmed by id, not just by count) rather
than joining a pool; the spawner then only ever produces that one
replaced-in kind over a long run, never a mix with the one it replaced;
clicking the currently-loaded kind again clears it back to the default;
a simulated pre-v2.35.1 snapshot with an old two-element array under a
spawner's key migrates to a single string (its first element), and a
simulated old EMPTY array migrates to "nothing loaded" rather than an
empty array; the previously-verified single-active-item concurrency
behavior still holds unchanged; and a fresh export with a spawner whose
content was loaded-then-replaced runs error-free across several real
spawn cycles, alongside the full 5-sample regression sweep and another
fresh switch+Gate export.

### A spawner facing a wall was launching actors into a runaway off-board flight, forever (v2.35.2)

Direct bug report, with an actual uploaded project to investigate: "the
spawner is not working properly in the upper left corner of the screen.
It's been loaded with a crate and nothing is happening. The other spawner
is working properly." Investigated against the real project file rather
than a guessed repro — loaded it into the live app, traced the exact
actors it contained, and found the project had TWO north-facing spawners
sitting directly on the room's own top row (row 0, one at the literal
upper-left corner (0,0), one at (30,0)) alongside two others placed with
open space around them ((47,1), (20,12)) — and the save file already
contained pushable actors from these two row-0 spawners sitting at
absurd y positions (`-1113238`, `-11030`) — a strong first clue that
something had already gone wrong once before.

**Confirmed with a frame-by-frame physics trace, not just read from the
code**: a pushable spawned (or resting) with its position fully
overlapping its own spawner's tile — which is physical/blocking, per
v2.21 — gets ping-ponged a full tile further away EVERY SINGLE FRAME,
forever. The trace showed exactly why: the moment gravity nudges `vy`
to even a small positive value, `resolveAxis`'s "landed on a floor from
above" branch (`actor.vy > 0`) fires against whatever row the actor is
CURRENTLY sitting in — but if that row is the spawner's own cell (which
the actor has never actually cleared) rather than a genuine floor
approached from above, the resolution shoves it to `cy*TILE - actor.h`,
i.e. a full tile further away. For a spawner with open space in its
facing direction, the initial launch (`SPAWNER_LAUNCH_SPEED`) carries the
actor several tiles clear of its own cell within the first ~17 frames,
well before gravity ever revisits that position, so this never triggers.
For a spawner on the room's own edge with nowhere to launch into (row 0
facing north: the actor is ~5px from the room's implicit top boundary,
which swallows the entire launch in a single frame), the actor can never
separate from its own cell at all — it immediately starts ping-ponging
between "landed on my own spawner tile" and "hit the boundary one cell
further out," gaining a full tile of displacement each frame with `vy`
pinned back to 0 every single time (confirmed directly: `vy` read exactly
`0` at every sampled frame while `y` diverged by ~1900px/s, climbing to
nearly -20000 within 10 seconds — it never even LOOKS like it's falling
or rising, just silently teleporting away a tile at a time). This is a
genuine runaway, not a cosmetic glitch: the "crate" the user loaded was
never visibly missing, it was flying off-board in a single frame, every
time, forever — reading as "nothing is happening" from the kid's seat.

**Fix: a spawner checks whether its own facing direction is actually
open before firing, and skips the cycle (with a one-time log message)
if it isn't** — `isCellBlocking(x + dir.x, y + dir.y, { isPlayer: false
})`, checked once per tick right after the clock updates, before the
existing single-item-occupancy gate. `isCellBlocking` (not the plainer
`isBlockingGeometry`) was chosen specifically so a spawner facing a
CURRENTLY-OPEN Gate/channel-gated wall is correctly treated as clear —
only a genuinely blocking cell (a solid wall, the room's own edge with no
wrap, a closed Gate) stops it from firing. Deliberately fixed at the
spawner's own call site, not inside `resolveAxis` itself: that collision
function is shared by every actor's every tile interaction and already
carries its own delicate tunneling-fix history (see its v2.20.1
comments) — correctly generalizing "an actor fully embedded in a solid
tile, not approaching from a clean direction" for every possible caller
is a much bigger, riskier change than preventing the ONE specific setup
(a spawner with nothing to launch into) that was actually reported.
`state.warnedBlocked` (new, transient, reset the same way `activeId`
already is) gates the log message to once per spawner per session,
rather than spamming it every tick the spawner stays misconfigured —
`log("A spawner can't launch anything — the way it's facing is blocked.
Try rotating it.")` tells the kid exactly what to do about it (the
existing click-to-rotate gesture already on every spawner).

**Deliberately NOT a retroactive data fix.** The two pushables already
sitting at `-1113238`/`-11030` in the uploaded project are leftover
corruption from a prior, pre-fix session — `resetActorsToSpawn` still
resets them to THEIR OWN saved `spawnX`/`spawnY` on every Play entry
(confirmed: reloading the exact uploaded file and entering Play still
shows them drift away from whatever stale position was last saved,
exactly as before). This patch stops the SPAWNER from ever minting a
new actor into this situation again; it does not hunt down and repair
already-corrupted actors sitting in old save data. Flagged directly to
the user: rotating the (0,0) and (30,0) spawners so they face a direction
with open space (any of east/south/west, which all have room in this
particular layout) is what actually lets them produce content; the two
already-drifted pushables are harmless, permanently off-screen clutter
that can be ignored or, if the kid wants them gone, selected and deleted
like any other actor once the room is rebuilt facing the right way.

Verified with Playwright: loaded the exact uploaded project and confirmed
neither row-0 spawner mints any new actor over a 4-second run (ids
unchanged before/after) while the two open-space spawners keep firing
normally; a freshly-placed spawner on row 0 (default north-facing)
produces zero actors ever and logs the warning exactly once; rotating
that same spawner to face east (open space, same row) makes it fire
normally, with the spawned actor settling at a sane on-board position
rather than flying away; and the full 5-sample regression sweep plus a
fresh export both run error-free.

Direct follow-up, with the user testing the v2.35.2 fix live: rotated the

`isCellBlocking` agreed), loaded it with a crate, and reported "nothing
happens." Investigated with the same uploaded project rather than assumed
fixed, since "I rotated it and it still doesn't work" directly contradicts

spawner's content was ALREADY `"pushable"` in the save from before (the
user had loaded a crate into it in an earlier session) — so clicking the

actually ran `toggleSpawnerContent`'s own click-to-clear path (v2.35.1's

**Second, the actual bug, confirmed by a fresh frame-by-frame trace**: even
with the spawner correctly identified as facing OPEN space (south) and
correctly firing (the v2.35.2 `launchBlocked` check passed, a hazard ball
was minted), the newly spawned actor STILL ran away off the top of the

blocking (v2.21), and `resolveAxis`'s per-axis collision scan resolves

correctly prevents the specific case it was built for (a spawner with

closely-related case (a spawner WITH open space, whose newly-spawned

the underlying fragility is the same one `resolveAxis`'s v2.20.1 comment

gate open — this isn't an edge case, it's close to the expected way a kid
discovers what a switch does. `checkPhysicsObjectSwitchContacts` (the
v2.31 "throws something into it" widening) has the exact same bug for a
crate or Large Stone left resting on a switch after a push or throw.

**Fix: the switch reaction became edge-triggered instead of overlap-
triggered.** `switchTouchedCells` (actor id → array of `"cx,cy"` switch-
cell keys that actor was overlapping as of the LAST call) is checked
before calling `triggerFlip`: a cell already in that actor's previous set
is skipped, a cell that's newly appeared in the overlap list fires.
Stepping off a switch (even briefly) clears it from the set, so a
deliberate second visit still correctly re-toggles the channel — only
*sustained, continuous* contact is now a no-op after the first frame,
which is what "activate when hit" always meant. Both call sites
(`checkPlayerTileContacts`, `checkPhysicsObjectSwitchContacts`) got the
same treatment; the former writes `switchTouchedCells[player.id]` at
every exit point, including its two early `return`s (door/warp), so a
mid-frame room change never leaves stale bookkeeping behind.
`flipCooldown` itself is untouched — it still does its original, narrower
job of preventing two triggers within the same instant of contact; this
is a second, independent guard layered on top for the "still touching
it" case `flipCooldown` was never meant to cover.

**Deliberately scoped to Switch only, not Button/Plate.** Button and
Plate are ALREADY correctly momentary by design (channel is live only
during overlap/push-contact, recomputed fresh every tick via
`updatePressurePlates`/`resolveAxis`) — there is no analogous bug there,
since "goes back off when you stop touching it" is their entire intended
behavior, not a glitch to fix.

**Export pipeline**: `switchTouchedCells = {}` added alongside the live
editor's declaration (and `clearTransientRuntimeState`'s reset list), plus
the exported template's own matching `let switchTouchedCells = {};` and
`restartStandaloneGame`'s reset line — the same "declared here by hand,
never persisted" treatment every other transient per-tick map
(`plateChannelsActive`, `pushButtonChannelsActive`, ...) already gets.
`checkPlayerTileContacts`/`checkPhysicsObjectSwitchContacts` were already
shared into the export via `runtimeFunctions` from earlier patches, so
the fixed logic carries over automatically.

Verified with Playwright: a player resting continuously on a colored
switch for 1.5s keeps the channel ON the whole time (previously flipped
back OFF partway through); walking fully across and past the switch, then
deliberately walking back through it a second time, correctly toggles the
channel OFF again (confirming edge-detection doesn't accidentally make
the switch "stick" one-way); the uploaded project's own Button→Gate
puzzle re-traced and confirmed unaffected (still correctly momentary); the
full 5-sample regression sweep (The Monster's Den's own switch/Gate
puzzle included) and a fresh export with a colored switch+Gate, played for
1.5s past `flipCooldown` while resting on the switch, both run
error-free.

### Actor shape

A live actor (in the `actors` array) looks like:

```js
{
  id, defId, x, y, w, h,           // AABB in px; w/h = ACTOR_SIZE = TILE - 2*ACTOR_INSET
  spawnX, spawnY,                   // where "reset to start" / Play-restart snaps it back to
  vx, vy, grounded, isPlayer, facingDir,
  impactMag, impactWobbleT, impactAxis, jumpCrouch, flashTimer,
  hazardCooldown, goalCooldown, flipCooldown, bouncyCooldown, doorCooldown,
  cannonCooldown, warpCooldown,
  // optional, spawner-created actors only:
  spawnerKey, spawnBornAt, ttlPopped,
  // optional, surface-dependent:
  onWhooshSurface,
  // v2.21, grab/carry/drop/throw (see its own section below):
  carried,             // true while glued to the player, no physics of its own
  carrying,            // player only: the id of whatever it's currently carrying, or null
  fuseArmed,           // carrybomb only: has this specific instance's fuse EVER been lit
  fuseRemainingMs,     // carrybomb only: ms left on the fuse — ticks down only while not held
  fuseTimerId,         // carrybomb only: the live setTimeout handle, or null while held/paused
  fuseStartedAt,       // carrybomb only: performance.now() when the current tick segment began
  cannonDir,           // carrycannon only: "ne"/"se"/"sw"/"nw", copied from the tile at grab time
}
```

`actorDefs[defId]` holds the static definition (`temperament`, `art`/
`poses`, `name`, `voice`, ...) — the live actor is the physics instance,
the def is the "what kind of thing is this."

### Rooms and the "hot globals" pattern

A room object holds: `board, backgroundBoard, colorBoard, groundSkinBoard,
groundSkinRotationBoard, actors, startPos, gravityEnabled, wrapHEnabled,
wrapVEnabled, cameraMode, editorPanCol`.

**Only one room is ever "hot"** — its fields are copied onto matching
top-level `let` globals (`board`, `actors`, `gravityEnabled`, etc.) by
`activateRoom(roomId)`, which also writes the *outgoing* room's globals
back onto its own object first. Every physics/render/paint function reads
these top-level globals directly, never `rooms[i].board` — that's exactly
what makes room-switching (doors, warps) cheap. `gravityEnabled` etc.
**default to `false`/`"fixed"` for a brand-new room** (`createEmptyRoom`) —
don't assume gravity is on just because other rooms/samples have it on.

**The four places new persistent state must be wired in**, every time,
together, or it will silently desync (this bit real time during v2.19's
spawner work):

1. **`activateRoom`** — copy the field both directions (outgoing room ←
   global, global ← incoming room) if it's a *per-room* hot global.
2. **`snapshotCurrentRoomState`** — the "outgoing" half of #1, used
   whenever the room isn't switching but its live state still needs
   flushing back onto the room object before a snapshot is taken.
3. **`captureProjectSnapshot` / `restoreProjectSnapshot`** — the one
   canonical whole-project shape shared by undo/redo, autosave, JSON
   save/load, and New Project. `restoreProjectSnapshot` must also
   backward-compat-default the field for an older snapshot that predates
   it (see the `spawnerContents ? ... : {}` pattern).
4. **`enterPlayMode`'s `buildSnapshot`, `restartPlaySessionFromSnapshot`,
   `exitToBuildMode`** — the separate Play-session snapshot/restore path
   (deliberately distinct from #3 — Play mutates live state directly and
   restores from a frozen pre-Play copy rather than diffing).
5. **`exportStandaloneGame`**'s `gameData` object, if the field needs to
   survive into an exported game at all.

A *project-global* (not per-room) piece of state only needs #3 and #5.

### Physics engine

`stepActor(actor, dt, player)` is the single per-actor physics step, called
once per actor per frame from `tick(dt)`. Shape, roughly:

1. Compute continuous forces as **acceleration**, not direct velocity:
   `windAccelFor`, `radialForceAccelFor` (magnet/gravity well),
   `fanAccelFor`. These fold into `ax`/`ay` alongside player input /
   NPC steering (`steeringAccelFor`) — **never add a raw velocity**, or
   `applyAxisFriction` will just eat it back to zero the instant no key is
   held (the "conveyor doesn't carry a standing player" bug shape). v2.20:
   both the player-input and steering contributions (not wind/fan/radial)
   are additionally scaled by `stickyMoveMult` (`STICKY_MOVE_MULT` while
   `isOnStickyGround(actor)`, else 1) — sticky ground damps a kid's OWN
   push, not a conveyor or fan blowing through it.
2. `applyAxisFriction(actor, axis, dt, accelInput)` integrates that axis:
   adds `accelInput*dt` if nonzero, otherwise decays toward 0 by
   `FRICTION_DECEL * frictionMultiplierFor(actor) * dt`. `frictionMultiplierFor`
   also returns `STICKY_FRICTION_MULT` (high — can't coast to a stop) while
   `isOnStickyGround`, alongside its existing `SLIPPERY_FRICTION_MULT` (low)
   case. The velocity cap itself (`cap`/`effectiveCap` in `stepActor`) is
   also scaled down by `stickyMoveMult` — damping acceleration alone barely
   reads as "slower" once `MOVE_ACCEL` reaches the ordinary cap within a
   fraction of a second; capping the ceiling is what makes it read as mud
   the whole time you're in it.
3. If `gravityOn()` (per-room `gravityEnabled`): normal platformer branch —
   jump, gravity accumulates into `vy` directly (not through `ay`/friction),
   clamped to `MAX_FALL`. If **`isStuckToSticky(actor)`** is true (touching
   a `sticky` solid tile via its LEFT, RIGHT, or TOP side — **not the
   bottom**, see the gotcha below) AND the actor hasn't used up its
   `STICKY_CLING_MS` window yet, it's fully frozen — `vx`/`vy` both hard to
   0, no movement input of any kind contributes (see the input section
   above `stepActor`'s gravity branch). **v2.20.3: sticky is a timed CLING,
   not indefinite climbing.** The original v2.19/v2.20 shape let free-roam
   input move the actor in any direction for as long as contact held, which
   in practice meant holding a direction key let a kid scale a sticky wall
   forever — direct feedback called this out explicitly ("you certainly
   shouldn't be able to climb walls that are sticky"). `actor.stickyClingT`
   counts up only while `isStuckToSticky` is true and resets to 0 the
   instant contact actually breaks, so a fresh touch (a different wall, or
   the same one after fully releasing) gets its own full cling. Once
   `stickyClingT` exceeds `STICKY_CLING_MS` — whether or not contact is
   still being made — the existing `stickyReleaseT` ramp (0 →
   `STICKY_RELEASE_MS`) takes over automatically, scaling gravity back in
   gradually ("slowly letting go") instead of slamming to full weight the
   very next frame; an actor that's never touched sticky keeps
   `stickyReleaseT` at its init value of `STICKY_RELEASE_MS` (= "already
   fully released"), so this is a no-op for everything else.
4. If gravity is off: free-roam 2D movement, single combined speed cap
   (also sticky-scaled, same as #2).
5. `resolveAxis(actor, axis, dt)` resolves AABB-vs-tile collision per axis
   separately (not swept), handling solid blocking, `bouncy` reflection
   (restitution scales with impact velocity — **a rebound can never exceed
   the fall height it came from**, restitution² × drop height is the rough
   rebound-height formula), the Trampoline geometry object's own stronger,
   minimum-enforced bounce (`isTrampolineGeom`, `TRAMPOLINE_RESTITUTION`/
   `TRAMPOLINE_LAUNCH_SPEED`), hazard/lethal damage, diggable erosion, and
   hazard-ball's always-bounce. **`return`s immediately once it resolves one
   blocking cell** (v2.20.1 fix) — see the dedicated gotcha below on why
   looping over every cell the AABB overlaps used to let a bounce tunnel a
   player straight through a multi-tile-wide bouncy floor/wall.
6. `resolveActorContact(moverActor, otherActor)` handles actor-vs-actor
   contact (player vs. NPC): temperament branches (`stationary`/
   `wanderer`/`chaser`/`fleer`/`collectible`/`PUSHABLE_KIND`/
   `HAZARD_BALL_KIND`) each get their own fixed reaction. This is the
   reaction table the "no scripting" principle refers to — it's a closed
   `if/else if` chain, not data-driven, and that's intentional.

Key constants worth knowing before tuning anything: `GRAVITY = 1450`,
`MAX_FALL = 750`, `MOVE_ACCEL = 2200`, `WIND_FORCE = 1000` (a plain wind/
conveyor tile's fixed force, deliberately *less* than gravity — it can slow
a fall, never reverse it, "a kid can still fight against it"),
`BOUNCE_RESTITUTION = 0.82`, `TRAMPOLINE_RESTITUTION = 0.97`/
`TRAMPOLINE_LAUNCH_SPEED = 900` (the Trampoline object, stronger than plain
`bouncy` on purpose), `STICKY_MOVE_MULT = 0.32`/`STICKY_FRICTION_MULT = 5`/
`STICKY_RELEASE_MS = 500` (sticky ground's own slow-down/no-coast/gradual-
release numbers), `STICKY_CLING_MS = 1000` (how long a sticky WALL freezes
an actor before the release ramp kicks in on its own — see below).

### Bouncy walls get real vector character (v2.21)

Direct feedback: a plain `solid:bouncy` tile had "no vector quality." A
wall bounce (an x-axis `resolveAxis` collision) only ever reflected
whatever horizontal speed the player already had — jumping straight up
between two close bouncy walls carries almost no `vx`, so the reflection
barely moved you at all. The reported use case: two vertical rows of
bouncy tiles a few columns apart, jump up into one and expect to carom
sideways-with-a-bit-of-lift into the other, bounce off that one the same
way, repeat. A floor/ceiling bounce (y-axis) never had this problem —
gravity plus restitution already gives it real vertical energy on its
own — so this is scoped specifically to the x-axis case, and specifically
to the plain `bouncy` modifier (not Trampoline, not a hazard ball — see
below).

`applyBouncyWallKick(actor, dir, jumpHeld)`, called from `resolveAxis`
right after its existing `-vx * restitution` reflection on both x-axis
branches, is the whole mechanic:
- **A minimum kick away from the wall** (`BOUNCY_WALL_KICK = 320`,
  overriding the reflection if it's weaker) — the direct fix for "jumped
  straight up, got barely reflected." `dir` is +1/-1, already matching the
  sign the reflection just produced, so this only ever *strengthens* a weak
  bounce, never fights a strong one.
- **A slight upward lift** (`actor.vy -= BOUNCY_WALL_LIFT` — `160`) on
  every such bounce — the "diagonal carom" quality that was missing;
  without this a wall bounce reads as a flat horizontal ping, with it the
  trajectory arcs.
- **`actor.bouncyCooldown = 350`**, the exact `recentlyLaunched` exemption
  `triggerBouncyLaunch`'s own real launch already uses — `BOUNCY_WALL_KICK`
  (320) is well above `MAX_SPEED` (220), so without this the ordinary
  horizontal speed-cap clamp would flatten the kick right back down within
  a single frame, same reasoning as every other "real impulse" in this file
  (cannon, bomb-blast, throw).
- **Holding jump at the moment of the bounce adds a further `JUMP_VELOCITY`
  on top of whatever the passive kick/lift already produced** (additive,
  not a clamp — "get more lift and better aim control" was the ask, and a
  clamp would sometimes *reduce* an already-strong bounce instead of
  boosting it). The same jump-key set `stepActor`'s own `wantsJump` reads
  (`" "`/`ArrowUp`/`w`/`W`) is checked directly inside `resolveAxis` via the
  shared `keys` global — no new input plumbing needed. This never
  double-fires with an ordinary ground jump: `actor.grounded` stays `false`
  through any bouncy-tile bounce (only the non-bouncy floor-landing branch
  ever sets it), so `stepActor`'s own `wantsJump && actor.grounded` gate
  can't also trigger in the same frame.
- **The same jump-assist applies to a plain bouncy FLOOR bounce too**
  (`actor.vy += JUMP_VELOCITY` right after its own restitution reflection,
  same additive shape) — "jump off the bouncy tiles for more lift" reads
  as a general bounce-pump ask, not wall-specific. Deliberately gated to
  `modifier === "bouncy"` only, not Trampoline — Trampoline already has its
  own enforced minimum launch just above this in the same branch
  (`TRAMPOLINE_LAUNCH_SPEED`), and stacking a second boost on top would
  blur the two mechanics' distinct identities (see the Non-negotiable
  principles section on why `spring` was removed for exactly this "two
  tunings of the same bounce" reason).
- **Gravity-mode only** (`gravityOn()` gates the whole thing) — free-roam's
  own single combined x/y speed cap wasn't audited against this feature,
  and the report was specifically framed as "with gravity on." Flag it to
  the user before extending this to free-roam.
- **Hazard-ball and Trampoline wall/floor contact is completely
  unaffected** — `isPlainBouncyHit` (the gating flag) requires
  `modifier === "bouncy"` specifically, so `isTrampolineGeom` bounces and
  `isHazardBall`'s always-bounce keep their exact pre-existing plain-
  restitution behavior on every axis.

**Continued opposing input still fights the kick, on purpose, same as
every other impulse in this codebase** — `bouncyCooldown` only exempts the
*speed-cap clamp*, it doesn't stop held-direction acceleration from still
being integrated (that's the literal mechanism, and reusing it here is
deliberate rather than inventing a second one). A kid holding the
direction that caused the bounce will keep fighting it exactly like
holding into a cannon shot or a bomb blast already does; releasing (or
reversing) the key right at the bounce is what lets the kick actually
carry through, same intuitive feel as every other launch in the game.

Verified with Playwright: a near-zero-`vx` approach into a bouncy wall now
produces a real, code-verified kick (~320) plus lift (~-135 `vy`), and
displaces the player a real distance once input stops fighting it; holding
jump at the bounce moment adds a further large boost (`vy` well past
-1000, vs. ~-135 passive); the same jump-assist on a plain bouncy floor
roughly doubles peak bounce height over the passive case; a Trampoline
tile's side contact is confirmed unaffected (no `bouncyCooldown` set);
re-ran the existing "ring of solid+bouncy tiles, gravity on, 4 seconds of
active held-key input including jump-mashing" tunneling regression (the
v2.20.1 fix's own test) and it still never warps through; confirmed
working identically in an exported standalone game.

### Pushables (v2.20.3)

`shovePushables(actor, axis)` is the actor-vs-actor collision path for
`PUSHABLE_KIND` — a continuous shove every frame contact holds (see its own
comment for why that's a separate mechanism from the discrete bump-and-
cooldown reaction `resolveActorContact` gives every other actor pair). It
attempts to displace the pushable by however far the mover just moved; if
that displacement would be blocked, the MOVER stops at the pushable's edge
instead (or, for a vertical mover with `vy > 0`, comes to rest exactly on
top of it). Two bugs fixed here, both direct feedback:

1. **Landing on a pushable never set `actor.grounded`** — only
   `resolveAxis`'s own tile-landing branch did that, so jump input was
   silently ignored for as long as a kid stood on a pushable. The `vy > 0`
   branch now sets `actor.grounded = true` explicitly when the mover comes
   to rest on top, the same as landing on a tile would.
2. **Two pushables could overlap or pass straight through each other** —
   `shovePushables` used to bail out entirely whenever the MOVER was itself
   a pushable ("no chaining pushable-into-pushable, for now"). It now runs
   for every actor regardless of kind, and its `blocked()` check consults a
   new sibling helper, `actorBlockedByOtherPushables(candidate, selfId,
   moverId)` (the actor-vs-actor analog of `actorBlockedByTiles`), in
   addition to tiles. This is what makes stacking work: a falling pushable
   landing on a resting one hits the same "displacement blocked, come to
   rest on top" path a mover already used for a single pushable resting on
   a tile — no chain-push physics needed, since `PUSHABLE_KIND`'s "zero
   self-driven accel" means a pushable essentially never carries its own
   horizontal velocity beyond an occasional bounce, so true multi-block
   chain-pushing (A pushes B pushes C sideways) isn't really exercised by
   this — it's a low-risk generalization, not a full physics simulation.

### Grab / carry / drop / throw (v2.21)

The first player-invoked verb in the whole project — every other reaction so
far happens automatically from contact or movement, never from a kid
pressing a dedicated key. Still not scripting: it's one more fixed reaction
(closed to a specific set of object kinds, no authoring), just triggered by
a keypress instead of a collision. "E" is the key (unchanged from the
validated prototype, `grab-carry-test.html`).

**State machine**, driven by a pair of `keydown`/`keyup` listeners (not
per-frame polling like movement — press/release edges matter here):
not carrying + `keydown` → `tryGrabNearestCarryable` attaches the nearest
carryable actor or tile within `GRAB_KEY_RANGE`; carrying + `keydown` →
starts a charge (`grabKeyDownAt = performance.now()`); carrying + `keyup` →
`heldMs < THROW_TAP_MS` drops at the feet with zero velocity, otherwise
`throwCarriedObject` fires with speed scaled by how long it was held
(capped at `THROW_CHARGE_MAX_MS`) in `player.facingDir`'s direction plus a
fixed `THROW_UPWARD_SPEED` arc. A carried actor is fully exempted from
physics — `stepActor` early-returns for any `actor.carried` — and instead
gets its `x`/`y` set directly, every frame, by `tick()`'s own carry-follow
step (glued just above the player's head). `renderActors` adds a
charge-shake (scaling with how long the key's been held) as the physical
cue that holding the key is doing something — the same principle as the
spawner's own wind-up pulse; without it the charge-to-throw relationship is
undiscoverable, not just less polished.

**What's carryable**: `PUSHABLE_KIND` (already an ordinary actor, the "does
carry-and-drop alone feel good" baseline) plus four kinds that normally
live as painted tiles — bomb, magnet, cannon, trampoline. Grabbing one of
these picks the *one cell* bodily up off the board (`board[gy][gx] = null`)
and turns it into a real actor of a matching `CARRY_*_KIND`/`CARRY_*_DEF_ID`
(`convertGrabbedTileToActor`/`placeCarryableActor`) — same shape as
`HAZARD_BALL_KIND`, never placed by hand, only ever created this way. Once
turned into an actor it stays one forever, even after being dropped or
thrown — never repainted back onto the board. **Deliberate design choice,
not a migration**: the tile itself is completely unchanged (every existing/
sample-game board full of painted bombs, magnets, cannons, trampolines
keeps working exactly as before) and there's no second, differently-named
palette entry for "the carryable version" — the same swatch a kid already
knows just becomes grabbable once placed. This was an explicit user call
("let's keep the interface simple, players will investigate and discover
on their own") over either a bigger tile-to-actor migration or a parallel
object category.

**Each kind reuses its tile's own mechanism, never a reimplementation**:
- **Bomb**: **held is safe; the tile's own touch-arm hazard is untouched.**
  Bumping into a live bomb TILE still lights it on mere physical contact,
  same landmine feel as always (`triggerBombArm`, fired from `resolveAxis`
  — see "Physical objects vs. fixtures" below), with the same flicker
  warning it's always had (`drawGameplayTile`'s `extra.armed` alpha-blink,
  driven by `bombArmed[key]`). Grabbing it is the one thing that changed
  twice now: `pauseBombFuseIfTicking(obj)` / `startOrResumeBombFuse(obj)`
  are the whole carry-side mechanic — `obj.fuseRemainingMs` (defaults to
  `BOMB_FUSE_MS`) tracks how much fuse is left, `obj.fuseTimerId` is the
  live `setTimeout` handle while actually ticking (`null` while held/
  paused), `obj.fuseStartedAt` is when the current running segment began so
  a pause can compute exact elapsed time to subtract. `attachCarryable`
  calls `pauseBombFuseIfTicking` for a bomb; `dropCarriedObject`/
  `throwCarriedObject` both call `startOrResumeBombFuse` once it's no
  longer held. **Replaced an earlier v2.21 shape** where grabbing armed a
  fresh real-time fuse immediately and it kept ticking whether held or not
  ("explodes in your hands" regardless) — direct feedback was that this
  didn't read as carryable, just as a slightly-delayed explosion.
  **A second round of feedback then caught a gap in that first fix**: the
  first pass reset ANY grab to a fresh full `BOMB_FUSE_MS`, discarding
  however far a tile-side touch-arm had already ticked down — so grabbing
  an already-lit bomb felt like it un-lit the fuse rather than pausing it.
  `bombArmed[key]` is now `{ armedAt, timerId }`, not just a flag:
  `convertGrabbedTileToActor`, on grabbing a bomb, checks it, computes the
  exact remaining time (`BOMB_FUSE_MS - (now - armedAt)`), calls
  `cancelBombArm(key)` (a new helper — `clearTimeout` the tile-side timer
  *then* delete the entry, so it can't also fire later against whatever's
  since been painted over that cell; the four single-cell repaint/erase
  sites that used to do a bare `delete bombArmed[key]` now call this too,
  for the same reason) to cancel the original tile timer, and seeds the new
  actor's `fuseRemainingMs`/`fuseArmed` from that instead of a fresh
  `BOMB_FUSE_MS` — so "grabbed mid-countdown" genuinely means *paused*
  mid-countdown, picking up exactly where the tile left off once dropped or
  thrown again. A bomb grabbed before ever being touched still starts at a
  full, unarmed `BOMB_FUSE_MS`, same as before. `detonateCarriedBombAt(roomId,
  actorId)` finds the actor by id in whichever room it's still in (it's
  simply abandoned there, detonating unseen, if the player's since left
  that room), auto-drops it from `player.carrying` first if it's still held
  (only possible if its `setTimeout` fired in the same tick a grab was
  about to pause it — JS's single-threaded execution makes this a
  theoretical, not practical, case; kept as a defensive no-op rather than
  removed), and calls the *same* `detonateBombAt` the tile uses for the
  tile-clearing/knockback/boom-sound side of the blast — no second
  explosion implementation for that part.

  **The explosion VISUAL was a separate, real gap**, reported as "the
  explosion animation is gone": `detonateBombAt`'s own blast effect
  (`tileAnimState[...] = { recipe: "bombBlast", ... }`) is grid-cell-based
  and only ever applies where `targetBoard[y][x]` actually has a painted
  tile — which a carried bomb, sitting freely over ordinary open ground by
  the time it goes off, usually isn't. The sound and tile-clearing side
  (for solid neighbors actually in the blast radius) still fired correctly;
  only the bomb's own on-screen poof was silently skipped. Fixed the same
  way a "popped" actor already is elsewhere (`popVanish`/
  `RECIPES.popVanish.duration` — see this doc's own testing gotchas):
  `detonateCarriedBombAt` now calls `playRecipe(bombActor, "bombBlast")`
  (position-based, via `animState`, not grid-cell-based, so it works
  wherever the bomb happens to be) and delays the actual
  `removeActorById(actorId)` by `RECIPES.bombBlast.duration` instead of
  splicing the actor out immediately — the bomb visibly plays its own
  shrink-and-fade blast animation for that ~350ms window before vanishing.
  (An off-screen room's bomb still gets removed immediately — nobody's
  watching it pop.) **A carried/dropped bomb also now gets its own ticking
  warning**, the actor-render equivalent of the tile's flicker:
  `renderActors` multiplies in the same alpha-flicker formula
  (`Math.floor(now/120)%2===0 ? 1 : 0.35`) whenever
  `def.temperament === CARRY_BOMB_KIND && actor.fuseTimerId != null` — which,
  since `fuseTimerId` is the same field the pause/resume mechanic already
  tracks, means the flicker and the countdown are always in lockstep with
  no extra state needed: paused (held) is dark and steady, ticking
  (dropped/thrown) blinks, automatically.

  **A third, unrelated latent bug found while chasing this one**:
  `removeActorById` — called by `resolveActorContact`'s own collectible-
  pickup and fleer-pop reactions, both already-shipped, ordinary Play
  mechanics — was never added to `exportStandaloneGame`'s
  `runtimeFunctions` array. Collecting an item (or popping a fleer) in an
  *exported* game threw a `ReferenceError` the instant it happened, same
  species of bug as the `nextActorInstId` and `actorDefs` gaps above and
  below — found here because the new bomb-blast fix's own
  `removeActorById` call was the first time an export test actually forced
  the question. Fixed by adding it to the list; every existing pickup path
  gets it for free.
- **Magnet**: `radialForceAccelFor(actor, player)` (now takes `player`) has
  a second pull source alongside its tile-scanning loop — a currently
  *actively held* `CARRY_MAGNET_KIND` actor's own live position, same
  `MAGNET_FORCE`/falloff math, same `magnetable` restriction (pushable/
  collectible only, never the player). Resting/dropped, it pulls nothing —
  "only while actively held" is the whole point, straight from the patch
  note's "mobile force field" framing.
- **Cannon**: keeps its orientation (`cannonDir`, copied from the tile
  geometry string at grab time — `"cannon-ne"` → `"ne"`) as real pose
  frames (`currentPoseFor` special-cases `CARRY_CANNON_DEF_ID` to pick by
  direction instead of physics state, the only actor def that does).
  Dropped/resting, `resolveActorContact`'s `CARRY_CANNON_KIND` branch calls
  the *same* `triggerCannon` the tile uses, player-only (matching the
  tile — only `checkPlayerTileContacts`/the Build-mode drag handler ever
  call it). Not blocking, exactly like the tile.
- **Trampoline**: the one kind that needed genuinely new physics —
  `bounceOffTrampolineObjects(actor, axis)`, the actor-vs-actor sibling of
  `resolveAxis`'s own `isTrampolineGeom` branch, called right after
  `shovePushables` on both axes. Unlike a pushable, it's never shoved out
  of the way; landing on its TOP specifically reuses the exact same
  `TRAMPOLINE_RESTITUTION`/`TRAMPOLINE_LAUNCH_SPEED` formula and sound as
  the tile. **Deliberate simplification**: bumping its side or underside
  just blocks (rests), it doesn't bounce on those sides the way the tile's
  4-directional `resolveAxis` bounce does — the primary "jump on a
  trampoline" case is what this covers; flag it to the user before trying
  to make every side bouncy too, since that needs a real actor-vs-actor
  collision model, not this one.

**`sounds` and the export-time closure-capture gotcha (see Sound section)
already covered this, but it bit here too while wiring cannon/bomb/magnet
sounds** — nothing new needed, just confirms the rule holds for any future
reaction. **A thrown object needs its own `recentlyLaunched` exemption**:
`throwCarriedObject` sets `obj.bouncyCooldown` (reusing the same field a
bouncy/Trampoline launch already exempts itself with) specifically because
`stepActor`'s non-player speed cap (`NPC_MAX_SPEED = 160`, far below any
real throw speed) would otherwise flatten the throw back down to a slow
drift within a single frame. Safe to reuse `bouncyCooldown` here — the
v2.20.1 tunneling risk that field's own comment warns about only exists
when something holds a directional key during the exemption window, and a
thrown pushable/bomb/magnet/cannon/trampoline never has steering input of
its own.

**A latent, pre-existing export bug found and fixed while building this**:
`spawnActorAt` (already shared into `exportStandaloneGame`'s runtime) does
`nextActorInstId++`, but nothing in the export template ever declared that
variable — a spawner firing in an *exported* game threw a `ReferenceError`
on its very first actor, undetected until this patch's own
`placeCarryableActor` hit the same missing declaration and a Playwright
export test actually exercised a spawner rather than just checking the
page loaded. Fixed by hand-declaring `let nextActorInstId = 1 + <max id
already in GAME_DATA>;` in the export template, the same "declared here by
hand" pattern `audioCtx`/`noiseBufferCache`/`chipBufferCache` already use
for transient runtime-only state.

**A second latent bug, this one live-editor-only and much nastier: `restoreProjectSnapshot`
never backward-compat-defaulted `actorDefs`' own new built-in entries.**
`CARRY_BOMB_DEF_ID`/`CARRY_MAGNET_DEF_ID`/`CARRY_CANNON_DEF_ID`/
`CARRY_TRAMPOLINE_DEF_ID` are seeded into `actorDefs` unconditionally at
boot — but `restoreProjectSnapshot` (called by `loadAutosave()` right after
that seeding, on every single page load) does a blind
`actorDefs = structuredClone(snap.actorDefs);` with no fallback, exactly
the mistake the Rooms section above calls out in general and the pattern
right below it (`collectibleSlotIds`/`groundTileDefs`, both "older saves
predate X, re-derive from `FACTORY_DEFAULT_SNAPSHOT`") was specifically
meant to prevent. Any autosave/save made before this feature existed
— which is to say almost anyone's real saved project, autosave included,
from before this patch — silently wipes those four keys back out of
`actorDefs` on every subsequent load, forever, until a fresh "New Project."
The result: `convertGrabbedTileToActor`'s own `actorDefs[defId].name` (no
null-guard, since the def was assumed to always exist) throws the instant
a kid grabs a bomb/magnet/cannon/trampoline tile, tripping the app's global
error boundary ("😵 Oops! Something glitched.") — reported as "pressing E
on [these] objects gives an error and deletes them," which read at first
like a grab-logic bug but reproduced on literally every carryable *tile*
(pushable, being much older, was unaffected) and turned out to have
nothing to do with grab's own code at all. **Why this evaded testing all
patch long**: every Playwright test in this session used a fresh browser
context with empty `localStorage`, so `loadAutosave()` always returned
false and `actorDefs` was never clobbered — the bug only surfaces on a
*real* browser carrying forward an *old* save, which no throwaway test
naturally recreates without deliberately seeding a stale autosave payload
first. Fixed the same way collectibles/ground tiles already were: right
after `actorDefs = structuredClone(snap.actorDefs)`, backfill
`[PUSHABLE_DEF_ID, HAZARD_BALL_DEF_ID, CARRY_BOMB_DEF_ID, CARRY_MAGNET_DEF_ID,
CARRY_CANNON_DEF_ID, CARRY_TRAMPOLINE_DEF_ID].forEach(id => { if
(!actorDefs[id]) actorDefs[id] = structuredClone(FACTORY_DEFAULT_SNAPSHOT.actorDefs[id]); })`.
**Any future built-in actor def needs the same one-line addition to that
list** — this is now the established, single place that guards against it,
same as `collectibleSlotIds`'s own fallback just above it in the function.

**Still open, carried over from the prototype, not solved by this patch**:
whether carrying something should affect player movement (slower, lower
jump), and whether a held object should collide with geometry while
carried (bonking against walls) instead of staying fully attached. Flag
either to the user before changing — no evidence yet either way.

### Physical objects vs. fixtures (v2.21)

Direct feedback right after grab/carry shipped: every carryable *except*
the pushable felt "glitchy" to grab, because bomb/magnet/cannon/trampoline/
fan/spawner were all pure contact-trigger pads (`isBlockingGeometry`
returned `false`) — a kid could walk straight through the very thing they
were trying to grab, so the grab gesture had nothing physical to register
against. Trampoline was already blocking (see above); this patch made
**bomb, magnet, cannon, fan, and spawner** blocking too, the same
`isBlockingGeometry` list solid/diggable/Trampoline already use. This
surfaced a second, more interesting question from the same feedback: some
placed objects (door, switch, plate, warp, goal, gravitywell) are the
opposite on purpose — their *entire function* is being walked onto, and
making them solid would break them outright. The user asked for these to
be named as their own category rather than left as an implicit exception
list. **`FIXTURE_GEOMETRIES`** (`goal, switch, plate, door, warp,
gravitywell`) is that category — "fixture" as in a kid-friendly word for
"a thing that's part of the room and doesn't move," parallel to how
`PUSHABLE_KIND`/`HAZARD_BALL_KIND`/`CARRYABLE_KINDS` name the actor side.
Unlike most of these internal-only categorization constants, this one is
also **kid-visible**: the Objects tab now shows two separate palette rows
— "Pick an object" (`PALETTE_OBJECT_GEOMETRIES`, now trimmed to just
cannon/bomb/fan/magnet/spawner/trampoline plus the pushable actor swatch —
real, bumpable things) and a new "Fixtures" row directly below it
(`renderFixtureSwatches`, reading `FIXTURE_GEOMETRIES` itself so the two
lists can't drift apart), each with its own hint text explaining the
distinction in the same "walk onto it" vs. "bump into it" language as this
section's own opening paragraph. `goal`/`switch`/`plate`/`door`/`warp`/
`gravitywell` used to live inside the single old `PALETTE_OBJECT_GEOMETRIES`
row undifferentiated from bomb/cannon/etc.; splitting the row was the fix
for a real gap — the category existed in code (this section, first shipped)
but wasn't visible in the app itself, which is what a kid or a parent
skimming the palette actually sees. `renderFixtureSwatches` reuses the
exact same swatch-drawing/`selectGeometry` click path as
`renderObjectSwatches`'s own geometry loop (same icons, same selection
highlighting) — it's a second row, not a second mechanism. No other code
branches on `FIXTURE_GEOMETRIES` beyond this rendering split and
`PALETTE_OBJECT_GEOMETRIES`'s own doc comment — "stay a walk-through
contact pad, never solid, never carryable" is still simply what every
fixture geometry already does by not appearing in `isBlockingGeometry` or
`CARRYABLE_KINDS`.

**Fan and spawner are blocking-only, deliberately not carryable.** Every
other carryable in this patch (bomb/magnet/cannon/trampoline) is a single
self-contained tile whose whole mechanic already lived in one cell, so
"pick the cell up and turn it into an actor" was a clean lift (see Grab /
carry / drop / throw above). Fan and spawner aren't: `fanAccelFor` scans
outward from a fixed `geometryAt` cell along a facing direction, and the
spawner's contents/cooldown/TTL/concurrency-cap system is keyed to its own
board position — neither has a "current cell" that could float around
glued to a player without a much bigger rework of how they store state.
Making them blocking (so nothing floats through empty air where a fan or
spawner obviously physically *should* be) was the fix this feedback
actually asked for; making them carryable is real, separately-scoped
future work, not attempted here.

**Consequence of blocking the tiles: touch-based triggers had to move from
"overlap" to "collision."** Bomb-arm and cannon-fire used to fire from
`checkPlayerTileContacts`, a function whose own comment assumed the player
never overlaps blocking geometry (true before this patch, since bomb/
cannon weren't blocking) — it read `modifierAt`/`geometryAt` under the
player's AABB every frame regardless of whether that cell was walkable.
Now that bomb/cannon tiles physically stop the player at their edge, that
overlap never happens, so the trigger moved into `resolveAxis` itself,
fired at the exact moment a per-axis collision against that geometry is
resolved (right beside the existing lethal/hazard/Trampoline branches, and
still before the v2.20.1 tunneling-fix `return`) — `checkPlayerTileContacts`
and the build-mode drag handler (`clampDragPosition`, via a small shared
`fireBlockingTileReaction` helper for its two blocking-clamp loops) both
had their now-dead overlap-based bomb/cannon branches removed in favor of
this single collision-time call site. Magnet and spawner need no such
migration — their mechanics were never touch-triggered to begin with
(magnet pulls at range, spawner fires on its own timer), so making them
blocking is a pure physics change with nothing else to wire up.

**An emergent interaction worth knowing about, not a bug**: a fan facing
straight up is now solid, so a player standing on/over it can never
actually occupy the fan's own cell (the strongest point on its force
curve, `i = 0`) — the closest it can rest is the cell directly above,
`i = 1`. `FAN_NEAR_FORCE` (1900) still exceeds `GRAVITY` (1450) at that
distance, so the player hovers there indefinitely rather than ever
settling to `grounded = true`. This was verified as a real, stable,
error-free outcome (not a stuck/undefined state) rather than patched away
— the user's instruction was specifically to make fans solid, and "hovers
in the updraft instead of standing in it" is a reasonable reading of that
for a fan, not a glitch. Flag it to the user before changing `isBlockingGeometry`
or the fan force curve if this ever needs to read differently.

### Camera & rooms (v2.17)

A room's board arrays are always allocated at `BOARD_MAX_COLS` (3× the
viewport), but `cameraMode` (`"fixed" | "follow" | "runner"`) controls how
much of it is reachable/rendered — `roomCols()` returns the *usable* width
for the current mode. Runner mode ties into the lethal-hazard reaction for
its fail state (`checkRunnerFailState`) rather than inventing a second
game-over path.

### Duplicate Room (v2.21)

One button, `renderRoomTabs`'s own last child so it's always the rightmost
thing in the room-tab row regardless of how many rooms exist — acts on
whichever room is currently open (the hot one), the same target every
other room-scoped control in that row already implies, rather than needing
a per-tab button of its own like delete (`×`) has. `duplicateRoom()`
flushes the hot globals first (`snapshotCurrentRoomState()`, so the copy
reflects whatever was just painted, not stale data), then `structuredClone`s
`board`/`backgroundBoard`/`colorBoard`/`groundSkinBoard`/
`groundSkinRotationBoard`/`startPos`/actors and Game Rules/Camera
(`gravityEnabled`/`wrapHEnabled`/`wrapVEnabled`/`cameraMode`/`editorPanCol`)
onto a fresh room object (`nextRoomId++`, name `<original> + " copy"`,
chains fine — duplicating a duplicate named "room 1 copy" yields "room 1
copy copy"), pushes it, and switches to it immediately — same
`rooms.push`/`activateRoom` shape every other room-creation path (an
auto-generated door-linked room, the built-in sample games) already uses,
so nothing new needed wiring into undo/redo/autosave/JSON save-load (those
already snapshot the whole `rooms` array plus its id counters wholesale).

**One deliberate exception to "copied exactly," worth flagging**: the
player is never duplicated. `removeAllPlayerInstances`'s own comment
already establishes the project's one hard rule here — there is only ever
ONE player actor across the *entire project*, not one per room — so
copying it would leave two actors simultaneously marked `isPlayer` (one in
each room) while `playerRoomId` could still only point at one of them, an
inconsistency nothing else in the codebase (camera follow, Play-mode
start, the room tab's own "•" marker) is built to tolerate. `duplicateRoom`
filters the player out of the cloned `actors` array before cloning; every
other actor — pushables, wanderers/chasers/fleers, collectibles, spawners
and their loaded contents, a grabbed-and-dropped carryable — comes along
untouched, reassigned a fresh id (`nextActorInstId++`) so it can never
collide with the original room's copy once both exist side by side.
`startPos` is copied as-is even though it's really "the player's own reset
position for this room" (see the Actor-shape section above) — harmless
dead weight on a room with no player in it, and gets overwritten correctly
the moment a kid places a fresh player there anyway (`placeNewActor`'s own
`if (isPlayer) { startPos.x = ...; playerRoomId = currentRoomId; }`).

Build-mode-only, like `deleteRoom`/`createEmptyRoom` already are — nothing
here belongs in `exportStandaloneGame`'s `runtimeFunctions` (an exported
game never creates rooms, it only ever plays the ones baked into
`GAME_DATA`), and the whole `#roomTabRow` this button lives in is already
hidden outright in Play mode (`body.play-mode #roomTabRow { display:
none; }`).

### Fan and Spawner (v2.19, force curve and always-live fixed in v2.20/v2.20.2)

A fan (`fanAccelFor`) projects wind's own force calculation outward from a
placed Object along its facing direction, scanning up to `FAN_RANGE_TILES`
cells and stopping at a wall or the fan itself. v2.20 gave it a distance
falloff instead of one flat force across the whole range: `FAN_NEAR_FORCE`
(1900, right at the fan — deliberately *more* than `GRAVITY`, so standing
directly in the stream actually lifts you) linearly interpolating down to
`WIND_FORCE` (1000, weaker than gravity, same as plain wind) by the far
edge. **v2.20.2 fix:** the scan used to start at `i = 1` (the cell BETWEEN
the actor and the fan), never `i = 0` (the actor actually overlapping the
fan's own cell) — so the exact moment a kid fell into or stood right on a
fan, the strongest and most expected point, got ZERO force, a cliff-edge
drop-off at closest approach. Now `i = 0` is the fan's own cell (peak
`FAN_NEAR_FORCE`) and `i = FAN_RANGE_TILES` is the far edge (plain
`WIND_FORCE`). This is what lets fan-to-fan hopping climb higher each jump
instead of topping out — the near-force genuinely overpowers gravity, the
far-force never does. `fanAccelFor` also returns a `near` flag (true within
~1 tile) purely for the floating-bob render cue (`actor.nearFan`, read in
`renderActors`) — a cosmetic sine wobble, never physics.

**v2.20.2: continuous accel alone can't visibly arrest a fast fall.** Even
though `FAN_NEAR_FORCE` genuinely "beats gravity" on paper, a terminal-
velocity drop only spends 2-3 frames inside the ~1-tile-deep near zone
before it's past the fan — ~450px/s² of net excess accel over ~0.03s barely
dents 750px/s of existing fall speed. Continuous accel made "fall into a
fan, feel bounced" imperceptible in practice, a real user-reported gap.
Fixed with a discrete kick layered on top (`FAN_BOUNCE_MIN_SPEED`,
`FAN_BOUNCE_RESTITUTION`, applied in `stepActor` right where `fanAccelFor`
is called): when `near` is true and the actor's velocity component along
the fan's push direction is opposing it beyond `FAN_BOUNCE_MIN_SPEED`, that
opposing speed is instantly converted into push-back at
`FAN_BOUNCE_RESTITUTION` — the same "instant, not just gradual" shape
`TRAMPOLINE_LAUNCH_SPEED` uses for the identical reason. A fast fall takes
2-3 successive partial kicks to fully arrest (each one isn't restitution
enough alone, same shape as a real settling bounce) — `actor.fanKickCooldown`
gates the accompanying `sounds.boing()` to once per episode rather than once
per frame. **Deliberately a separate cooldown field from `bouncyCooldown`**
— reusing that one would also flip `stepActor`'s `recentlyLaunched` speed-
cap skip on, and holding a direction key during that window is exactly the
mechanism that caused the v2.20.1 tunneling bug elsewhere; a fan kick must
never disable the movement speed cap.

The animated white "wavy line" VFX (`drawFanStream`) originally spanned
the whole `FAN_RANGE_TILES` reach in the blow direction, which read as
"several tiles of dashes" rather than a wind effect at the fan's mouth — a
second piece of direct feedback. **v2.20.2:** now confined to the single
tile immediately in front of the fan — 2-3 short wavy lines side by side
(spaced across the perpendicular axis), each a small sine ripple kept well
inside that one tile's bounds and animated by phase so they shimmer in
place, rather than a dashed line marching outward across the whole range.

The spawner (`tickSpawners`/`tickSpawnedTTL`) originally only ran in Play
mode, reasoned as "a gameplay mechanic a kid experiences by pressing Play."
v2.20 removed that gate — it directly contradicted "always live" (a
wanderer/chaser already roams the instant it's placed in Build mode; the
spawner sitting inert until Play was the actual bug, not a deliberate
carve-out). It now runs unconditionally from `tick()`, same as every other
actor behavior; only genuinely session-scoped things (`updateCamera`,
`checkRunnerFailState`) stay Play-gated. A spawner still needs nothing
loaded to work — it falls back to `HAZARD_BALL_DEF_ID` — and any actor kind
(the default hazard ball, `pushable`, or a full custom character/temperament)
can be loaded by selecting it and clicking an existing spawner tile
(`toggleSpawnerContent`); the player itself can't be loaded (spawning
players makes no sense). Each spawn plays a `materialize` chime
(`sounds.spawn()`) and reuses the `caughtBounceIn` pop-in keyframe recipe
— deliberately reused rather than inventing a near-identical second
"something appearing" animation.

### Sound (v2.21 — chip engine, replacing the v2.18 Wavesculpt port)

Fully synthesized, no samples. The v2.18 placeholder (oscillator "patches"
ported from Wavesculpt) was replaced wholesale by a tiny NES-2A03-style chip
synth: `renderChipDesign(design, opt)` renders a finished, hand-tuned
per-frame sound description (2 pulse channels, 1 triangle, 1 noise — see its
own header comment for the exact per-frame format) to a `Float32Array`.
`CHIP_DESIGNS` holds eleven finished designs (`thunk`, `boing`,
`trampolineBoing`, `pop`, `splat`, `kaboom`, `ding`, `creak`, `wind`,
`swoosh`, `zip`, `cat`) — **finished per-frame data, not a generator**: they
were tuned in a separate, unshipped throwaway tool (`sound-designer.html`,
built in an earlier session, against `chip.js`/`designs.js`, also not
shipped as-is) and pasted in as plain numbers. `getChipBuffer(name)` renders
a design to an `AudioBuffer` **once, on first use**, and caches it;
`playChip(name, pitchMult, velocity)` always plays from that cache — never
re-renders per trigger. `sounds` is a plain object literal mapping each
reaction directly to a `playChip(...)` call (see below for why it's written
as literals, not built from a lookup table).

**Not every reaction got a new chip design.** `jump`, `flip`, `fuse`,
`gameOver`, and three of the four creature voices (`dogBark`,
`chickenCluck`, `genericCreature` — only `cat` was redesigned) still run on
the original v2.18 one-shot oscillator engine, kept below the chip engine
in the same section (`playPatch`, `osc`, `getAudioCtx`, the trimmed
`SOUND_PATCHES` with just those 7 entries). This is a deliberate, narrow
exception — nothing was silenced just because it wasn't redesigned yet —
not a half-finished migration; flag it to the user before either deleting
this leftover engine or authoring new chip designs to replace it.
`playActorSound(actor, fallbackReactionName)` is what dispatches per voice:
`def.voice === "cat"` goes to `playChip("cat", ...)`, any other non-empty
`def.voice` goes to `playPatch(def.voice, ...)` (the legacy engine), empty
falls back to the generic reaction sound — see `VOICE_PATCHES` for the
picker's id/label list.

**The old ~20-entry `REACTION_PATCH` table is gone, consolidated onto the
new engine's 8 designed families.** Each family's own `use` field (in the
original `designs.js`) is what decided the consolidation, not guesswork:
`boing` also covers a plain actor-vs-actor bounce and (via its own
`trampolineBoing` entry — the family's "fat" tuned variant, not a duplicate
of plain `boing`) the Trampoline object's launch, keeping the "extra bounce
power should be heard, not just felt" distinction v2.20.1 gave it; `pop`
also covers a spawner's arrival (no separate `materialize` sound anymore);
`splat` also covers being caught by a chaser (same severity tier — a life
lost — as a lethal hazard, not the old separate `gotcha` patch); `thunk`
also covers every other physical bump/knock (NPC `boop`/`oof`, a hazard's
non-lethal knockback, a diggable tile eroding) that used to be its own
named patch. **`kaboom` deliberately covers both bomb detonation and cannon
launch** — this looks like it's reintroducing the exact v2.20.1 "cannon and
bomb sounded identical" bug, but it isn't: the delivered sound design's own
`use` field says `"bomb explosion, cannon shot"` together, a decision made
in the design data itself, not by whoever wires up the reaction table. Only
`wind`/`slide`/`warp` changed in the other direction — they're now three
genuinely distinct rendered sounds (`wind`/`swoosh`/`zip`, three tuned
variants of one design family) instead of one shared patch pitched three
ways, which is what `sounds.wind`'s old pitchMult hack was working around.

**Export-pipeline gotcha, found while building this:** `sounds` must be
written as literal, self-contained arrow functions
(`thud: () => playChip("thunk")`), never built by looping over a lookup
table and closing over the loop variable
(`sounds[name] = () => playChip(TABLE[name])`). `exportStandaloneGame`
ships each `sounds.X` function by literal source text (`fn.toString()`) —
a closure over an outer variable serializes as that variable's *name*, not
its resolved value, and throws a `ReferenceError` the instant it runs in
the exported game's own scope, where that outer variable doesn't exist.
This bit every reaction sound except the couple that were already
hand-written as literals (`thud`, the old `wind` override) in the v2.18
engine, undetected until this patch actually loaded an exported game and
called its sounds directly. Same rule for anything else added to `sounds`
later — one line per reaction, referencing only literals and globals that
are also in `runtimeFunctions`/`constantsSource`, never a captured local.

`RECIPES` (separate from sound) are visual deformation/animation keyframe
sequences (`popVanish`, `caughtPunt`, ...) — note `RECIPES.popVanish.duration`
(220ms) is a **real wall-clock `setTimeout`**, not a game-tick-driven delay,
so an actor that "pops" is still in the `actors` array for ~220ms after the
reaction fires before `removeActorById` actually runs.

**v2.20.1: a bounce needs to sound like a bounce.** `triggerImpact` (called
unconditionally from every `resolveAxis` collision, bounce or not) used to
always fire the generic landing `thud` regardless of whether the tile was
plain solid or bouncy — a bounce and an ordinary landing were
indistinguishable by ear, another user-reported bug. Fixed with a 4th
`triggerImpact(actor, axis, incomingSpeed, isBounce)` parameter that
suppresses the thud specifically (the visual impact wobble still tracks
every contact, bounce or not); `resolveAxis` now calls a small
`bounceSound` (`sounds.boing` for plain bouncy, `sounds.trampolineBoing`
for the Trampoline object) right at each of its 4 reflection sites,
player-only (a wandering hazard ball caroming off walls doesn't need a
boing every hit). The general "does an ordinary footstep/small-hop landing
really need its own thud" question is left as-is for now — `mag` (the 0-1
scale `sounds.thud` reads for pitch/volume) saturates to 1 after roughly a
single tile of fall, so there's currently no clean way to distinguish "a
kid hopped down one step" from "an actual big fall" without reworking that
scale; flag it explicitly to the user before changing `IMPACT_NOISE_FLOOR`
or the thud threshold, since a bigger change risks silencing normal jump
landing feedback the game already relies on elsewhere.

### Export pipeline

`exportStandaloneGame()` builds a second, self-contained HTML file:
`gameData` (a frozen snapshot of current project content), a
`runtimeFunctions` array (shared functions serialized via `fn.toString()`
— **any new function the runtime needs at play-time must be added to this
list explicitly**, source-sharing isn't automatic), a `constantsSource`
array (hand-written `const X = ${JSON.stringify(X)};` lines — **also not
automatic**, a new constant needs its own line here), and `soundsSource`.
The exported template declares its own copies of transient
runtime-only state (things like `spawnerRuntime = {}` that don't belong in
`gameData`) and re-derives everything else via the same shared
`activateRoom`/`restartStandaloneGame` functions the editor itself uses.

## Version labels are not reliable — read the code, not the comment

Comments and commit messages use an informal `v2.N` (and occasionally
`v2.N.M`) scheme, but **it is not monotonic and has been reused**. Concrete
example already in this repo's history: `9f5264a` ("Ground tab revamp: real
textures, animated lava/fire, custom tiles") is labeled **v2.19**, has its
own sub-patches commented `v2.19.2` through `v2.19.5` scattered through the
file (e.g. around `placeNewActor`, `activateRoom`, drag-repaint, actor
reset), and predates commits labeled v2.15/v2.16/v2.17 in git history — and
then a **completely unrelated** later patch (magnet/gravity-well/sticky-
wall/fan/spring/spawner) was *also* labeled **v2.19** (commit `775c94c`).
There are two unrelated features both calling themselves "v2.19" in this
codebase. Don't trust a version label to uniquely identify a feature or to
order commits — check the actual diff/git log/surrounding code instead. If
you're tempted to leave a `vX.Y` comment on new work, a plain description
of *why* ages far better than a number that may already be taken.

## Testing conventions

There is no test framework, no `npm test`, nothing checked into the repo.
Tests are throwaway Playwright scripts written fresh each session:

- **Debug hook pattern**: add a temporary `window.__toyDebug = { ... }`
  object exposing whatever internals the current patch needs to assert on
  (`getActors`, `getBoard`, `getSpawnerContents`, etc.), placed right after
  `updateUndoRedoButtons()` near the boot sequence. Write Playwright tests
  against it. **Strip it before the final commit** — `grep -n "toyDebug"
  index.html` must return nothing. This has been the pattern since at
  least v2.16 and should keep being the pattern.
- **Playwright environment specifics** (this sandbox): launch with
  `chromium.launch({ executablePath: '/opt/pw-browsers/chromium' })`,
  `require('/opt/node22/lib/node_modules/playwright')` directly rather than
  via a local `node_modules`. Always wire `page.on('dialog', d =>
  d.accept())` (the app uses native `confirm()` for New Project / sample
  loading / etc.) and `page.on('pageerror', ...)` to catch runtime errors.
  Load via `file://` on the real `index.html` path, not a copy.
- **Test files live in the session scratchpad directory**, not the repo —
  they're intentionally not committed. The literal path changes per
  session; use whatever scratchpad path this session's environment gives
  you.
- **`getActors()`/`getBoard()` etc. should return live references**, not
  copies, when you write a debug hook — this lets a test directly mutate
  actor velocity/position/`spawnBornAt`/etc. to fast-forward past
  real-time waits (e.g. seeding a spawner's `clock` field close to its
  firing threshold instead of waiting the full interval) while still
  exercising the real production code path on the next tick. Very useful
  for anything gated by a multi-second timer.

### Gotchas learned the hard way (read before writing new physics tests)

- **Gravity defaults OFF for every new/empty room.** A fresh "New Project"
  or a room you just created has `gravityEnabled = false`. Any test (or
  manual check) of a gravity-dependent mechanic (sticky wall suspension,
  a bouncy/Trampoline launch, a fan "fighting" a fall) needs to explicitly
  click the gravity swatch in `#gameRuleSwatches` first, every time, after
  every New Project.
- **Row/column indices are 0-based and bounded by `ROWS`/`COLS` (18/24 as
  of v2.20)** — `board[18]` is out of bounds when `ROWS = 18` (valid rows
  are 0–17). A test that paints a "floor" at row `ROWS` itself (an easy
  off-by-one when copying an old test) throws `Cannot read properties of
  undefined` the moment anything reads that row back, not a silent no-op.
- **Selecting the `bouncy` Surface swatch defaults `selectedGeometry` to
  `"solid"` if it was `"none"`** (`selectSurfaceModifier`, v2.20 fix) — a
  deliberate UX default, not a bug, so don't be surprised if a test that
  expects `"none"` after clicking bouncy sees `"solid"` instead. `sticky`/
  `slippery`/`hazard`/`lethal` are deliberately NOT defaulted this way —
  each has its own valid, distinct reading on `"none"` ground.
- **`paintMode` ("tile" vs "actor") is sticky across tab switches and is
  *not* set by a debug-hook shortcut that only assigns `selectedGeometry`.**
  If a previous action selected an actor (e.g. the player, for a "can this
  be loaded into X" check), a later debug-hook `setSelectedGeometry(...)`
  followed by a canvas click will still place an *actor* (whatever was last
  selected), not paint the tile, because nothing changed `paintMode`. Prefer
  clicking the real palette swatch (which sets both `selectedGeometry` and
  `paintMode` correctly via the actual click handler) over a debug-hook
  field-setter for anything that will immediately be followed by a canvas
  click.
- **`enterPlayMode()` silently no-ops if no player has been placed**
  (`if (playerRoomId == null) { log(...); return; }`). If a test's `appMode`
  stubbornly stays `"build"` after clicking Play, this is almost always why
  — check that a real player placement (not a click that got intercepted
  by something else, like a spawner tile's toggle-contents handler) has
  actually happened.
- **A click on an existing spawner tile while `paintMode === "actor"` never
  places an actor there** — it calls `toggleSpawnerContent` instead. This
  is correct product behavior (loading a spawner is the same click-to-place
  gesture, by design) but means "place the player at cell X" tests must
  use a cell that is *not* a spawner tile.
- **A restitution bounce can't exceed the height it fell from** — this
  still holds for plain `bouncy` (0.82). The Trampoline OBJECT is the one
  exception: it enforces a hard minimum launch speed
  (`TRAMPOLINE_LAUNCH_SPEED`) on top of reflection specifically so a gentle
  step-on still gets a real bounce — see `resolveAxis`'s `isTrampolineGeom`
  branch. Testing "does it launch the player" by checking it clears its
  *starting* height still isn't reliable for a short fall onto plain
  `bouncy`; use a tall, deliberate fall and compare rebound height
  *between* plain bouncy and Trampoline, not against the spawn point.
- **A bouncy floor/wall/ceiling more than one tile wide used to let the
  player tunnel straight through it** (v2.20.1 fix, and the actual root
  cause of a user-reported "warp out the bottom of a ring of bouncy tiles"
  bug — the earlier v2.20 geometry-defaulting fix in `selectSurfaceModifier`
  was real but insufficient on its own). Two independent bugs stacked:
  (1) `resolveAxis`'s cell loop didn't stop after resolving one collision —
  an actor's AABB routinely spans two columns (or rows) that are BOTH
  blocking whenever a bouncy surface is more than one tile wide (i.e. any
  real one), so the loop reflected `vy` twice in the same call: once
  correctly (positive → negative), then a second time reading its OWN
  already-flipped negative value as "hit from below," pushing the actor to
  `(cy+1)*TILE` — the tile's FAR side. Ordinary non-bouncy solid never
  showed this because its landing branch zeroes `vy` to exactly 0, and
  neither `vy > 0` nor `vy < 0` fires on a second pass over 0 — only
  bouncy's nonzero reflected velocity exposed it. Fixed by `return`ing
  immediately after resolving the first blocking cell per axis call — one
  AABB only ever needs one resolved collision per axis per frame. (2)
  Separately, `checkPlayerTileContacts` (written assuming, per its own
  comment, that "the player never overlaps blocking geometry" since
  `resolveAxis` pushes it flush to the boundary) fired
  `triggerBouncyLaunch` — meant only for the non-blocking `none:bouncy`
  walk-over pad — whenever it saw `modifier === "bouncy"` on ANY cell the
  AABB overlapped, blocking or not. On uneven/staircase terrain (a
  hand-painted circle of solid+bouncy tiles is exactly that) the player's
  AABB can genuinely graze a neighboring solid+bouncy cell it isn't
  resting on. That falsely set `bouncyCooldown`, which `stepActor`'s
  `recentlyLaunched` check uses to skip the `MOVE_ACCEL` speed cap
  entirely — holding a direction key during that ~350ms window let
  velocity run away completely unbounded (observed vx > 1000px/s), more
  than enough to fly past a ring's own curve. Fixed by gating all three
  modifier reactions in that function on `!isBlockingGeometry(geometry,
  player)`. **When testing any bounce-related mechanic, always test it
  under active player input (hold a direction, jump repeatedly) in
  addition to passive drop-and-watch** — the passive case alone won't
  surface either of these; both needed genuine held input to reproduce (a
  ring that "stays inside for the full duration" with zero input proves
  nothing about whether it holds up once a kid actually plays with it).
- **`WIND_FORCE (1000) < GRAVITY (1450)`** for plain wind/conveyor tiles,
  deliberately — a "none/solid + wind" tile facing straight up will slow a
  fall, never reverse it. A **fan is different since v2.20**: its force
  falls off with distance (`FAN_NEAR_FORCE = 1900` at `i = 0`, the fan's own
  cell, down to `WIND_FORCE` at `i = FAN_RANGE_TILES`), and right at the fan
  it's *stronger* than gravity on purpose (so fan-hopping climbs higher).
  Query `fanAccelFor(x, y)` directly at fixed distances to test the falloff
  curve itself — physically dropping an actor toward a fan conflates
  "distance from the fan" with "time elapsed" since both change every frame
  as it falls, which makes the curve much harder to isolate, AND (see the
  next gotcha) continuous accel alone genuinely isn't enough to arrest a
  fast fall regardless of the curve's shape — check `fanAccelFor`'s raw
  output for the force curve, and a real physics trace (with the discrete
  kick engaged) for the felt bounce.
- **`fanAccelFor`'s distance index `i` starts at 0 (the actor overlapping
  the fan's own cell), not 1** (v2.20.2 fix — it used to start at 1, so an
  actor actually standing on/falling into the fan, the single most expected
  moment for it to matter, got zero force). If a test scans distances with
  `for (i = 1; i <= FAN_RANGE_TILES; i++)`, it's silently skipping the
  strongest point on the curve.
- **A fan's continuous force can't visibly arrest a fast fall on its own —
  a discrete kick does the real work** (`FAN_BOUNCE_MIN_SPEED`/
  `FAN_BOUNCE_RESTITUTION` in `stepActor`, v2.20.2). Testing "does falling
  into an upward fan produce a bounce" by only checking `fanAccelFor`'s
  returned `ay` proves the force curve is right but not that it's felt —
  run an actual fall (`enterPlayMode`, drop the player through several
  tiles onto/through the fan, sample `vy` every frame) and look for `vy`
  actually going negative (a true reversal), not just a smaller positive
  number.
- **`isStuckToSticky` only checks a sticky solid tile's LEFT, RIGHT, and TOP
  sides — never the tile directly under an actor's feet** (fixed in v2.20;
  it originally also checked the bottom-adjacent tile, which meant merely
  *standing on* an ordinary sticky floor was misread as "clinging to a
  wall" — gravity got permanently stuck at `vy = 0`, `grounded` never went
  true again, and jump input silently stopped working, for anyone who ever
  stood still on one). Sticky ground's own separate "slows you down" effect
  is `isOnStickyGround` (any geometry, top-surface-or-walkable-through),
  deliberately a different function from the wall-climb check.
- **Sticky is a timed cling (`STICKY_CLING_MS`), not indefinite climbing**
  (v2.20.3 — direct feedback that holding a direction while stuck let a kid
  scale a sticky wall forever). An actor freezes completely (no movement
  input of any kind, see `stuck` in `stepActor`) for `STICKY_CLING_MS`,
  THEN the existing `stickyReleaseT` ramp starts automatically — whether or
  not contact is still being made. If a test tries to "break contact early"
  by holding a direction away from the wall while still within the cling
  window, **nothing happens** — input is fully ignored while `stuck` is
  true, so the actor won't actually move until the cling timer itself
  expires. Don't assume pressing away ends the stick early; sample well
  past `STICKY_CLING_MS` (1000ms) before expecting any release to have
  started.
- **The level has an implicit solid floor/edges at the board boundary.**
  An actor that free-falls long enough will ground out at the bottom of
  the room and read `vy === 0` for that reason — not because whatever
  gravity-suspension mechanic you're testing is still active. Sample
  velocity *mid-fall*, not after an arbitrarily long wait.
- **A "popped" actor lingers ~220ms after its reaction fires** (real
  wall-clock `setTimeout`, `RECIPES.popVanish.duration`) before
  `removeActorById` actually removes it from `actors`. Wait past this
  before asserting an actor is gone.
- **Not every swatch in the Objects tab row is an actor** (see Architecture
  above — `goal`/`switch`/`plate`/`door`/`cannon`/`bomb`/`warp`/`fan`/
  `magnet`/`gravitywell`/`spawner`/`trampoline` are geometry tiles).
  Clicking one and reading `getSelectedActorDefId()`
  afterward will silently return whatever actor def was last actually
  selected, not anything related to the tile you clicked. Only `pushable`
  and the Collectibles-row presets are real loadable/placeable actor defs
  from the Objects tab.
- **`GRAB_KEY_RANGE` (~1.3 tiles) is measured from the player's own
  center to the target's center** — an actor-vs-actor grab and a
  grab-off-a-tile-cell both use this, but a kid (or a test) walking at
  `MAX_SPEED`/`NPC_MAX_SPEED` for even a few hundred ms covers this
  distance and more, especially toward a NON-blocking tile like cannon/
  bomb/magnet that a moving actor just walks straight through. A test that
  walks toward a carryable and then presses the grab key needs either a
  short, precisely-timed walk or (simplest) to place the player already
  adjacent before pressing Play — don't assume "walked roughly toward it"
  lands back in range. Under gravity, this cuts the other way too: a
  player placed in mid-air starts falling the instant Play begins, so a
  grab attempted even 100-200ms later may already be out of range of
  whatever's beside its ORIGINAL placed cell.
- **A dropped/thrown pushable-or-carryable's landing spot isn't
  predictable enough to assume in a later step of the same test.** A test
  that throws an object and then tries to grab something else nearby (by
  walking there) can end up re-grabbing the just-thrown object instead, if
  it happened to land closer than the intended target. Prefer teleporting
  the player via a debug-hook position set (or spacing the two objects/
  cells much further apart) over chaining "throw, then walk toward the
  next thing" in one test.

we've been talking about different items. Move the 'button' to the
fixtures and have it replace the switch currently there giving all of the

never used `"switch"` at all — only Button (`pushbutton`) + Gate

for the whole time: fold Switch's entire permanent-toggle mechanic into
Button, move Button into the Fixtures row (walk-onto, not bump-into), and
retire `"switch"` outright.

**Scope, decided by reading every call site touching either geometry
before writing anything** (not re-confirmed with the user — proceeding on
a confident, internally-consistent reading, per this session's own
pattern of making a judgment call and letting feedback redirect it, the
same way v2.27.2's cannon/bomb removal was its own full-replacement
precedent): Button fully takes over Switch's job — permanent toggle

economy, just driven by a different piece of state. Button moves from
`PALETTE_OBJECT_GEOMETRIES` (bump-into, blocking) into

precedent the old stick-figure preset and the cannon/bomb → cannon2/bomb2

## Spawner: no more single-item cap, no more automatic timed disappearance (v2.38)

Direct feedback: "Spawners still only make 1 item at a time. They should be able to make lots of
the item. No reason they should automatically disappear. If they are overlapping with no place to
go, then yes, maybe they start to disappear, but as the default behavior it's too restrictive."
This reverses two separate population-management mechanisms v2.35 and earlier had built up —
both existed for a reason at the time (keeping concurrent spawns from visually clumping, per
v2.34's own jitter work), but the user's experience of them in practice was that a spawner just
felt broken/limited, not managed.

**Two restrictions removed, not replaced with a smarter version of either:**
- The v2.35 "one live spawn at a time" cap (`state.activeId`, the `occupied` gate in
  `tickSpawners`) is gone. A spawner now fires on schedule every `SPAWN_INTERVAL_MS`, full stop,
  regardless of how many of its own earlier spawns are still alive.
- The v2.19-era `SPAWN_TTL_MS` (8s) automatic despawn (`tickSpawnedTTL`, called unconditionally
  from `tick()`) is gone outright, along with its call site, the constant itself, and the
  `spawnBornAt` field it was the only reader of. Spawned content no longer pops on a clock just
  for existing — it persists exactly like anything else placed in the room, until something
  actually removes it (caught by the player, popped by touching it, destroyed in lethal, etc.).

**What's kept, and why it's not the same thing as either removed restriction**: the user's own
carve-out — "if they are overlapping with no place to go, maybe they start to disappear" — was
read narrowly rather than built as a new despawn mechanism for already-existing actors (which
would reintroduce exactly the "things vanish on their own for no visible reason" complaint this
patch exists to fix). Instead, `cellOccupiedByActor(cx, cy)` (a plain AABB-vs-cell-rect scan
against `actors`, the actor-world equivalent of the tile-blocking checks this file already has)
gates the spawner's own firing: if the cell it's about to launch into already has an actor sitting
in it, this cycle's fire is skipped — the clock keeps counting (same as the old `occupied` gate
did), so the very next tick after the cell clears, it fires immediately rather than waiting out a
fresh interval. Nothing that already exists is ever removed by this — it's purely "don't
materialize a brand-new actor fully on top of one that's already there," which is also what
actually prevents a literal stack of exact-overlapping clones from ever happening, not a cosmetic
nicety. This is a deliberate, narrower reading of the user's own "maybe they start to disappear"
phrasing than an active despawn-on-overcrowding reaction would have been — flagged here in case
the user actually wants existing crowded spawns to start popping too, which would be a different,
bigger change (deciding what "no place to go" means for something that already exists and can't
move, not just a cell a new one hasn't been born into yet).

**`despawnSpawnedActor` itself is completely untouched** and still does real work — every
touch-triggered "this spawned thing goes away" reaction (`resolveActorContact`'s hazard-ball-pops-
when-it-hurts-the-player branch, and the stationary/wanderer "bumping it counts as popping it
early" branches) still calls it exactly as before; only the standing TIMER that used to call it on
a clock, with no contact needed, is gone. `ttlPopped` still guards those touch-triggered calls
against re-firing every frame while a popped actor is mid-fade.

**A real, if obvious, consequence worth stating plainly**: with no cap and no timer, a spawner left
running for a long Play session will accumulate actors indefinitely (bounded only by whatever
naturally removes them — the player catching/touching them, lethal, etc.). This is the literal
behavior asked for ("lots of the item"), not an oversight, but it's worth flagging since nothing in
this patch adds a safety valve against a genuinely long, idle, uninterrupted run building up a
large actor count — if that ever becomes a real problem, it needs its own explicit ask rather than
silently reintroducing one of the two restrictions this patch just removed.

**Export pipeline**: `tickSpawnedTTL` is removed from `runtimeFunctions` and replaced with
`cellOccupiedByActor`; `SPAWN_TTL_MS`'s `constantsSource` line is removed (nothing reads it
anymore). `spawnActorAt`'s signature dropped its now-unused `nowMs` parameter (and the `spawnBornAt`
field it set) — its one call site in `tickSpawners` updated to match. Every other function this
touches (`tickSpawners`, `despawnSpawnedActor`) was already shared into the export from earlier
patches.

Verified with Playwright: a spawner with open space ahead, run for 9 real seconds, produces at
least 2-3 concurrently-alive spawns (not 1) and the count never drops on its own over that window
(no automatic disappearance); a spawn frozen in place directly in the spawner's launch cell
correctly blocks the next cycle's fire for as long as it stays there, then the spawner fires again
within about a tick of the cell clearing; the exact same two checks hold in a freshly exported
standalone game; The World's Worst Elevator (the one built-in sample with live spawners) plays for
3+ seconds with zero errors under the new behavior; and the full 5-sample regression sweep plus a
fresh Button+Gate export both still run clean.

## Follow camera eases toward its target instead of snapping every frame (v2.39)

Direct feedback: "let's smooth out the 'follow' camera. it can't be so sensitive to pixels, as
it's constantly jerking back and forth." `updateCamera`'s Follow branch (v2.17) had always just
assigned `cameraX` to the exact centered-on-player target every single tick — no damping of any
kind — so any frame-to-frame sub-pixel wobble in the player's own position (friction settling
toward 0, a collision resolution snapping it flush to a tile edge, ordinary frame-timing variance)
was copied onto the camera instantly and in full, reading as constant jitter rather than smooth
tracking.

**Fix: an exponential ease toward the target, not a position lerp with a fixed step.**
`CAMERA_FOLLOW_RATE` (9, a per-second rate) feeds `cameraX += (target - cameraX) * (1 -
Math.exp(-CAMERA_FOLLOW_RATE * dt))` — frame-rate independent (unlike a flat `* 0.1` per-frame
lerp, which would track differently at 30fps vs 144fps), closing about 95% of the gap to the
target within roughly a third of a second. Fast enough that a running player stays comfortably
on screen, slow enough that a one-or-two-pixel target wobble gets smoothed into nothing a kid
would notice. The target itself (centered-on-player, clamped to the room's edges) is computed
exactly as before — only how `cameraX` moves toward it changed.

**One case deliberately kept as an instant snap, not eased**: the very first Follow-mode tick
after a room becomes hot (entering a room via a door, or Play/Restart). `cameraX` has always reset
to 0 the instant `activateRoom` runs (see the Rooms section above) — easing FROM that arbitrary 0
every time would read as the camera visibly sliding in from the room's left edge on every single
room entry, which nothing asked for and is a worse experience than the old instant snap it's
replacing. `cameraFollowSnapNeeded` (reset `true` alongside `cameraX = 0` in `activateRoom`) makes
`updateCamera`'s first Follow tick in a freshly-hot room snap straight to the target, same as the
old behavior always did, with only every tick after that eased.

**Fixed and Runner modes are completely untouched** — Fixed always sets `cameraX = 0` and Runner
advances at its own constant `RUNNER_SPEED`, neither of which ever had a jitter complaint; the
easing is scoped to the one branch that actually had the reported problem.

**Export pipeline**: `CAMERA_FOLLOW_RATE` got its own `constantsSource` line;
`cameraFollowSnapNeeded` was added to the export template's own duplicate global declarations
(right alongside its existing `cameraX` line) — `updateCamera`/`activateRoom` were already shared
into the export from earlier patches, so the eased behavior applies automatically.

Verified with Playwright: entering Play with Follow mode active snaps the camera to the clamped,
centered-on-player target within the very first frame (not starting at 0 and visibly sliding in);
holding the player perfectly still for a sustained run shows zero camera movement at all (previously
the complaint — sub-pixel wobble reads as a dead-still camera now, not a jittering one); a sudden
large jump in the player's position eases the camera toward the new target over multiple frames
rather than snapping instantly, and fully catches up given enough time; Fixed and Runner camera
modes are confirmed unaffected; the same snap-on-entry and steady-while-idle behavior holds
identically in a freshly exported standalone game; and the full 5-sample regression sweep plus a
fresh Button+Gate export both still run clean.

## Follow camera, round two: a real render bug, plus a genre-standard dead zone (v2.40)

Direct follow-up right after v2.39 shipped its easing fix: "this is still very jerky. 1) the
motion needs to be smooth (not moving a tile at a time), and 2) the follow camera mode should
probably be more a transition... Is there not a common convention for how this is done in video
games?" Two separate things were actually wrong, and the second request named a real, well-known
genre convention this engine had never implemented.

**The actual root cause of "moving a tile at a time" was never cameraX — it was the renderer.**
v2.39's exponential ease made `cameraX` itself move smoothly, but `renderRoomContents` (and
`drawFanStream`, and the faint grid overlay) had always taken a pre-floored `viewStartCol =
Math.floor(viewOffsetPx / TILE)` and drawn every tile at `sx * TILE` — a plain whole-tile screen
column. No matter how smoothly the underlying camera position eased, the DRAWN tiles only ever
jumped to a new position once `viewOffsetPx` crossed a full `TILE` (32px) boundary, snapping
instantly the rest of the time. Confirmed by code read, not just suspected: `renderActors` already
used the raw continuous `viewOffsetPx` to position actor sprites (`actor.x - viewOffsetPx`), so the
player itself was always moving smoothly — the MISMATCH between a smoothly-sliding player sprite
and a tile-snapping background underneath it is exactly what would read as jerky regardless of any
camera-side easing. This had been latent since v2.17 (Runner mode's own continuously-advancing
`cameraX` has always had the identical bug, just apparently never flagged) — Fixed and Build-mode
panning never exposed it because both only ever move in whole-tile steps to begin with.

**Fix: `renderRoomContents`/`drawFanStream` now draw every tile at its exact continuous screen
position** (`screenX = bx * TILE - viewOffsetPx`) instead of a snapped column, sweeping one extra
edge column (`firstCol` to `firstCol + COLS` inclusive) so nothing pops in or out as the fractional
remainder crosses 0 — harmless when the extra column lands off-canvas. The three `renderGame` call
sites now pass the real `viewOffsetPx` straight through instead of a pre-floored `viewStartCol`,
which no longer exists as a concept. The thin grid overlay (`rgba(255,255,255,0.06)` lines, drawn
unconditionally in both Build and Play) used to sit at fixed screen columns regardless of
`viewStartCol` — harmless before, since every camera that ever moved did so in whole tiles, but it
would have visibly drifted out of sync with the now-smoothly-scrolling tiles underneath it, so it
scrolls with the same `screenX` formula now. This fix is a no-op for Build mode and Fixed rooms
(`editorPanCol * TILE` is always an exact tile multiple) — only Follow and Runner, the two camera
modes with a genuinely sub-tile position, are affected.

**The second ask — "more a transition," with specific numbers (85%/40%) — named a real, standard
pattern: a camera dead zone with a look-ahead anchor**, the same family of camera used in Mario,
Metroid, and Celeste. v2.39's continuous "always centered on the player" easing was replaced
outright (not layered on top) because dead-center tracking is structurally the wrong shape for this
ask — a kid's own small side-to-side wiggling continuously nudges a centered camera, which never
reads as "smooth," only as "still twitchy, just damped." The dead zone fixes that at the source: the
camera doesn't move AT ALL while the player stays within a band of the screen, and only shifts once
they approach an edge.

**Mechanically**: `CAMERA_DEADZONE_TRIGGER_FRAC` (0.85) is the screen fraction a shift is triggered
at; `CAMERA_DEADZONE_ANCHOR_FRAC` (0.40) is where the player ends up resting after the shift — 40%
from the left when moving right, mirrored to 60% from the left (= 40% from the right) when moving
left, the standard "look-ahead" bias of showing more room in the direction of travel than behind it.
Letting the trigger and the rest point be two DIFFERENT numbers, rather than a single dead-zone edge
the player is simply pinned against (the more textbook Mario-style shape), is what produces the
"reveals a chunk of room, then holds" feel that was explicitly asked for, instead of a camera that
creeps along just barely keeping pace with the player's own edge-hugging.

**A real design mistake caught and fixed before shipping, worth remembering for any future
dead-zone-style mechanic**: a first implementation computed the shift target fresh every tick purely
from the CURRENT frac — "chase the 40% anchor only while frac > 85%, otherwise freeze" — on the
theory that this would be self-terminating with no state needed. Verified by direct trace and found
wrong: since the trigger (85%) and the anchor (40%) are different numbers, the eased `cameraX` only
has to crawl a little before frac dips back under 85%, and the very next tick's "else freeze" branch
catches it there — the shift stalled around ~78-80% and never got anywhere near 40%. Fixed with real
remembered state, `cameraShiftSide` (`null`/`"right"`/`"left"`, reset alongside `cameraX`/
`cameraFollowSnapNeeded` in `activateRoom`): once a trigger edge is crossed, the camera keeps
chasing THAT side's anchor — recomputed every tick from the player's live position, so a sustained
run keeps revealing room continuously — until frac actually reaches the anchor (within
`CAMERA_DEADZONE_SETTLE_EPS`, 0.02) or the camera hits the room's own edge, only then dropping back
to `null` and letting the dead zone re-engage. `CAMERA_DEADZONE_SHIFT_RATE` (16, faster than v2.39's
own 9) is the same exponential-ease shape as before, just snappier — "smoothly and quickly," not a
gentle idle correction, and genuinely irrelevant while frozen: inside the dead zone `cameraX` is
simply never written to, not eased toward itself.

**The very first Follow-mode tick after a room becomes hot still snaps instantly to a plain centered
target** (`cameraFollowSnapNeeded`, unchanged from v2.39) rather than picking a 40%/60% anchor —
there's no established direction of travel yet on room entry to pick one from, and easing in from
the fresh room's `cameraX = 0` would visibly slide the camera in from the edge on every single
entry, which was never asked for.

**Export pipeline**: `CAMERA_DEADZONE_TRIGGER_FRAC`/`CAMERA_DEADZONE_ANCHOR_FRAC`/
`CAMERA_DEADZONE_SETTLE_EPS`/`CAMERA_DEADZONE_SHIFT_RATE` each got `constantsSource` lines (replacing
v2.39's single `CAMERA_FOLLOW_RATE` line, now gone); `cameraShiftSide` was added to the export
template's own duplicate global declarations alongside its existing `cameraX`/
`cameraFollowSnapNeeded` lines. `updateCamera`/`activateRoom`/`renderRoomContents`/`drawFanStream`
were already shared into the export from earlier patches, so the fixed renderer and the new
dead-zone behavior both apply automatically.

Verified with Playwright: a small in-dead-zone player movement produces exactly zero camera
movement (not just "very little"); crossing the 85% trigger moving right shifts the camera forward
and the player settles within 5% of the 40% anchor, then the camera freezes again (two more samples
300ms apart read identically); the mirrored leftward case (15% trigger, 60% rest point) produces the
same result in the other direction; `cameraX` itself is confirmed to move in genuine non-32px-multiple
(sub-tile) increments during an active shift, proving the value feeding the renderer is truly
continuous; the camera clamps correctly and holds rock-stable (no oscillation) when the player is
pinned near a room's physical edge; Runner mode (which already had a continuously-advancing
`cameraX`, now benefiting from the same render fix) plays cleanly and its camera genuinely advances;
the exact same dead-zone-freeze/trigger/settle sequence is confirmed working identically in a
freshly exported standalone game; and the full 5-sample regression sweep plus a fresh Button+Gate
export both still run clean.

## Palette prose reduction: one caption line and two real affordances replace most of the hint text (v2.41)

Direct request, stated as a design principle rather than a list of sentences to delete: "the UI
should teach through affordances, the way a box of Lego does — try it, discover it — not through
documentation." The request itself sorted the fix into three different categories by which
problem each one actually solves, explicitly warning against a single blanket "remove hints"
pass — "some things being cut need an affordance in their place, not silence." (This patch
reuses the "v2.41" label purely as an internal code-comment convenience to avoid colliding with
this doc's own existing, unrelated v2.22 section — see "Version labels are not reliable" above;
it isn't claiming a real chronological position.)

**Category 1 — cut outright, no replacement.** Wherever a click's effect is immediate and
plainly visible, the paragraph explaining it added nothing a kid couldn't already see: the Game
Rules paragraph (gravity/wrap), the Camera paragraph (Fixed/Follow/Runner), the category-level
blurbs under Characters ("Custom characters"), Objects ("Pick an object"), Fixtures, and
Collectibles that restated the v2.14 sprite-vs-colored-square taxonomy in words, and the bottom
catch-all hint about Ground/Surface using built-in icons while Paint/Characters are hand-drawn.
All of these `.hint` blocks are simply gone from the HTML — no new mechanism replaces them because
none was needed.

**Category 2 — one fixed caption line, not scattered tooltips.** The real problem this solves:
choosing between similar-looking things with genuinely different consequences before testing any
of them — Hazard vs. Lethal vs. Diggable vs. Trap is the request's own motivating example. Built
as a single shared mechanism rather than per-item floating tooltips (which would have meant
solving placement/collision for every swatch individually): `CAPTION_TEXT` is a plain lookup
object (same shape as the existing `GEOMETRY_LABELS`/`MODIFIER_LABELS` pattern) mapping whatever
plain identifier each row's own render function already iterates by — a geometry string, a
modifier string, an actor kind, or a camera-mode key — to a short caption. `wireCaption(el, text)`
attaches `mouseenter`/`mouseleave`/`touchstart` listeners that write to one fixed DOM element,
`#captionBar` (new, sits right under the `<h1>`, never reflows since its height is fixed by CSS
regardless of caption length) — the same element serves hover (desktop, cleared on
`mouseleave`) and last-tap (touch, deliberately NOT cleared on any touch-end equivalent, so a
tapped caption stays legible after the finger lifts) with zero separate touch-handling logic, per
the request's own "same mechanism serves both input types" instruction. `CAPTION_IDLE_TEXT`
("Hover (or tap) a piece to see what it does.") is both the HTML's own static initial content and
what `setCaption` falls back to whenever `text` is empty/undefined — a plain Ground texture or a
Collectible or a Character preset has no entry in `CAPTION_TEXT` at all, so hovering one is a
silent no-op (idle text keeps showing), consistent with category 1's own test: a texture or
preset swatch is "choosing a look," not "choosing a consequence," so there's nothing a caption
would usefully add. `wireCaption` is called from every render function whose row this patch
touches: `renderSurfaceSwatches` (Ground Effects — this is the direct replacement for the retired
"Hazard costs one life... Trap looks solid" paragraph), `renderGroundSkinSwatch` (shared by the
Ground row and the Lethals row — only the four built-in Lethal ids resolve to real text, a
texture id silently no-ops through the same shared call site), both loops in `renderObjectSwatches`
(actor kinds and tile geometries), `renderFixtureSwatches`, and `renderCameraSwatches`. The
request supplied nine example captions verbatim (cannon, bomb, magnet, lava, hazard, lethal,
diggable, trap, runner camera) and explicitly called the list "a starting point for the voice, not
the full set, reasonable to do directly in code" — the remaining captions (fan, spawner,
trampoline, Gate, crate, large stone, fire/spike/mine, the other Ground Effects, goal/plate/door/
warp/gravitywell/button, Fixed/Follow) were written directly in this patch in the same short/
funny/names-the-effect voice, a judgment call made without asking first since the request itself
authorized it; flag any that land wrong.

**Category 3 — two affordances replacing a sentence, not a shorter sentence.** Both describe
something genuinely invisible on screen today, where cutting the sentence would hide a real
discoverability gap rather than fix it:
- **Rotate badge.** The old "Double-click any painted Ground texture or Lethal to spin it 90°"
  sentence is gone, replaced by a small vector-drawn circular-arrow badge
  (`drawRotateBadge`, plain canvas primitives — not pixel art, matching `drawEmptySocketCue`'s own
  precedent that a Build-mode-only editing cue doesn't need to live in the game's ART-resolution
  sprite system) in the top-right corner of whichever Ground/Lethal-skinned cell is currently
  hovered (desktop) or last tapped (touch). "Selected tile" wasn't an existing concept anywhere in
  this codebase, so a new `hoveredGroundCell` (`{gx, gy}` or `null`) reuses the exact same
  hover/last-tap duality the caption bar already established rather than inventing a second one —
  updated by the same `mousemove`/`touchstart`/`touchmove` listeners that already exist for
  painting, plus one new `mouseleave` listener (touch has no "leave" gesture, so a tapped badge
  deliberately persists until the next tap, same asymmetry as the caption bar). Drawn inside
  `renderGame`'s existing `appMode === "build"` block, gated on `groundSkinBoard[gy][gx]` being
  truthy at the hovered cell — a silent no-op over an empty cell, a plain `none`/`solid` swatch, or
  any modifier with no named skin, since double-click-rotate was never meaningful there either.
  The double-click-to-rotate mechanic itself (`rotateGroundSkinAt`) is completely untouched — only
  the sentence describing it is gone, replaced by a badge that shows up exactly where that
  mechanic actually applies.
- **Door-color-cap greyout.** The old "Only two doors can ever share one color" sentence (plus
  its surrounding Button/Gate/Door color explanation — all three Object Color paragraphs, in
  fact) is gone. `renderColorSwatchesInto` now computes `isDoorColor = containerId ===
  "objectColorSwatches" && selectedGeometry === "door"` and, only in that case, checks each color
  option against the existing `findDoorsWithColor(color).length >= 2` — the same helper
  `wireColoredDoor` already uses to enforce the cap reactively. A full color gets a `.full` CSS
  class (dimmed, grayscale, `cursor: not-allowed`) and no click listener at all (not just a
  disabled-looking one that still fires), plus a title-attribute explanation
  ("— already used by two doors") for anyone who does hover it. The limit was already enforced
  server-side exactly as before (`wireColoredDoor` still refuses and reverts a would-be third
  placement, unchanged) — this only adds the proactive visual cue a kid sees before reaching for
  a color that's already spoken for, instead of after. Scoped specifically to Door colors (via
  the `isDoorColor` check) — every other color-taggable geometry (solid wall, barrier/Gate,
  pushbutton/Button, plate) has no such cap and is unaffected.

**Net effect, matching the request's own framing.** The three Object Color paragraphs and the
Ground Effects Hazard/Lethal/Diggable/Trap paragraph — the densest prose in the old palette — are
fully retired: the color-linking logic is now just the door-cap greyout (3) plus whatever the
caption line (2) covers for Button/Gate in passing, and the modifier-behavior paragraph is
replaced entirely by per-swatch captions (2). Nothing about what any piece actually does changed —
only how a kid finds out. Left deliberately untouched, since none of these were named in the
request: the plain Ground-row hint ("What it looks like, and whether it blocks you"), the Ground
Effects "two independent choices" hint, the Lethals-row hint, the `groundColorBlock` hint
(colored solid walls — a different block from the retired `objectColorBlock` paragraphs), and the
Paint/`presetsBlock` hints.

**No backward-compat or export-pipeline work needed.** This is pure Build-mode palette UI — no
board/project data format changed, nothing here is serialized, and `renderGame`'s new
rotate-badge branch lives inside the exact same `appMode === "build"` guard that already wraps
`isCanvasEmpty`/`drawEmptySocketCue` (themselves never added to `exportStandaloneGame`'s
`runtimeFunctions`) — an exported game hardcodes `const appMode = "play"`, so that whole branch,
`hoveredGroundCell` included, is statically unreachable there and needs no export wiring, the same
established precedent those two existing Build-only helpers already set.

Verified with Playwright (47 checks across three passes): every wired swatch's caption text
matches exactly on hover, including the full Hazard/Lethal/Diggable/Trap/lava set named in the
request; the idle caption shows by default and is restored on `mouseleave`; a plain Ground texture
swatch has no caption override (idle text stays); `touchstart` also sets the caption without
needing `mouseleave` to clear it first; every one of the ten retired hint paragraphs is confirmed
absent from the palette's own DOM text (checked against `.hint`/`.section-title`/`#captionBar`
specifically, not `document.body.textContent`, which would have false-matched this very test's
own source-code comments describing the retired sentences); the untouched hints (groundColorBlock,
Paint, presets) are confirmed still present; painting a single colored door (which auto-pairs with
a brand-new room's own return door of the same color, reaching the 2-cap immediately) marks that
color swatch `.full` with an explanatory title and no click handler, and un-marks it once erased
back down to one; a non-door color-taggable geometry (a plain colored wall) never shows `.full`
regardless of how many share a color; an empty cell and a painted ground-skinned cell are
confirmed to feed the rotate-badge's own guard condition correctly; double-click-to-rotate still
fires with zero errors on a painted tile; and the full 5-sample regression sweep (including the
one built-in sample, The Monster's Den, with its own live Button/Gate puzzle) plus a fresh
Button+Gate export — confirmed to have no `#captionBar` in its output, correctly excluding this
whole patch's UI from the shipped game — both run error-free.

## Git / commit conventions

- One file changes almost every commit: `index.html`. Commit messages so
  far explain the **why** for each feature at some length (see `git log`)
  — matches this project's own principle of design rationale mattering
  more than mechanical description. Keep that style.
- No PRs opened unless explicitly asked; work happens directly on the
  designated feature branch per the session's instructions.
- Nothing else in the repo needs updating for a typical feature patch —
  no lockfile, no build artifacts, no test files (those are scratchpad-only
  and never committed).
